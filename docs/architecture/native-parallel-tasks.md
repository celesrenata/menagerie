# Native parallel tasks

The `parallelTasks` experiment exposes `parallel_tasks`. It runs one to four independent full Zoo agents in separate editor tabs and Git worktrees. It uses a process-wide pool of four workers; each worker retains the existing single-task runtime. The parent waits in one tool call, collects all terminal results, and reviews/applies the returned patches. Completion text crossing back into the parent is bounded (smaller for `project-reader` workers); the full worker result remains persisted in the batch manifest and worker record. The ordinary `new_task` handoff remains available for dependent work.

Each worker receives its mode and provider configuration through the same `getTaskHandoffContext` policy as serial delegation. Mode/profile locking and saved profile mappings still apply. No worker changes the parent's selected profile. Worker tools cannot create further tasks, avoiding nested-pool deadlocks.

The worktrees contain a Git snapshot of current tracked and non-ignored untracked files, created with a private index and an unattached commit. The source index, branch, and files stay unchanged. A committed HEAD is required. Ignored dependencies and secrets are not copied; workers may need to install dependencies. Commands retain the user's existing permissions; a worktree is file isolation, not an operating-system sandbox.

The tool owns result delivery. Worker completion/cancellation listeners are installed before dispatch. Parent cancellation, disposal, and the 30-minute batch deadline cancel queued workers and stop admitted workers. Every admitted runtime is disposed before its permit is released and its patch is exported. Manifests and per-worker records live under the extension's global storage `parallel-tasks/<batch-id>/`. Worktrees and patches remain available for review. After an extension-host restart, an interrupted batch is not automatically resumed or injected into a parent; inspect its per-worker records and histories, then explicitly resume or start a new batch. Once results have been retained or integrated, remove worktrees explicitly using `git worktree remove`.

The separate `parallelToolExecution` experiment runs contiguous, complete native read calls concurrently, up to eight at a time. The allowlist is `read_file`, `list_files`, `search_files`, `codebase_search`, and `read_command_output`. Batched `read_file` calls share a bounded default line budget when no explicit limit is supplied so a wide read does not multiply the single-file default into the parent context. Assistant history must be persisted before admission; all results join before the next command, edit, MCP call, or model turn. Unknown tools are barriers. Manual asks and status messages use a task-local UI mutex so one read cannot consume another read's approval. Both experiments default off and use the existing experiment settings persistence path.

These are independent task runtimes linked by a batch manifest, not a multi-child replacement for the boomerang lifecycle. Existing lifecycle reducers remain unchanged. Pool, result ownership, manual approval, presenter barriers, and Git preservation have focused tests. The real extension-host test proves three simultaneous inference requests, distinct code/long profiles, multiple native reads, isolated edits and returned patches. The optional abstract fanout model remains a separate safety reference, rather than a claim of a production trace adapter.

The `Zoo: Show Task Board` command opens a native tree of currently open chats in this extension host. Each row includes mode, status, checklist progress, provider profile, model, workspace, task ID and parent ID. Selecting a row focuses its existing chat. Closed chats remain in History; the board does not infer that a historical interrupted chat is running. `zoo-code.getTaskBoard` returns a fresh JSON snapshot, and `Zoo: Export Task Board JSON` opens a saved snapshot. Once the board is opened, it publishes a private snapshot every five seconds under global storage `task-boards/<window-id>.json`. Consumers must check `updatedAt`; a saved file can outlive its extension host. Each VS Code window must open the board once to publish live snapshots.

Spec-driven behavior is supplied by the separately installed `spec-orchestrator` custom mode and Spec Kit slash-command bridges. They mirror stable task IDs and spec paths into Zoo's existing `update_todo_list`; the Task Board displays that checklist without introducing another task database. These are agent instructions, not a compiler-enforced acceptance gate. Existing mode/profile mappings still determine routing.
