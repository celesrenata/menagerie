# Pagination clamp fix for OmniRoute `/api/combos` 0-combos symptom

The plan ruled out data corruption with direct in-pod SQLite evidence (91/91 rows well-formed) and traced the reported "0 combos" to `paginationSchema` hard-rejecting `limit > 200` with an HTTP 400, which a status-blind caller would read as zero results. The fix (commit `c9230dee8`, local on `feat/hybrid-reader-combo`, not pushed) replaces the Zod `.max(200)` rejection with a `.transform()` clamp to 200, and adds a `console.warn` on the pre-existing silent-drop path in `parseComboRow` so a genuine legacy-data recurrence would be visible in logs. Both changes match the plan's prescribed fix verbatim — no scope drift, no reversion of FEAT-002/004/005 (confirmed via `git log`, those commits sit untouched beneath this one on the branch).

Watch for: this is a shared-schema change affecting three other routes (`model-combo-mappings`, `playground/presets`, `provider-nodes`) that silently inherit a 400→200 behavior change for `limit > 200` — confirmed intentional and tested, but worth knowing the blast radius extends past combos. Also note the fix is uncommitted-to-remote and unreleased (no rebuild/redeploy performed), so it does not yet address the live pod.

**Verdict**: APPROVED

## High-level view

The root cause is confirmed, not guessed: the plan's live-pod evidence (91 well-formed rows, identical `all=true` vs. no-params behavior, a reproducible 400 on `limit=300`) is thorough enough to rule out the data-corruption hypothesis and pin the defect precisely on `paginationSchema`'s hard cap. The code change is a minimal, correctly-scoped Zod schema edit plus a one-line warning log, both exactly as specified in the plan.

The 0-result case is handled by the clamp (300/1000 → 200 clamped, 200 response instead of 400) and the 5-result (legacy/malformed-row) case is handled by the pre-existing silent-drop behavior in `parseComboRow`, now with a warning log naming the dropped row's id — the plan explicitly chose not to "fix" that drop since there's no evidence any row is currently malformed, which is the right call given the evidence.

Tests cover both symptom paths: the clamp boundary (0, 200, 201, 300, 1000) and the silent-drop-plus-warning path via a BLOB-backed row that bypasses the normal JSON-string write path. Verification evidence in `verification.md` shows 39 targeted tests, 99 sibling-route tests, 421 broader-combo-suite tests, and a clean `typecheck:core` run, all plausible in scope and consistent with the diff's size.

FEAT-002/004/005 commits are untouched on the branch — confirmed via `git log --oneline`, they sit as prior commits beneath `c9230dee8` with no reverts or amends.

### Schema change: clamp instead of reject

`src/shared/validation/schemas/misc.ts`'s `paginationSchema.limit` moves from `z.coerce.number().int().min(0).max(200).optional()` to the same chain minus `.max(200)`, with `.transform((v) => (v === undefined ? v : Math.min(v, 200)))` appended. Verified by reading the diff directly: `undefined` passes through untouched (so "no limit" still means unbounded, matching the `GET /api/combos` route's existing `range.limit !== undefined` branch in `getCombos`), and any defined value — including `0` — gets `Math.min(v, 200)` applied, which is a no-op below 200 and a clamp above it. The `limit=0` test case specifically guards against `Math.min(0, 200)` accidentally becoming falsy/undefined and reactivating the unbounded path; reading `getCombos`'s `if (limit !== undefined)` branch confirms `0` is `!== undefined` so the `LIMIT 0` SQL path is preserved correctly.

This schema is shared by four routes (confirmed via grep: `combos`, `model-combo-mappings`, `playground/presets`, `provider-nodes`), so the 400→200 behavior change for over-cap `limit` values lands on all four simultaneously, consistent with how the original `.max(200)` cap was introduced across all four in one commit per the plan. The plan's claim that no existing test asserts a 400-for-`limit>200` on any of these four routes checks out: `tests/unit/pagination.test.ts` targets a separate `parsePaginationParams` helper (confirmed by reading the test file — it imports and calls `parsePaginationParams`/`buildPaginatedResponse`, not `paginationSchema`), so there's no stale test asserting the old 400 contract that would now be silently passing on a changed assumption.

### Test coverage

The new test file seeds a malformed row by inserting a `Buffer` directly via raw SQL, deliberately bypassing `createCombo`'s normal write path — this is the correct way to simulate the legacy/corrupted-row shape, since SQLite's TEXT column affinity would otherwise coerce a string or number literal back to text on storage and defeat the test's purpose. The four clamp-boundary tests (0, 200, 300, 1000) cover Fix 1's off-by-one risk at the exact 200 boundary; the malformed-row test covers Fix 2's warning text and id.
