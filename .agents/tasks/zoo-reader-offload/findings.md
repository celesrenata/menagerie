# Zoo (Roo Code fork) — Can file reads be moved off the orchestrator's own model?

**Investigation:** read-only. Branch `feat/omniroute-tier-dropdown-feat005`. Repo `/Users/celes/sources/celesrenata/menagerie`.

---

## Summary answer (TL;DR)

**No. In Zoo today there is no core mechanism that moves an inline `read_file` (or `list_files` / `search_files` / `codebase_search`) off the active task's own model.** A tool result is architecturally returned straight into the calling task's conversation history and is therefore processed by that same task's single API handler (`this.api`). For the spec-orchestrator running on GLM, that means every inline read is read "by" GLM. This is by design, not a misconfiguration.

The ONLY reader-model routing that exists applies to **parallel workers** (dispatched sub-tasks), and even that is:

1. driven by the **worker's `mode`**, not by read activity, and
2. invoked only when the **orchestrator LLM explicitly calls the `parallel_tasks` tool** (or, in one narrow auto case, when exactly three `code` workers share a referenced design doc).

Zoo also **does not have** a separate "condensing API configuration" model (the upstream Roo Code feature). Context condensing/summarization runs on the task's own `this.api` too. So there is no condensing lever to push reads onto a cheaper model either.

**Bottom line for the user:** getting reads onto the 9B/27B readers (`hybrid/reader`, `hybrid/research`) **fundamentally requires the orchestrator model to choose to delegate** by dispatching `project-reader` / `project-research` parallel workers. No configuration can force an inline parent read onto another model. The nearest real lever is behavioral (mode prompts / rules that make the orchestrator delegate), not structural.

## Evidence

### Q1 — Is any read tool ever executed by a _different_ model than the running task?

**No. Tool results return inline into the active task's own context.**

- Read tools are plain executors: `ReadFileTool`, `ListFilesTool`, `SearchFilesTool`, `CodebaseSearchTool` in `src/core/tools/`. They read from disk and hand bytes back via a callback. `ReadFileTool.execute()` (`src/core/tools/ReadFileTool.ts:85`) does filesystem reads (`extractTextFromFile`, `readWithSlice`, `readWithIndentation`) and returns results through `callbacks.pushToolResult(...)` (e.g. `src/core/tools/ReadFileTool.ts:109`, `:113`). There is no model call anywhere in the read tools.
- The dispatch harness `BaseTool.handle()` (`src/core/tools/BaseTool.ts:116`) parses args and calls `this.execute(params, task, callbacks)` (`src/core/tools/BaseTool.ts:168`). The `ToolCallbacks` (`src/core/tools/BaseTool.ts:9-14`) are just `askApproval` / `handleError` / `pushToolResult` — no model handle, no routing, no secondary-model hook. `pushToolResult` writes the content back into the same task's `userMessageContent`, which is then sent to that task's own `this.api` on the next turn.
- There is **no model indirection** between a read and the context it lands in. A tool result is always consumed by the task that issued the tool call.

**Condensing is the only place a read-adjacent payload is re-processed by a model — and it uses the task's OWN model, not a reader.**

- `summarizeConversation()` (`src/core/condense/index.ts:302`) performs the only "read heavy content, re-emit a shorter version" LLM call. It takes an `apiHandler` and calls `apiHandler.createMessage(...)` (`src/core/condense/index.ts` inside `summarizeConversation`).
- Every caller passes **`apiHandler: this.api`** (the task's own handler):
    - `Task.condenseContext()` → `summarizeConversation({ ..., apiHandler: this.api })` (`src/core/task/Task.ts:2009`, `:2012`).
    - `Task.handleContextWindowExceededError()` → `manageContext({ ..., apiHandler: this.api })` (`src/core/task/Task.ts:4569`, `:4575`).
    - `Task.attemptApiRequest()` → `manageContext({ ..., apiHandler: this.api })` (`src/core/task/Task.ts:4828`, `:4834`).
- `manageContext()` forwards that same handler into `summarizeConversation` (`src/core/context-management/index.ts`, `manageContext` → `summarizeConversation({ apiHandler, ... })`).
- Condensing _does_ fold read file content (`filesReadByRoo`, `generateFoldedFileContext`, `src/core/condense/index.ts`), but it folds them into a summary generated by the **same** model — it does not offload the reading to another model.

**Conclusion Q1:** No read tool is ever executed by, or returned into, a different model. The only secondary processing (condensing) runs on the active task's own model.

### Q2 — What triggers a parallel worker / subtask dispatch? Is any read auto-routed to a reader?

**Dispatch is LLM-driven. There is no programmatic auto-routing of inline reads to reader workers.**

- The dispatch tool is `parallel_tasks` (`ParallelTasksTool`, `src/core/tools/ParallelTasksTool.ts:34`). It only runs when the **orchestrator model emits a `parallel_tasks` tool call**. It requires the `parallelTasks` experiment (`src/core/tools/ParallelTasksTool.ts:48`) and forbids nested dispatch from workers (`src/core/tools/ParallelTasksTool.ts:51`).
- Sub-tasks via `new_task` are likewise LLM-driven (the model calls `new_task`; see `src/core/webview/ClineProvider.ts:3350`, `:4199`).
- Worker model selection happens in `runParallelTasks()` at `src/core/task/runParallelTasks.ts:45`, via `resolveWorkerModelId(spec.route, spec.mode, context.apiConfiguration, parent.apiConfiguration.openAiModelId)`. Precedence (pure id pass-through, OmniRoute owns placement): explicit `spec.route` → `roleDefault(mode)` → parent model id (`src/core/task/parallelWorkerRouting.ts:32-39`).
- `roleDefault()` maps `READER_MODES` → `openAiOmniRouteReaderRouteId`, everything else → `openAiOmniRouteReasonerRouteId` (`src/core/task/parallelWorkerRouting.ts:22-24`). `READER_MODES = new Set(["project-reader"])` (`src/core/task/parallelWorkerRouting.ts:10`). **This routing keys off the worker's `mode`, not off whether the worker reads files.**

**The `addSharedDocumentReader` mystery is resolved — it is implemented, just narrow and auto-fired, NOT a general read-offload.**

- It lives in `src/core/task/ParallelTaskReader.ts:46` (the earlier grep found zero hits only because it was run against a different spelling/scope; the symbol is real and imported by `ParallelTasksTool.ts:8` and called at `ParallelTasksTool.ts:51`).
- It appends **one** extra `project-reader` worker (`AUTO_READER_NAME = "m5-contract-audit"`, `ParallelTaskReader.ts:11`) and ONLY when **all** of these hold (`ParallelTaskReader.ts:51`): the `project-reader` mode exists, there are **exactly 3** workers, **all** are `mode: "code"`, and **≥2 of them reference the same `docs|specs|contracts/*.md|…` document** (`SHARED_DOCUMENT` regex, `ParallelTaskReader.ts:5`; threshold `count < 2` continue, `ParallelTaskReader.ts`).
- That extra worker is handed a **pre-extracted excerpt** of the shared doc and is explicitly told **not** to call `read_file` or investigate the repo (`ParallelTaskReader.ts`, the generated `message`). So even this "reader" does not do live file reads routed off the orchestrator — it audits a bounded excerpt. It is an idle-GPU filler for a specific fan-out shape, not a general read-offload mechanism.

**Conclusion Q2:** No automatic/programmatic routing of inline reads to reader workers exists. Reader-mode workers only run when the orchestrator LLM dispatches `parallel_tasks`, and the single auto-added reader (`addSharedDocumentReader`) fires only in the 3×`code`-workers-share-a-doc case and is forbidden from reading files itself.

### Q3 — Is there a condensing / context-management model setting selecting a separate cheaper model?

**No. Zoo has only a custom condensing _prompt_, not a condensing _model_ selector.**

- Grep for `condensingApiConfigId | condensingApiHandler | getCondensing | condensingApiConfig` across `src/**/*.ts` returns **zero matches**. Upstream Roo Code exposes a "condensing API configuration" (a separate profile for summarization); **this fork does not have it.**
- What _does_ exist is `customCondensingPrompt` (prompt text only): `packages/types/src/global-settings.ts:133`, surfaced as `customSupportPrompts.CONDENSE` and read at `src/core/task/Task.ts` condensing path. There is no field anywhere selecting a different model/profile for condensing.
- Because every condensing call uses `apiHandler: this.api` (see Q1 citations: `Task.ts:2012`, `:4575`, `:4834`), condensing for the GLM orchestrator runs on GLM.

**Conclusion Q3:** There is no condensing-model setting to push reading/summarization work onto a cheaper model. The only configurable condensing knob is the prompt text.

### Q4 — Definitive statement

**File reads cannot be moved off the orchestrator's own model (GLM) through configuration or any existing inline feature.** The architecture returns every tool result into the issuing task's own context, and that task has exactly one API handler (`this.api`). Condensing — the only secondary-model-shaped operation — also runs on that same handler, and no separate condensing-model setting exists in this fork.

The only way to get reads onto a reader model (9B `hybrid/reader` / 27B `hybrid/research`) is for the **orchestrator LLM to explicitly delegate** by dispatching `project-reader` / `project-research` workers via the `parallel_tasks` tool. That worker then runs on its role-default route (`openAiOmniRouteReaderRouteId` / `openAiOmniRouteReasonerRouteId`) and does its own reads on that model — but **the orchestrator must choose to delegate**; it cannot be forced structurally. (The sole automatic exception, `addSharedDocumentReader`, is narrow, fires only for the 3×`code`-worker/shared-doc shape, and explicitly forbids its worker from reading files.)

## Why the live logs show GLM reading, turn after turn

Given the above, the observed behavior (`Trying model 1/1: llama-cpp/ds4-glm53 with 56 tools`, inline `read_file`, 37s–120s/turn) is exactly what the architecture dictates: the spec-orchestrator issued inline `read_file` calls, the results returned into its own context, and its own model (GLM) processed them. Nothing was eligible to route elsewhere because no inline-read offload path exists.

Note also: `resolveWorkerModelId` only runs inside `runParallelTasks` for _dispatched workers_. An orchestrator opened directly in the `orchestrator`/`spec-orchestrator` mode is the **parent**, so its own reads never pass through `roleDefault` at all.

## Recommendation — the single most-core lever

There is **no config-only structural lever**. Ranked, honest options:

1. **(Behavioral — the realistic lever today) Make the orchestrator delegate reads.** Shape the `spec-orchestrator` / `orchestrator` mode definition and rules so the model proactively dispatches `project-reader` (low/9B) and `project-research` (high/27B) workers for reading-heavy investigation instead of reading inline, and ensure those modes carry the correct role defaults. This is the only lever that works with the current code, but it depends on the orchestrator model actually choosing to delegate — it cannot be forced. Verify the OmniRoute profile has `openAiOmniRouteReaderRouteId` → `hybrid/reader` and `openAiOmniRouteReasonerRouteId` → `hybrid/research` set (`packages/types/src/provider-settings/openai.ts:103`, `:106`; mapping at `parallelWorkerRouting.ts:22-24`), so dispatched `project-reader`/`project-research` workers land on the intended models. Note `READER_MODES` currently contains only `project-reader` (`parallelWorkerRouting.ts:10`); `project-research` is treated as a _reasoner_ and would use `openAiOmniRouteReasonerRouteId` — align these sets with the user's intended 9B/27B split if `project-research` should be a reader-tier route.

2. **(Code change — the real "core thing in Zoo") Port upstream Roo Code's condensing API configuration.** Add a `condensingApiConfigId` setting and have `condenseContext()` / `manageContext()` build a _separate_ `ApiHandler` from that profile instead of `this.api` (`Task.ts:2012`, `:4575`, `:4834`). This would move the heaviest read/summarize work (context condensing + folded file context) onto a cheaper reader model globally, without the orchestrator deciding anything. It does **not** move _individual inline `read_file` calls_ off GLM — those still land in GLM's context — but it is the single most impactful core change for getting reading-heavy processing off the mastermind, and it matches the user's instinct that there is "a more core thing in Zoo." This is a non-trivial feature addition, not a toggle.

3. **(Not recommended as the primary fix) Expanding `READER_MODES` / `parallelWorkerRouting`** only affects _dispatched workers'_ model selection; it does nothing for inline parent reads. Useful only in combination with option 1.

**Plain-language answer to the user's question ("is there a more core thing in Zoo we need to do?"):** The structurally correct "core" change is porting a **condensing API configuration** (option 2) so summarization/condensing runs on a reader model. But for _inline per-file reads specifically_, there is no setting — the orchestrator must delegate (option 1). You cannot force inline reads onto another model via configuration in Zoo as it stands.
