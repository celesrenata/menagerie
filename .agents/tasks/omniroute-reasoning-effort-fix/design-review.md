## Findings

### 1. [MEDIUM] "Confirmed non-regression" stops at `getCredentialRequirement`; it misses a second, more consequential `authType`-keyed behavior change via `getProviderCategory()`

**Where:** Section 3, Step 1, "Confirmed non-regression of URL/header building" and the following "Accepted side effect" paragraph.

Registering `ollama-local` with `authType: "optional"` doesn't only change `getCredentialRequirement()`. It also changes `getProviderCategory(provider)` (`open-sse/config/providerRegistry.ts:304-308`):

```ts
export function getProviderCategory(provider: string): "oauth" | "apikey" {
	const entry = getRegistryEntry(provider)
	if (!entry) return "apikey" // Safe default for unknown providers
	return entry.authType === "apikey" ? "apikey" : "oauth"
}
```

Today, with no registry entry, `ollama-local` falls into the `!entry` branch and is categorized `"apikey"`. After the design's change, `authType: "optional"` is **not** `"apikey"`, so the function returns `"oauth"`. This is a real behavior flip, not a cosmetic one — `getProviderCategory()` feeds `PROVIDER_PROFILES` (`open-sse/config/constants.ts:258-293`), which has materially different oauth vs. apikey resilience numbers:

|                            | apikey (today, for ollama-local) | oauth (after this fix) |
| -------------------------- | -------------------------------- | ---------------------- |
| `providerFailureThreshold` | 15                               | 10                     |
| `providerFailureWindowMs`  | 30 min                           | 15 min                 |
| `providerCooldownMs`       | 10 min                           | 5 min                  |
| `circuitBreakerThreshold`  | 12                               | 8                      |

This is directly consumed by `providerCooldownTracker.ts`'s whole-provider circuit breaker (`providerWindowProfile`), `rateLimitManager.ts`'s auto-enable gate (`getProviderCategory(provider) === "apikey"` — `ollama-local` would silently **stop** qualifying for rate-limit-protection auto-enable), `errorClassifier.ts`'s 429/quota-signal preservation (`shouldPreserveQuotaSignalsFor429`), and `accountFallback.ts`'s `getProviderProfile`/`getRuntimeProviderProfile`. All of these are exactly the bug report's own symptom category (connections tripping/healing, 500s marking the connection unhealthy) — the design is making a change in the immediate vicinity of a resilience bug while introducing an unreviewed resilience-profile change for the same provider. This is a direct regression candidate for the user's `gremlin-4070ti-ollama` connection's breaker/cooldown math, not a cosmetic catalog-listing change like the credential-requirement side effect the design does analyze.

**Fix:** Either (a) set `authType: "apikey"` instead of `"optional"` on the new registry entry (Ollama genuinely has no credential requirement either way for the connect form via `LOCAL_PROVIDERS`'s own `authHint`, so this doesn't change the user-facing credential story, only the internal resilience bucket — verify this is acceptable), or (b) keep `authType: "optional"` but add an explicit paragraph analyzing the oauth-bucket resilience profile change for `ollama-local` and confirm with the user/reviewer that moving every `ollama-local` connection from the apikey breaker thresholds (15 failures/30 min, 10 min cooldown) to the oauth ones (10 failures/15 min, 5 min cooldown) is intended. Sibling local providers already registered with `authType: "optional"` (`g4f-ollama`, `ovhcloud`, `kilo-gateway`, `naga-ac`) are precedent for the credential story but the design never checks whether those providers' resilience-profile bucket change was itself reviewed — "precedent exists" is not the same as "the consequence was analyzed," and this design should not repeat an unexamined pattern for the same oversight it's trying to fix.

### 2. [MEDIUM] `overrideLookup`'s on-demand synchronous SQLite read is added to the hottest part of the per-request forwarding path with no caching, unlike every cited "precedent"

**Where:** Section 3, Step 4, "An operator override ... always wins" paragraph, citing `@/lib/db/paramFilters` as "the same cost class" precedent.

Verified: `getParamFilterConfig()` (`src/lib/db/paramFilters.ts:137-139`) reads from an **in-memory cache** (`loadParamFilterConfigs()` populates `filterCache` once and only invalidates on write via `bumpCacheGeneration()`); it is not a per-call SQLite query. Likewise, every current caller of `getModelCapabilityOverride`/`getReasoningEffortsOverride` outside the DB module itself (`src/lib/modelCapabilities.ts`, `src/lib/modelMetadataRegistry.ts`) passes a `bulk`/`snapshot` map built once per catalog build — none of them do an uncached per-call `getDbInstance().prepare(...).get(...)` in a per-request hot path the way Step 4 proposes wiring `getReasoningEffortsOverride` directly into `sanitizeReasoningEffortForProvider()`'s two live call sites (`targetRequestSanitizer.ts`'s `sanitizeRequestForResolvedTarget`, called once per `prepareUpstreamBody()`, and `base.ts`'s `BaseExecutor.execute()`, called on every attempt/fallback/retry URL). The design's claim that this "is the same cost class as the existing on-demand path already used in the hot request path" is not supported by what it cites — the paramFilters precedent is a cached read, not an uncached one, so there is no existing precedent for an uncached synchronous SQLite call fired on every chat-completion request to every provider (not just `ollama-local` — the new optional parameter is unconditional once wired at the two call sites, so if a caller does pass it, every request to every provider under that call path pays the SQLite read, including requests that have nothing to do with `ollama-local`).

**Fix:** Either (a) cache `getReasoningEffortsOverride` the same way `getParamFilterConfig` is cached (in-memory map keyed `provider/modelId`, invalidated on `setModelCapabilityOverride`/`removeModelCapabilityOverride`), or (b) explicitly scope Step 4's wiring so the override lookup is only invoked for providers that have a static `defaultSupportedThinkingEfforts`/`supportedThinkingEfforts` declared (i.e., gate it behind the same `declaredRanked.length > 0` check that already exists), so the extra DB read cannot regress the per-request latency of every provider that currently has zero reasoning-effort metadata. Also correct the "same cost class" claim or drop it — citing an existing cached pattern to justify a new uncached one is a factual error the design should not carry into implementation review.

## Verified Assumptions

- The forwarding path trace in §1 (steps 1–7, `handleChatImplementation` → `chatCore.ts` → `upstreamBody.ts`'s `prepareUpstreamBody()` → `targetRequestSanitizer.ts`'s `sanitizeRequestForResolvedTarget()` → `getExecutor()`/`DefaultExecutor` fallback for `ollama-local` → `BaseExecutor.execute()`'s second `sanitizeReasoningEffortForProvider()` call → the 400/422-only reactive recovery) is accurate; confirmed by reading every file in the chain.
- `applyReasoningEffortRecovery()` only triggers on `response.status === HTTP_STATUS.BAD_REQUEST || response.status === HTTP_STATUS.UNPROCESSABLE_ENTITY` (`reasoningEffortRecovery.ts:80-85`) — a bare 500 never reaches it, confirming why the live bug's HTTP 500 bypasses the existing reactive-learning safety net entirely, exactly as the design claims.
- `parseReasoningEffortEnum`'s `LIST_INTRO` regex does match the quoted Jinja error text ("Supported types are xhigh (default), medium, and low.") — confirmed by reading the regex and the matching test in `tests/unit/learned-reasoning-effort-caps.test.ts`'s general shape (not the exact Ollama string, but the regex construction supports it).
- `getRegistryThinkingEfforts()` does bake `entry.defaultSupportedThinkingEfforts` into its own return value (`providerRegistry.ts:204-213`), confirming the double-defaulting bug the design's Finding 1 (from the prior review pass) correctly diagnosed, and that the corrected Step 2 algorithm (`getRegistryModelThinkingEfforts()` exact-then-family, falling back to `getRegistryEntry(provider)?.defaultSupportedThinkingEfforts` only once) is a real fix: replaying it by hand against the registry data in the design produces the claimed, correct results for `qwen3:14b-q4_K_M`, `qwen3-vl:8b-thinking-q4_K_M`, `gemma4:e4b`, and `qwen3.8:27b-iq3-code144k`.
- The "explicit per-model capability clamp" block the design proposes to edit is real and matches the design's quoted line numbers and logic almost exactly (`reasoningEffort.ts:573-598`); nearest-tier semantics (`declaredRanked.find((x) => x.rank >= requestedRank) ?? declaredRanked[declaredRanked.length - 1]`) do produce `high → xhigh` for the proposed `["low","medium","xhigh"]` vocabulary, confirmed by hand-tracing `REASONING_EFFORT_ORDER`'s ranks.
- No existing registry model entry anywhere in the repository combines `aliases` with `supportedThinkingEfforts` on the same object (verified by a brace-matching scan across every `registry/**/*.ts` file) — so the family-prefix probe introduced in Step 2 cannot collide with or shadow the pre-existing `entry.aliases?.includes(...)` exact-match branch used elsewhere in the same function.
- `ollama-cloud` is confirmed to be the only existing provider with colon-containing ids that also declares `supportedThinkingEfforts`/`defaultSupportedThinkingEfforts`; its two models with declared vocabularies (`gpt-oss:20b`/`gpt-oss:120b`) exact-match before the new family-prefix branch would ever run, and its two without one (`gemma4:31b`/`qwen3.5:397b`) have no colliding bare-family entry in its `models` array — the Step 2b "no-op for ollama-cloud" claim holds. Every other colon-id provider found by grep (`routeway`, `cline`, `g4f-ollama`, `bedrock`, `synthetic`, `xkiro`, `kilo-gateway`, `bazaarlink`) declares no `defaultSupportedThinkingEfforts` at all, so `getRegistryEntry(provider)?.defaultSupportedThinkingEfforts` is `undefined` for all of them and the new clamp branch never activates (`declaredRanked.length > 0` gate).
- `DefaultExecutor.buildUrl()`'s `case "ollama-local":` branch (`default.ts`, confirmed by reading the switch) does read `LOCAL_PROVIDERS[this.provider]?.localDefault` / `credentials?.providerSpecificData?.baseUrl` and never reads `this.config.baseUrl` — so adding a registry entry with no `baseUrl` field leaves URL construction byte-for-byte unchanged, confirming that specific claim.
- `KNOWN_CATALOG_ONLY["ollama-local"]`'s removal is safe exactly as described: `findCatalogOnlyLlmProviders()` only flags providers absent from `REGISTRY`, and once `ollama-local` is registered the function excludes it before the allowlist is consulted — confirmed by reading `check-provider-consistency.ts` and its test file directly.
- `REASONING_EFFORT_ORDER` (`learnedReasoningEffortCaps.ts:30-38`) and the generic learned-cap clamp both match the design's description, and are correctly positioned (per the design's own file-level comment, confirmed by reading it) to run _before_ the new static per-model/provider-default clamp — so the ordering relationship between the learned-cap system and the new static declaration does not need to change.
- The dashboard's `getReasoningEffortsOverride()` function (`src/lib/db/modelCapabilityOverrides.ts:132-150`) does accept a `bulk` snapshot parameter and otherwise falls through to a synchronous `getDbInstance().prepare(...).get(...)` call, confirming the mechanism exists exactly as described — the Finding above is about where/how it's wired, not whether the function itself works as claimed.

## Unverified / Wrong Assumptions

- **Wrong (addressed in Finding 2):** "The two call sites ... pass `getReasoningEffortsOverride` bound with no bulk snapshot (on-demand DB read, same cost class as the existing `getModelCapabilityOverride` on-demand path already used in the hot request path ... so a `@/lib/db/modelCapabilityOverrides` import from the same executor layer is an established pattern, not a new architectural boundary)" — verified false. The cited `@/lib/db/paramFilters` import in `base.ts` reads from an in-memory cache (`loadParamFilterConfigs()`/`filterCache`), not a per-call SQLite query, and no current caller of `getModelCapabilityOverride`/`getReasoningEffortsOverride` outside catalog-build code omits the `bulk`/`snapshot` parameter in a per-request path. The "established pattern" claim is not supported by the code it cites.
- **Unverified by the design (addressed in Finding 1):** The design's non-regression analysis for the `authType: "optional"` side effect stops at `getCredentialRequirement()`/`listNoCredentialProviders()`. It does not walk `getProviderCategory()`'s consumers (`providerCooldownTracker.ts`, `rateLimitManager.ts`, `errorClassifier.ts`, `accountFallback.ts`, `quotaResetParsing.ts`), even though these are the resilience/breaker/cooldown subsystems most directly relevant to the bug being fixed (an unhealthy connection after a 500). This is a real behavior change the design did not verify, not merely an incomplete citation.
