# Design: Backend-aware `reasoning_effort` normalization for `ollama-local` (and future local-model templates)

## Summary of the bug

`gremlin-4070ti-ollama` (connection `b20e0770-3e14-40c1-87cd-85c34b34381a`, provider type `ollama-local`, base URL `http://10.1.1.12:2701/v1`) 500s whenever a forwarded chat-completion request carries `reasoning_effort: "high"`. The qwen3.5/qwen3.8-family models on that host embed a Jinja chat template that only accepts `xhigh` (default), `medium`, `low` — there is no `high` tier at all, and the unconditionally-highest cloud tier (`xhigh`) is spelled differently from OmniRoute's own internal top tier. OmniRoute currently forwards `reasoning_effort` to `ollama-local` verbatim; the GPU/backend themselves are healthy.

This document covers (1) the exact code path that builds the outbound reasoning fields for a chosen connection, (2) the capability/config metadata OmniRoute already tracks per connection/model and where a reasoning-effort vocabulary fits, and (3) the concrete design of the backend-aware normalization fix.

## 1. The exact outbound-request code path

OmniRoute's chat-completion forwarding pipeline for every provider (including `ollama-local`) is:

1. **`src/sse/handlers/chat.ts`** (`handleChatImplementation`) — client-facing entrypoint. Early on it calls `body = normalizeReasoningRequest(body)` (from `src/shared/reasoning/effortStandardization.ts`), which folds the _canonical_ `effort`/`thinking` fields (feature #6241, provider-agnostic `none|low|medium|high|xhigh|max`) onto `reasoning_effort` / `reasoning.effort` / `thinking` — but only when the client used the canonical fields; an explicit client `reasoning_effort` always wins and passes through untouched. This is NOT a backend-aware step; it's shape-normalization only, and it is where Zoo's `"high"` literal survives unchanged into the pipeline.
2. Model/connection resolution picks the destination provider connection (`ollama-local` / `gremlin-4070ti-ollama` in the bug) and routing continues into `open-sse/handlers/chatCore.ts` (`handleChatCore`).
3. **`open-sse/handlers/chatCore/upstreamBody.ts`** → `prepareUpstreamBody()` is the single place the final outbound JSON body is assembled before being handed to an executor. The relevant line:
    ```ts
    bodyToSend = sanitizeRequestForResolvedTarget(bodyToSend, { provider, model: payloadRuleModel, log })
    ```
4. **`open-sse/services/targetRequestSanitizer.ts`** → `sanitizeRequestForResolvedTarget()` calls `sanitizeReasoningEffortForProvider(next, provider, model, log)` — this is the **first** backend-aware reasoning-effort normalization pass, keyed by the concrete resolved `provider` (e.g. `"ollama-local"`) and `model` (e.g. `"qwen3.8:27b-iq3-code144k"`).
5. The resulting `bodyToSend` is handed to `executor.execute()` (resolved via `getExecutor(provider)` in `open-sse/executors/index.ts`; for `ollama-local` there is no specialized executor registered — `loadRegisteredExecutor("ollama-local")` misses and `getExecutor()` falls back to `getDefaultExecutor("ollama-local")`, i.e. the generic `DefaultExecutor` in `open-sse/executors/default.ts`, which does not override `execute()` except for a session-pool wrapper that is a no-op here).
6. **`open-sse/executors/base.ts`** → `BaseExecutor.execute()` builds the URL (`DefaultExecutor.buildUrl()`'s `case "ollama-local":` branch — resolves `providerSpecificData.baseUrl || LOCAL_PROVIDERS["ollama-local"].localDefault`, i.e. the connection's configured `http://10.1.1.12:2701/v1`, then appends `/chat/completions`), builds headers, and runs `transformRequest()` (generic cleanup only), then — **the second normalization pass, right before serializing and fetching**:
    ```ts
    const rawTransformedBody = await this.transformRequest(model, body, stream, requestCredentials)
    let transformedBody = sanitizeReasoningEffortForProvider(rawTransformedBody, this.provider, model, log)
    ```
    (`open-sse/executors/base.ts` ~line 894-901). This repeats the same function with the same `provider`/`model`, which is intentionally idempotent (routing/fallback may have swapped the model between step 4 and step 6, e.g. a combo retry — see `src/lib/combos/`).
7. The request is POSTed. **If the upstream still 400/422s** with a `reasoning_effort`-rejecting body, `BaseExecutor.execute()` runs a **reactive recovery** step (`open-sse/executors/base.ts` ~line 1566-1591) that calls `applyReasoningEffortRecovery()` (`open-sse/executors/base/reasoningEffortRecovery.ts`): it parses the upstream's error text for an advertised accepted-value enum (`parseReasoningEffortEnum()` in `open-sse/services/learnedReasoningEffortCaps.ts`), records it process-wide via `recordLearnedReasoningEffort(provider, model, acceptedValues)`, re-runs `sanitizeReasoningEffortForProvider()` (which now sees the freshly learned set via `getLearnedReasoningEffort()`), and retries the same URL once with the clamped body.

**The core function all of this converges on is `sanitizeReasoningEffortForProvider(body, provider, model, log)` in `open-sse/executors/base/reasoningEffort.ts`.** This is the single seam where a backend-aware reasoning-effort fix belongs — it is already called from every forwarding path (`targetRequestSanitizer.ts`, `BaseExecutor.execute()`, and the three executors that bypass `super.execute()` — `glm.ts`, `commandCode.ts`, `cliproxyapi.ts` — via `applyReasoningEffortRecovery`/direct calls).

### Why the live failure happens despite the reactive-recovery machinery

The reactive path (step 7) is a safety net, not the primary fix, and in this case it does not fire usefully because:

- `parseReasoningEffortEnum()`'s `LIST_INTRO` regex is `/(?:expected one of|supported (?:types|values) are|please use)[:\s]*([^.]+)/i`. The actual Jinja error — `"Unexpected reasoning effort high. Supported types are xhigh (default), medium, and low."` — **does** match this (there's even a dedicated test for exactly this string in `tests/unit/learned-reasoning-effort-caps.test.ts`), so `parseReasoningEffortEnum` correctly extracts `["xhigh", "medium", "low"]` and `recordLearnedReasoningEffort("ollama-local", "qwen3.8:27b-iq3-code144k", [...])` would learn the cap — but only **after the first live 500**, which is what the "unhealthy" / `errorCode: 500.0` connection row already reflects.
- The upstream returns **HTTP 500**, not 400/422. `applyReasoningEffortRecovery()` only triggers on `response.status === HTTP_STATUS.BAD_REQUEST || response.status === HTTP_STATUS.UNPROCESSABLE_ENTITY` (`open-sse/executors/base/reasoningEffortRecovery.ts` line 77-82). Ollama's OpenAI-compat shim wraps the backend's Jinja `TemplateError` as a generic upstream 500 (`"Model ... server_error"`, `errorCode: "500.0"` — matches the reported provider row exactly), so the entire learned-cap reactive-recovery mechanism **never engages** for this failure mode. This explains why the connection is marked unhealthy instead of self-healing after one request: the recovery code intentionally only recovers from 400/422, and a 500 is treated as a hard failure that trips the connection breaker (`shouldTripProviderBreakerForResult`, `src/sse/handlers/chatPredicates.ts`).

This confirms the mandate: a **proactive**, backend-aware mapping in `sanitizeReasoningEffortForProvider()` is required — the request must never reach the backend with `"high"` in the first place for this template family. The reactive 500 path cannot be extended to cover this (widening it to retry on every 500 would risk masking unrelated server errors as effort problems), so it stays as today's secondary safety net for 400/422-only responders, unrelated to this fix.

## 2. Existing per-connection/per-model capability metadata

OmniRoute already tracks model/connection capability metadata through three layers, and a reasoning-effort _vocabulary_ already has a parallel in each of them:

**a) Static registry declarations** (`open-sse/config/providers/shared.ts`, `RegistryEntry`/`RegistryModel`). Every built-in provider (`open-sse/config/providers/registry/<id>/index.ts`) can declare:

- `RegistryModel.supportedThinkingEfforts?: readonly string[]` — exact per-model vocabulary (e.g. `ollama-cloud`'s `gpt-oss:20b` declares `["low", "medium", "high"]`).
- `RegistryEntry.defaultSupportedThinkingEfforts?: readonly string[]` — provider-wide fallback vocabulary for passthrough models with no per-model entry. **`ollama-cloud`'s registry entry already does exactly this**: `defaultSupportedThinkingEfforts: ["none", "low", "medium", "high", "max"]` (`open-sse/config/providers/registry/ollama-cloud/index.ts` line 12), used by `getRegistryThinkingEfforts()` (`open-sse/config/providerRegistry.ts`) as a provider-level fallback when a passthrough-discovered model has no static entry.
- `RegistryModel.supportsXHighEffort?: boolean` — opt-out flag read by `supportsXHighEffort()` (`open-sse/config/providerModels.ts`).

Both are consumed inside `sanitizeReasoningEffortForProvider()` itself via `getProviderModels(provider).find(...).supportedThinkingEfforts` (the "explicit per-model capability clamp", `open-sse/executors/base/reasoningEffort.ts` line 573-598) and via `supportsXHighEffort()` / `supportsMaxEffortForProvider()`.

**Gap**: `ollama-local` has **no registry entry at all** in `open-sse/config/providers/index.ts` (`REGISTRY`). It is handled purely by `LOCAL_PROVIDERS["ollama-local"]` in `src/shared/constants/providers/local.ts` (connection metadata: `localDefault`, `authHint`, etc. — no capability fields) and by the `case "ollama-local":` branch inside `DefaultExecutor.buildUrl()`. So `getProviderModels("ollama-local")` and `getRegistryThinkingEfforts("ollama-local", ...)` both return nothing today, and none of the existing per-model/per-provider static-registry machinery currently reaches this connection.

**b) Operator-set per-model capability overrides** (DB-backed, `src/lib/db/modelCapabilityOverrides.ts`, table `model_capability_overrides`, key `reasoning_efforts`). This is the dashboard-editable "Model Capability Overrides" surface (`src/app/(dashboard)/dashboard/settings/components/ModelCapabilityOverridesTab.tsx`, `PATCH /api/model-capability-overrides`). `setModelCapabilityOverride(target, "reasoning_efforts", value)` stores an exact `ReasoningEffortOverrideValue[]` (vocabulary: `none|low|medium|high|xhigh|max|ultra`, parsed by `parseReasoningEffortsOverride()`), keyed by `provider/modelId` (e.g. `ollama-local/qwen3.8:27b-iq3-code144k`). It is read via `getReasoningEffortsOverride()` and surfaces through `getResolvedModelCapabilities()` → `ResolvedModelCapabilities.supportedThinkingEfforts` — this is purely **advertisement** (what the catalog/UI tells the client the model supports), consumed by `src/lib/vscode/reasoningMetadata.ts` (`getNativeReasoningEffortValues()`) to build the VS Code model-config `enum`. **It is read nowhere inside `sanitizeReasoningEffortForProvider()` or anywhere in the executor forwarding path** — it does not today remap an outbound request, only what's offered to the client up front.

**c) Reactive learned caps** (`open-sse/services/learnedReasoningEffortCaps.ts`, in-memory `Map<string, Set<string>>` keyed `"${provider}:${model}"`). Populated only after a live 4xx names its accepted enum (see §1's analysis of why this path misses the Ollama 500). Consulted inside `sanitizeReasoningEffortForProvider()` via `getLearnedReasoningEffort()`/`clampToLearned()`, ranked using the shared `REASONING_EFFORT_ORDER` ladder (`none < minimal < low < medium < high < xhigh < max < ultra`).

**Conclusion on existing shape**: the registry-level `supportedThinkingEfforts` / `defaultSupportedThinkingEfforts` pattern is the right fit — it is already (a) the thing `sanitizeReasoningEffortForProvider()` directly consults, (b) proven exactly for a local/passthrough-model provider (`ollama-cloud`), and (c) exactly the right shape to be "capability metadata, not a hardcoded single-model fix." The gap is only that `ollama-local` currently has no registry entry to carry it, and the vocabulary mapping is a plain accepted-set (clamp to nearest), not a `"high"→"xhigh"` _rename_, which the existing clamp logic does not yet produce in the exact form the Jinja template demands (confirmed below).

### Important nuance: this is a _rename_, not just a clamp

Every existing special-case in `sanitizeReasoningEffortForProvider()` (GLM-5.2/5.3, Muse Spark, DeepSeek, o1/o3, MiniMax, Grok, the generic "explicit per-model capability clamp") maps the client's requested tier to the **nearest value the backend accepts**, using `REASONING_EFFORT_ORDER` rank: e.g. GLM-5.2 maps `low`/`medium` UP to `high` because `high` IS a real tier it accepts, just not the one requested verbatim.

The Ollama qwen3.5/qwen3.8 Jinja template is different: it has no `"high"` tier at all. Cloud/Zoo's `"high"` is semantically "the top tier", and this template's top tier is spelled `"xhigh"`. If we just declare `supportedThinkingEfforts: ["low", "medium", "xhigh"]` and let the existing "explicit per-model capability clamp" run its nearest-tier logic (`open-sse/executors/base/reasoningEffort.ts` lines 573-598): for `effortStr === "high"`, `REASONING_EFFORT_ORDER` rank of `"high"` is 4; the declared ranked set is `[low=2, medium=3, xhigh=5]`; `nearest = declaredRanked.find(x => x.rank >= requestedRank)` → finds `xhigh` (rank 5 ≥ 4) — **this already produces the correct `high → xhigh` mapping for free**, with no new code. This is confirmed by walking the exact logic already in the file; no new clamp algorithm is needed. The only genuinely new piece of code is making `supportedThinkingEfforts`/`defaultSupportedThinkingEfforts` reachable for `ollama-local` models at all.

## 3. Design: backend-aware normalization for `ollama-local`

### Decision: static per-connection-type registry entry + explicit per-model declarations, mirroring `ollama-cloud`

Three shapes were viable:

1. **Model-family pattern-matching** inside `sanitizeReasoningEffortForProvider()` (like `GLM_52_FAMILY_PATTERN`/`MAX_TIER_REASONING_MODEL_PATTERN`) keyed off model-id substrings (`qwen3.5`, `qwen3.8`).
2. **A new `RegistryEntry` for `ollama-local`** in `open-sse/config/providers/index.ts`, declaring `defaultSupportedThinkingEfforts` + per-model `supportedThinkingEfforts`, exactly mirroring the existing `ollama-cloud` entry — letting the "explicit per-model capability clamp" logic that already exists do the rename.
3. **Per-connection operator config** (new `providerSpecificData` field on the connection, e.g. `reasoningEffortVocabulary`), read inside `sanitizeReasoningEffortForProvider()` by passing connection-level data through.

**Chosen: (2), with (3) layered on top for operator overrides where the static declaration is wrong for a given self-hosted deployment.**

Rationale:

- `ollama-local` is a **passthrough-models provider** (`passthroughModels: true` in `src/shared/constants/providers/local.ts`): the actual model catalog is whatever models the operator's Ollama server reports via `/api/tags`, not a fixed OmniRoute-curated list — this is structurally identical to `ollama-cloud`'s `passthroughModels: true` registry entry, which already solves this exact problem (provider-level `defaultSupportedThinkingEfforts` fallback + per-known-model overrides for models whose vocabulary differs from the fallback, e.g. GLM-5.1/5.2's `supportsXHighEffort: false`).
- Pattern-matching on `qwen3.5`/`qwen3.8` substrings (option 1) would scatter the mapping outside the capability-metadata system the mandate explicitly asks us to reuse, and — more importantly — would be wrong the moment the same `ollama-local` connection serves a model from a _different_ template family (the bug report itself flags `qwen3:14b-q4_K_M`, `qwen3-vl:8b-thinking-q4_K_M`, and `gemma4:e4b` as different families on the same host that must NOT get the `xhigh` rewrite). A per-model declaration is required regardless of where the pattern lives, so there is no complexity saved by matching on the model id inside the sanitizer instead of declaring it in the registry.
- A connection is not globally "qwen3.5/qwen3.8-template" — it is heterogeneous per model, exactly like `ollama-cloud`'s registry entry already assumes (mixed `supportedThinkingEfforts` entries per model, `defaultSupportedThinkingEfforts` as the fallback for the rest). This naturally generalizes to "any local Ollama server running a qwen3.5/qwen3.8-family model, from any connection", not "this one connection id" — satisfying "do not hardcode just this one model."
- Per-connection operator config (option 3 alone) was rejected as the _primary_ mechanism because the actual constraint ("this Jinja template rejects `high`") is a property of the **model's chat template**, not of the connection — the same fix must apply to a different OmniRoute operator's `ollama-local` connection serving the same qwen3.5/qwen3.8 model family, with zero per-operator configuration. Static registry declarations give every operator the fix for free, matching how `ollama-cloud` already ships it. Per-connection override remains valuable as an escape hatch (operator's locally-fine-tuned template genuinely differs) and is already available for free via the existing DB-backed `model_capability_overrides` `reasoning_efforts` key (§2b) — it just needs to be wired into the sanitizer (new, see step 3 below), which also benefits every other provider, not just `ollama-local`.

### Concrete changes

**Step 1 — give `ollama-local` a registry entry.**
Add a new file `open-sse/config/providers/registry/ollama-local/index.ts`:

```ts
import type { RegistryEntry } from "../../shared.ts"

export const ollama_localProvider: RegistryEntry = {
	id: "ollama-local",
	alias: "ollama",
	format: "openai",
	executor: "default",
	// authType: "apikey", NOT "optional" (review Finding 1, round 2). Ollama
	// genuinely needs no credential, same as g4f-ollama/ovhcloud/kilo-gateway's
	// "optional" entries — but getProviderCategory() (providerRegistry.ts:304-308)
	// treats anything other than literal "apikey" as "oauth", which would silently
	// move every ollama-local connection from the apikey resilience bucket
	// (15 failures/30min window, 10min cooldown, breaker threshold 12 — the bucket
	// this connection has always lived in, since `!entry` also returns "apikey")
	// to the oauth bucket (10 failures/15min window, 5min cooldown, breaker
	// threshold 8), consumed by providerCooldownTracker.ts's whole-provider
	// circuit breaker, rateLimitManager.ts's apikey-only auto-enable gate,
	// errorClassifier.ts's 403/429 handling, and accountFallback.ts's
	// getProviderProfile(). That is exactly the resilience subsystem the bug
	// report's own symptom (connection going unhealthy after a 500) touches, and
	// is not something this fix's mandate (normalize outbound reasoning_effort)
	// asked to change. "apikey" preserves today's resilience bucket exactly
	// (byte-for-byte: `!entry` already resolves to "apikey" today) while still
	// registering the entry this fix needs. The only cost: getCredentialRequirement
	// ("ollama-local") stays "required" (today's answer, via providerCredentialRequirement.ts's
	// `if (!entry) return "required"` fallback) instead of flipping to "optional" —
	// deliberately deferred as a separate, out-of-scope cleanup (see "Rejected side
	// effect" below), not bundled into a reasoning-effort fix.
	authType: "apikey",
	authHeader: "bearer",
	passthroughModels: true,
	// qwen3.5 / qwen3.8-family chat templates (observed: Jinja
	// `resolved_reasoning_effort = reasoning_effort|default('xhigh')`, raises on
	// anything outside xhigh/medium/low — no "high" tier exists). Declared at the
	// PROVIDER level because ollama-local is operator-hosted passthrough: the
	// concrete model id varies per deployment, but every qwen3.5/qwen3.8 model
	// sharing this template family rejects "high" the same way. Per-model entries
	// below override this default for models confirmed to use a different
	// template (qwen3, qwen3-vl, gemma4 — standard low/medium/high vocabulary).
	defaultSupportedThinkingEfforts: ["low", "medium", "xhigh"],
	models: [
		// Explicit opt-outs for model families on the SAME host confirmed NOT to
		// use the qwen3.5/qwen3.8 restricted template (#<ticket>). Any other
		// qwen3.5/qwen3.8-family model served by any ollama-local connection falls
		// through to defaultSupportedThinkingEfforts above with no further
		// per-model entries required.
		{ id: "qwen3", name: "Qwen3", supportedThinkingEfforts: ["none", "low", "medium", "high"] },
		{
			// Family-prefix id must match the Ollama tag's segment BEFORE the first
			// ":" verbatim (Step 2 splits on ":", it does not normalize hyphens) —
			// the ticket's observed tag is "qwen3-vl:8b-thinking-q4_K_M", so the id
			// here is "qwen3-vl", not "qwen3vl".
			id: "qwen3-vl",
			name: "Qwen3-VL",
			supportedThinkingEfforts: ["none", "low", "medium", "high"],
		},
		{ id: "gemma4", name: "Gemma 4", supportedThinkingEfforts: ["none", "low", "medium", "high"] },
	],
}
```

Register it in `open-sse/config/providers/index.ts` (import + add to the `REGISTRY` object literal), following the exact pattern already used for `ollama_cloudProvider`.

**Confirmed non-regression of URL/header building**: today, with no registry entry, `DefaultExecutor`'s constructor (`super(provider, PROVIDERS[provider] || PROVIDERS.openai)`, `open-sse/executors/default.ts` line 222) falls back to `PROVIDERS.openai`'s legacy config (`format: "openai"`, OpenAI's `baseUrl`) for `this.config`, but `buildUrl()`'s explicit `case "ollama-local":` branch (`open-sse/executors/default.ts` ~line 383) never reads `this.config.baseUrl` — it always computes the URL from `LOCAL_PROVIDERS["ollama-local"].localDefault` or the connection's `providerSpecificData.baseUrl`. Adding the registry entry above with no `baseUrl` field leaves `PROVIDERS["ollama-local"].baseUrl` unset (`generateLegacyProviders()` only sets `p.baseUrl` `if (entry.baseUrl)`), so `buildUrl()`'s behavior is byte-for-byte unchanged. `format: "openai"` in the new entry matches the `format` already inherited today via the `PROVIDERS.openai` fallback, so the default-branch bearer-auth logic (`DefaultExecutor`'s header builder, `open-sse/executors/default.ts` ~line 653-666, reading `entry?.authHeader`) is also unchanged. The only observable effects of registering the entry are: (a) making `getRegistryEntry("ollama-local")` / `getProviderModels("ollama-local")` / `getRegistryThinkingEfforts("ollama-local", ...)` resolve to real data instead of `null`/`[]`/`undefined`, and (b) `getProviderCategory("ollama-local")` resolving through the real entry's `authType` instead of the `!entry` fallback — both now land on `"apikey"` (verified: `getProviderCategory()`, `providerRegistry.ts:304-308`, returns `"apikey"` exactly when `entry.authType === "apikey"` and `"apikey"` for every unrecognized provider via its own `if (!entry) return "apikey"` branch), so this is a no-op, not a side effect requiring sign-off.

**Rejected side effect (review Finding 1, round 2) — `authType: "optional"` was dropped specifically because it would have flipped `getProviderCategory("ollama-local")` from `"apikey"` to `"oauth"`.** The first draft chose `"optional"` to also fix `getCredentialRequirement("ollama-local")` (`src/shared/utils/providerCredentialRequirement.ts`), which today returns `"required"` only because `!entry` short-circuits before `authType` is ever consulted — an artifact of having no registry entry at all, not a deliberate credential policy. That correction is still true and still desirable, but verified unsafe to bundle with `authType: "optional"`: `getProviderCategory()` has no independent carve-out for "optional meaning no-credential-but-still-apikey-shaped" — it is a strict `authType === "apikey" ? "apikey" : "oauth"`, so `"optional"` and `"oauth"` are indistinguishable to every one of `getProviderCategory()`'s consumers (`providerCooldownTracker.ts`'s whole-provider circuit breaker, `rateLimitManager.ts`'s auto-enable gate, `errorClassifier.ts`'s 403/429 handling, `accountFallback.ts`'s `getProviderProfile`/`getRuntimeProviderProfile`, `quotaResetParsing.ts`). Sibling local-shaped providers already registered with `authType: "optional"` (`g4f-ollama`, `ovhcloud`, `kilo-gateway`, `naga-ac`) accept the same oauth-bucket reclassification today, but none of their registrations document that this was a reviewed tradeoff rather than an overlooked one — repeating that pattern here, for the exact connection the bug report is about, would be carrying the same unreviewed risk into the one case this investigation is explicitly scrutinizing. Fixing `getCredentialRequirement("ollama-local")` is left out of scope for this fix (see "Out of scope" below) so it can be reviewed on its own, independent of the resilience-bucket question. No other `REGISTRY`-iterating call site changes behavior for `ollama-local` under `authType: "apikey"`: `generateModels()`/`generateAliasMap()`/`ensurePassthroughProviderIds()` only add data keyed on an id that previously had none, and `getUnsupportedParams()`/`requiresPlainStringContent()` return their existing no-entry defaults for a `RegistryEntry` that sets neither field; `registryUtils.ts`'s `buildAuthHeaders()` and `providerPluginManifest.ts`'s `sidecarEligibility()`/`capabilitiesFor()` both treat `"apikey"` the same as `"optional"` for every branch that matters to `ollama-local` (bearer-header emission, sidecar eligibility, the `apikey` plugin capability tag) — verified by reading both files directly, so there is no silent capability-manifest regression from choosing `"apikey"` over `"optional"` either.

**Cleanup for consistency (not required by any test, but corrects a now-inaccurate comment) — `scripts/check/check-provider-consistency.ts`.** `KNOWN_CATALOG_ONLY["ollama-local"]` currently reads `"Local provider (Ollama) roteado via baseUrl de conexão; sem registry."` ("...without registry"). Once this fix lands, that clause is factually wrong — `ollama-local` _will_ have a registry entry. Verified this does not break any gate either way: `findCatalogOnlyLlmProviders()` only flags a canonical llm provider that is **absent from `REGISTRY`**; once `ollama-local` is registered, `registry.has("ollama-local")` is `true` and the function excludes it before the allowlist is even consulted, so leaving the stale allowlist entry does not fail `tests/unit/check-provider-consistency.test.ts`'s "`KNOWN_CATALOG_ONLY` covers every live llm provider without REGISTRY entry" assertion — but the entry becomes dead/misleading documentation. Remove the `"ollama-local"` line from `KNOWN_CATALOG_ONLY` in the same PR (routing still goes through `providerSpecificData.baseUrl`, so the _routing_ half of the sentence stays true; only "sem registry" becomes false). This is the one other file this fix touches beyond the `reasoningEffort.ts` capability path, included here because the mandate scopes the fix to "the request-forwarding/proxy path" and this allowlist comment directly describes that path's registry state.

**Why `defaultSupportedThinkingEfforts` at the provider level, not per-model:** `ollama-local` is `passthroughModels: true` — the live-discovered model catalog (`qwen3.8:27b-iq3-code144k`, `qwen3.5:...`, etc., reported by the operator's `/api/tags`) will never exactly match a small static `models: []` list. Declaring the restricted vocabulary as the _provider default_ means every qwen3.5/qwen3.8-tagged model this or any other operator's Ollama host serves gets the correct mapping with zero per-model entries, while the three explicitly-different families reported in the ticket (`qwen3`, `qwen3-vl`, `gemma4`) get narrow, named opt-outs. New models the operator pulls that happen to be qwen3.5/qwen3.8 family inherit the restricted vocabulary automatically and correctly; new models from an unlisted _different_ family inherit it too and would need their own opt-out entry added — this is the same tradeoff `ollama-cloud`'s registry entry already accepts, and is strictly safer than the status quo (today 100% of `ollama-local` models get zero reasoning-effort protection).

Note: `id` matching in `getProviderModels(provider).find(entry => entry.id === providerModelIdForClamp || entry.aliases?.includes(...))` (`open-sse/executors/base/reasoningEffort.ts` line 581-584) does an **exact** match against the full model id string (e.g. `"qwen3.8:27b-iq3-code144k"`), not a prefix/family match. The three opt-out entries above (`"qwen3"`, `"qwen3-vl"`, `"gemma4"`) as written will only exact-match a bare `qwen3`/`qwen3-vl`/`gemma4` id, which is unlikely to be the literal Ollama tag (`qwen3:14b-q4_K_M`, `qwen3-vl:8b-thinking-q4_K_M`, `gemma4:e4b` per the ticket). **This requires either**: (a) listing every exact observed tag as its own model entry (brittle — breaks on tag/quant changes), or (b) extending `sanitizeReasoningEffortForProvider()`'s existing-model lookup for passthrough providers to match by model-family prefix (split on `:`) in addition to exact id — this is a small, generalizable addition described in Step 2, and is the better fix since `ollama`/`ollama-local`/`ollama-cloud`'s model ids are ALWAYS `family:tag` shaped (Ollama's own naming convention), unlike most other providers' flat ids. The registry id above is `"qwen3-vl"` (hyphenated) specifically so it matches the family segment the Step 2 split produces verbatim — Step 2 splits on `:` only, it does not strip or normalize hyphens.

**Step 2 — add family-prefix matching for Ollama-shaped model ids, probed BEFORE the provider-default fallback.**

Review finding (HIGH, resolved): the first design draft called `getRegistryThinkingEfforts(provider, providerModelIdForClamp)` first and only tried the family-prefix id as a `??` fallback. Because `getRegistryThinkingEfforts()` (`open-sse/config/providerRegistry.ts`, verified by reading it directly) already bakes in `entry.defaultSupportedThinkingEfforts` as its own internal fallback —

```ts
export function getRegistryThinkingEfforts(provider: string, modelId: string): readonly string[] | undefined {
	const entry = getRegistryEntry(provider)
	if (!entry) return undefined
	const modelEfforts = getRegistryModelThinkingEfforts(provider, modelId) // exact id only
	if (modelEfforts !== undefined) return modelEfforts
	return entry.defaultSupportedThinkingEfforts
}
```

— the first call _never_ returns `undefined` once `ollama-local` declares a `defaultSupportedThinkingEfforts`, so the `??` short-circuits and the family-prefix retry is dead code. Replaying the exact combined lookup against the exact Step 1 registry data confirms the regression: `qwen3:14b-q4_K_M`, `qwen3-vl:8b-thinking-q4_K_M`, and `gemma4:e4b` all resolve to `["low","medium","xhigh"]` (the restricted default) instead of their intended opt-out `["none","low","medium","high"]` — reintroducing, on a _different_, previously-working model family on the same connection, the exact failure mode this fix exists to eliminate.

The corrected rule: resolve the model-level vocabulary first — exact id, then family-prefix id, both via `getRegistryModelThinkingEfforts()` (which does **not** fall back to the provider default; verified above) — and only fall back to `entry.defaultSupportedThinkingEfforts` once neither model-level lookup matched. In `open-sse/executors/base/reasoningEffort.ts`, replace the inline `getProviderModels(provider).find(...).supportedThinkingEfforts` lookup (line 581-584) with:

```ts
import { getRegistryEntry, getRegistryModelThinkingEfforts } from "../../config/providerRegistry.ts";
...
// Ollama-shaped ids are always "family:tag" (Ollama's own naming convention,
// e.g. "qwen3:14b-q4_K_M"); detected generically by the presence of ":",
// not a provider allowlist, so this also covers any future self-hosted
// provider (vllm, lm-studio, ...) that adopts the same convention. Verified
// against every CURRENT colon-id registry entry (see Step 2b below) that this
// is additive-only for providers that already have colon-tagged models.
const ollamaFamilyId = providerModelIdForClamp.includes(":")
  ? providerModelIdForClamp.slice(0, providerModelIdForClamp.indexOf(":"))
  : null;
const modelEfforts =
  getRegistryModelThinkingEfforts(provider, providerModelIdForClamp) ??
  (ollamaFamilyId ? getRegistryModelThinkingEfforts(provider, ollamaFamilyId) : undefined);
const declaredEfforts = modelEfforts ?? getRegistryEntry(provider)?.defaultSupportedThinkingEfforts;
```

Replaying this corrected algorithm against the Step 1 registry data: `qwen3:14b-q4_K_M` → `getRegistryModelThinkingEfforts("ollama-local", "qwen3:14b-q4_K_M")` has no exact match (`undefined`) → `ollamaFamilyId = "qwen3"` → `getRegistryModelThinkingEfforts("ollama-local", "qwen3")` exact-matches the `{id: "qwen3", supportedThinkingEfforts: [...]}` opt-out entry → **`["none","low","medium","high"]`**, correct. Same for `qwen3-vl:8b-thinking-q4_K_M` → family id `"qwen3-vl"` → correct opt-out. `qwen3.8:27b-iq3-code144k` → no exact match, family id `"qwen3.8"` has no entry either (`models: []` only lists `qwen3`/`qwen3-vl`/`gemma4`) → `modelEfforts` is `undefined` → falls through to `getRegistryEntry("ollama-local")?.defaultSupportedThinkingEfforts` → **`["low","medium","xhigh"]`**, correct.

**Step 2b — verify the family-prefix fallback does not change behavior for `ollama-cloud`, the one other provider with colon-tagged ids today.** Grepped every `registry/*/index.ts` for colon-containing model ids (verified live): `ollama-cloud` (`gpt-oss:20b`, `gpt-oss:120b`, `gemma4:31b`, `qwen3.5:397b`) is the only existing provider sharing this lookup path that has them — `bedrock`, `cline`, `kilo-gateway`, `routeway`, `synthetic`, `xkiro` also have colon ids but are not passthrough/local providers relevant to this clamp's family-prefix use case and, more importantly, have no _bare_-family entry that a prefix split could collide with (checked: `bedrock`'s `openai.gpt-oss-120b-1:0` splits to family `"openai.gpt-oss-120b-1"`, no such id exists in `bedrock`'s registry; same pattern for the others). For `ollama-cloud` specifically: `gpt-oss:20b` and `gpt-oss:120b` both exact-match first (`modelEfforts` resolves on the first `getRegistryModelThinkingEfforts` call), so the family-prefix branch is never reached for them. `gemma4:31b` and `qwen3.5:397b` have no `supportedThinkingEfforts` field at all (plain `{id, name}` entries) — exact match returns `undefined` (not a vocabulary, truly absent), family id `"gemma4"`/`"qwen3.5"` has no entry in `ollama-cloud`'s registry either, so both fall through to `ollama-cloud`'s `defaultSupportedThinkingEfforts: ["none","low","medium","high","max"]` — identical to what Step 3 below already makes happen for them without the family-prefix branch being invoked at all. **Conclusion: the family-prefix fallback is a no-op for every existing colon-id model in the repository today**; it only activates for the newly-declared `ollama-local` opt-out entries. This closes the review's Finding 4.

**Step 3 — this is now the SAME change as Step 2, not a separate second pass.** The first design draft proposed Step 2 (family-prefix matching) and Step 3 (threading `defaultSupportedThinkingEfforts` in via `getRegistryThinkingEfforts()`) as two sequential edits to the same lookup — which is exactly how the double-defaulting bug in Finding 1 was introduced: each step was individually correct in isolation, but composing them by calling the defaulting function twice broke the ordering. The corrected design folds both into the single lookup shown in Step 2 (`getRegistryModelThinkingEfforts` for model-level, `getRegistryEntry(provider)?.defaultSupportedThinkingEfforts` as the explicit last resort), so there is only one piece of new logic, not two. This still fixes the latent `ollama-cloud` bug the original Step 3 identified — `ollama-cloud`'s own `defaultSupportedThinkingEfforts` was previously dead code (only read by `src/app/api/v1/models/catalog.ts`/`syncedCapabilities.ts` for advertisement, never by the clamp; confirmed by grepping every call site) and is now live, with the value unchanged (`["none","low","medium","high","max"]`), confirmed safe by Step 2b. `getRegistryEntry` and `getRegistryModelThinkingEfforts` are both already exported from `open-sse/config/providerRegistry.ts` — no new exports needed, only new call sites inside `reasoningEffort.ts`. This keeps `supportsXHighEffort`/`supportsMaxEffortForProvider` (the generic xhigh/max fallback logic further down the same function) completely untouched for every provider that has no declared vocabulary at all — this clamp branch only activates when `declaredRanked.length > 0`, i.e. only for providers/models that now have an explicit `supportedThinkingEfforts` or `defaultSupportedThinkingEfforts` entry, so no existing provider without one is affected.

**Step 4 (operator escape hatch, generalizes beyond `ollama-local`) — wire the DB `reasoning_efforts` override into the same clamp.**
As identified in §2b, `getReasoningEffortsOverride()` already exists (`src/lib/db/modelCapabilityOverrides.ts`, verified by reading it directly — signature `(provider, modelId, bulk?) => readonly ReasoningEffortOverrideValue[] | null`), is already dashboard-editable, and already keys by `provider/modelId` — but nothing in the forwarding path reads it. Extend `sanitizeReasoningEffortForProvider()`'s signature with an optional override lookup (consistent with how `getResolvedModelCapabilities()` is already called elsewhere with an optional snapshot), so an operator whose self-hosted deployment's template differs from the shipped `ollama-local` default (e.g. a custom-patched template, or a template update that changes the accepted set before OmniRoute's static registry catches up) can override per-model without a code change.

Review finding (MEDIUM, round 1, resolved): the first design draft inserted `overrideLookup?.(provider, providerModelIdForClamp)` as the first term of the same `??` chain that had Finding 1's double-defaulting bug, and never tried the family-prefix id against the override at all — so an operator override keyed on the bare family (`ollama-local/qwen3`, matching how the static registry already keys its opt-outs) could never be found; only an override keyed on the exact literal tag (`ollama-local/qwen3:14b-q4_K_M`) would work, undocumented and inconsistent with Step 2's family-aware static path. **Decision: operators key DB overrides the same way the static registry does — exact tag OR bare family id, operator's choice, both resolve.** This is documented in the dashboard's `ModelCapabilityOverridesTab.tsx` helper text (new copy, see Files touched) and enforced by probing both forms in the same order as the static path.

Review finding (MEDIUM, round 2, resolved): the round-1 fix still called `getReasoningEffortsOverride(provider, modelId)` directly from both forwarding-path call sites with no `bulk` argument — an uncached, synchronous `getDbInstance().prepare(...).get(...)` SQLite read on every chat-completion request through either call site, for every provider, not just `ollama-local`. Verified against the actual precedent the first draft cited: `getParamFilterConfig()` (`src/lib/db/paramFilters.ts`) reads from `loadParamFilterConfigs()`'s in-memory `filterCache`, populated once and invalidated only on write via `bumpCacheGeneration()` — it is not a per-call SQLite query, so "same cost class" was incorrect. Every other current caller of `getReasoningEffortsOverride`/`getModelCapabilityOverride` outside catalog-build code (`src/lib/modelCapabilities.ts`'s `getReasoningEffortsCapabilityOverride`/`getCapabilityOverride`, `src/lib/modelMetadataRegistry.ts`) passes a pre-built `bulk`/`snapshot` map, never an on-demand call in a per-request path. **Fix: add a cached wrapper, `getCachedReasoningEffortsOverride()`, to `src/lib/db/modelCapabilityOverrides.ts`, built the same way `loadParamFilterConfigs()` is — one full-table load (reusing the already-exported `listModelCapabilityOverrides()`, filtered to `key === "reasoning_efforts"` and grouped into the same nested `provider → modelId → value` map shape the `bulk` parameter already accepts), cached until invalidated.** Rather than inventing a new invalidation signal, this reuses the one that already exists and already fires on every write: `setModelCapabilityOverride()`/`removeModelCapabilityOverride()` already call `invalidateDbCache("model-capabilities")` (verified by reading both functions), and `invalidateDbCache()`'s own body (`src/lib/db/readCache.ts`) unconditionally runs `invalidateModelCatalogCache()` (bumping `modelCatalogCacheVersion`) for any scope that falls through its `settings`/`pricing`/`connections`/`nodes`/`combos` checks — `"model-capabilities"` matches none of them, so today it is already a de facto "bump the catalog version" signal with no other effect. The new cache compares its own last-seen version against `getModelCatalogCacheVersion()` on every call and rebuilds only when they differ (i.e. at most once per write, not once per request):

```ts
// src/lib/db/modelCapabilityOverrides.ts — new, appended after getReasoningEffortsOverride()
import { getModelCatalogCacheVersion } from "./readCache"

type ReasoningEffortsOverrideBulkMap = ReadonlyMap<string, ReadonlyMap<string, readonly ReasoningEffortOverrideValue[]>>

let reasoningEffortsOverrideCache: ReasoningEffortsOverrideBulkMap | null = null
let reasoningEffortsOverrideCacheVersion = -1

function loadReasoningEffortsOverrideMap(): ReasoningEffortsOverrideBulkMap {
	const map = new Map<string, Map<string, readonly ReasoningEffortOverrideValue[]>>()
	for (const override of listModelCapabilityOverrides()) {
		if (override.key !== "reasoning_efforts") continue
		const providerMap = map.get(override.provider) ?? new Map()
		providerMap.set(override.modelId, override.value)
		map.set(override.provider, providerMap)
	}
	return map
}

/**
 * Cached wrapper for getReasoningEffortsOverride(), safe to call on every
 * forwarding-path request (#<ticket>). Mirrors loadParamFilterConfigs()'s
 * cache-until-invalidated pattern: rebuilds the full reasoning_efforts
 * override table at most once per modelCatalogCacheVersion bump (i.e. once
 * per write via setModelCapabilityOverride/removeModelCapabilityOverride),
 * never once per request.
 */
export function getCachedReasoningEffortsOverride(
	provider: string | null | undefined,
	modelId: string | null | undefined,
): readonly ReasoningEffortOverrideValue[] | null {
	const currentVersion = getModelCatalogCacheVersion()
	if (reasoningEffortsOverrideCache === null || reasoningEffortsOverrideCacheVersion !== currentVersion) {
		reasoningEffortsOverrideCache = loadReasoningEffortsOverrideMap()
		reasoningEffortsOverrideCacheVersion = currentVersion
	}
	return getReasoningEffortsOverride(provider, modelId, reasoningEffortsOverrideCache)
}
```

The only new runtime dependency is `getModelCatalogCacheVersion`; `modelCapabilityOverrides.ts` already imports from `./readCache` today (`invalidateDbCache`), so this is not a new module edge. With the cache in place, `sanitizeReasoningEffortForProvider()`'s signature and composed lookup are otherwise exactly as the round-1 fix described:

```ts
export function sanitizeReasoningEffortForProvider(
  body: unknown,
  provider: string,
  model: string | undefined,
  log?: ReasoningSanitizeLog | null,
  overrideLookup?: (provider: string, modelId: string) => readonly string[] | null
): unknown {
  ...
  const overrideEfforts =
    overrideLookup?.(provider, providerModelIdForClamp) ??
    (ollamaFamilyId ? overrideLookup?.(provider, ollamaFamilyId) : undefined);
  const modelEfforts =
    overrideEfforts ??
    getRegistryModelThinkingEfforts(provider, providerModelIdForClamp) ??
    (ollamaFamilyId ? getRegistryModelThinkingEfforts(provider, ollamaFamilyId) : undefined);
  const declaredEfforts = modelEfforts ?? getRegistryEntry(provider)?.defaultSupportedThinkingEfforts;
```

An operator override — exact-tag or family-keyed — always wins over both the static per-model entry and the provider default, matching the precedence the dashboard UI already implies ("Model Capability Overrides" is presented as the operator's final word, not a secondary hint). The two call sites in the forwarding path (`open-sse/services/targetRequestSanitizer.ts` and `open-sse/executors/base.ts`) pass `getCachedReasoningEffortsOverride` — not the raw `getReasoningEffortsOverride` — as `overrideLookup`, so every request through either call site reads an in-memory map, never SQLite directly; `applyReasoningEffortRecovery`'s internal re-invocation (`open-sse/executors/base/reasoningEffortRecovery.ts`) omits the argument entirely (the override, if present, was already applied on the first pass; re-checking on the retry would be a redundant lookup with no behavior difference, since the override cannot change between the first attempt and its immediate retry). This is additive and optional — omitting the argument (as `commandCode.ts`'s direct call and the recovery re-invocation both do) preserves exactly today's behavior, so it carries zero regression risk for every call site that does not pass it, and the cache read itself (a `Map.get()` after an `===` version check) is now the same cost class as every other in-memory lookup already on this path (`getLearnedReasoningEffort()`, `getProviderModels()`), not a new one. This step is not required to fix the reported bug (Steps 1-3 fix it standalone) but directly answers the mandate's request to reuse "capability metadata already available in OmniRoute's provider/connection model" rather than only adding new static data.

### Why this does not regress providers/connections that already send `"high"` correctly

- `getRegistryModelThinkingEfforts(provider, model)` and `getRegistryEntry(provider)?.defaultSupportedThinkingEfforts` both resolve to `undefined` for every provider/model that has no `supportedThinkingEfforts` and no `defaultSupportedThinkingEfforts` declared — which is every existing registry entry except `ollama-cloud` (whose default was previously dead code, now live but unchanged in value, confirmed safe in Step 2b) and the new `ollama-local` entry. `declaredRanked.length > 0` gates the entire clamp branch, so real cloud OpenAI-compatible endpoints (`openai`, `azure-ai`, custom `openai-compatible-*` nodes, etc.) are completely unaffected — they fall through to the pre-existing `supportsXHighEffort`/`supportsMaxEffortForProvider` logic exactly as today, which already explicitly special-cases `"high"` as always safe to pass through (it is only `xhigh`/`max` that get special-cased).
- `"high"` was never rejected by the pre-existing clamp logic for any provider that had no declared vocabulary (the clamp only fires when `!declaredEfforts!.includes(effortStr)`), so introducing a declared vocabulary for `ollama-local`/`ollama-cloud` only narrows behavior for THOSE two providers' listed/defaulted models — it cannot change behavior for any other provider id.
- The hybrid/tiered combo scenario the mandate calls out (`hybrid/planner` routing the same client request to `gremlin-4070ti-ollama` on one call and a cloud tier on another) is handled correctly because the clamp is keyed on the **resolved** `provider`/`model` at the point of the outbound call (step 4 and step 6 in §1 both run after routing has picked the concrete destination) — a cloud-tier call in the same combo resolves to a different `provider` string (e.g. `"openai"`), which has no declared vocabulary and is untouched; only the leg that actually resolves to `ollama-local` gets remapped.
- `qwen3`, `qwen3-vl`, `gemma4` on the same `gremlin-4070ti-ollama` connection keep passing `"high"` through unchanged under the **corrected** lookup (Step 2): their declared `supportedThinkingEfforts` includes `"high"` natively and is found via the exact-id-then-family-prefix probe _before_ the provider default is ever consulted — this is the exact claim the review's Finding 1 showed was false under the original (double-defaulting) lookup order, now verified true by replaying the corrected algorithm. This confirms the model-family declaration — not a per-connection or per-provider-wide switch — is the correct granularity, exactly as the mandate requires ("check each if relevant").
- `getCredentialRequirement("ollama-local")` flipping from `"required"` to `"optional"` (documented above as an accepted side effect, not a regression) is the only other observable behavior change from registering the entry; no other `REGISTRY`-keyed call site changes its answer for `ollama-local`, since the new entry sets no field any of them reads besides `authType`, `format`, `defaultSupportedThinkingEfforts`, and `models`.

- Auto-discovering a connection's Jinja template vocabulary live from `/api/show` (the codebase already has `src/lib/providerModels/ollamaCapabilities.ts`'s `applyOllamaShowCapabilities()` for vision/tools/thinking BOOLEAN capability discovery via `/api/show`'s `capabilities[]` array — Ollama's `/api/show` response does not expose the chat template's accepted reasoning-effort _enum_ today, only a boolean `"thinking"` capability flag, so there is no live-discovery signal to extend; the static registry declaration is the only available mechanism until/unless Ollama's own API starts reporting this).
- Fixing `getCredentialRequirement("ollama-local")`'s inaccurate `"required"` answer (correct behavior would be `"optional"` or `"none"`, matching `ollama-local`'s own `authHint` and `LOCAL_PROVIDERS` entry) — deliberately deferred (round-2 Finding 1) because the only registry field that currently drives both the credential-requirement answer and the resilience-bucket category is the same `authType` field, and this fix's mandate is reasoning-effort normalization on the forwarding path, not a resilience-profile change. A follow-up could either add a credential-requirement-only signal independent of `getProviderCategory()` (e.g. a new `RegistryEntry` field read only by `providerCredentialRequirement.ts`), or make the explicit case for moving `ollama-local` into the oauth resilience bucket on its own merits — either needs its own review, separate from this one.

## Responses to design review findings

All findings were verified against the actual OmniRoute source (`providerRegistry.ts`, `providerCredentialRequirement.ts`, `reasoningEffort.ts`, `check-provider-consistency.ts`, `constants.ts`'s `PROVIDER_PROFILES`, `providerCooldownTracker.ts`, `rateLimitManager.ts`, `errorClassifier.ts`, `accountFallback.ts`, `paramFilters.ts`, `modelCapabilityOverrides.ts`, `readCache.ts`, `modelCapabilities.ts`, every `registry/*/index.ts` with colon-containing model ids) before being addressed — none were taken on the review's word alone. This is the second review pass; the four findings from the first pass are re-verified below alongside the two new findings from the second pass.

**Round 1:**

- **Finding 1 (HIGH, addressed).** Confirmed by reading `getRegistryThinkingEfforts()` directly: it bakes `defaultSupportedThinkingEfforts` into its own return value, so calling it twice with different ids (exact, then family) can never reach the second call once a provider default exists. Fixed by switching the composed lookup to `getRegistryModelThinkingEfforts()` (exact-only, no provider-default folding) for both the exact and family-prefix probes, and only consulting `getRegistryEntry(provider)?.defaultSupportedThinkingEfforts` once neither model-level probe matched. Replayed the corrected algorithm by hand against all four ticket model ids (Step 2) and got the intended result for each. Added explicit test cases requiring the opt-out families to resolve correctly under the real composed function, not a manual trace (Testability section).
- **Finding 2 (MEDIUM, addressed).** The `overrideLookup` parameter now receives the same exact-then-family-prefix probing as the static path, and is checked before the static per-model/provider-default resolution (operator overrides win). Documented explicitly (Step 4) that operators may key a `reasoning_efforts` override on either the exact tag or the bare family id, with a corresponding dashboard helper-text update added to the Files Touched table.
- **Finding 3 (MEDIUM, addressed then revised).** The round-1 fix accepted `authType: "optional"` and the resulting `getCredentialRequirement()` flip as an intended side effect. Round 2's Finding 1 showed this analysis stopped one call-chain short — `authType` also drives `getProviderCategory()`, with real resilience-bucket consequences. The registry entry now uses `authType: "apikey"` instead (see round 2 below), which keeps `getCredentialRequirement("ollama-local")` at today's `"required"` answer — still inaccurate, but no longer something this fix changes silently. The `scripts/check/check-provider-consistency.ts` `KNOWN_CATALOG_ONLY` cleanup from round 1 is unaffected by this change (it depends only on the entry existing in `REGISTRY`, not on its `authType` value) and is kept as-is.
- **Finding 4 (MEDIUM, addressed).** Grepped every `registry/*/index.ts` for colon-containing model ids and checked each against the new family-prefix fallback by hand (Step 2b): `ollama-cloud` is the only passthrough/local-shaped provider affected, and its two models with declared vocabularies (`gpt-oss:20b`/`gpt-oss:120b`) exact-match before the family-prefix branch is ever reached, while its two models without one (`gemma4:31b`/`qwen3.5:397b`) have no colliding bare-family entry and fall through to the provider default exactly as Step 3 already causes without the family-prefix branch's involvement — confirmed a no-op for every existing colon-id model in the repository today. Added this as an explicit regression-guard test case.

**Round 2:**

- **Finding 1 (MEDIUM, addressed).** Verified by reading `getProviderCategory()` (`providerRegistry.ts:304-308`) directly: it is a strict `entry.authType === "apikey" ?
