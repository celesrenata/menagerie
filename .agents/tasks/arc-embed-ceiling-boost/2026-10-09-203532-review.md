# arc-embed embedding outage fix, ceiling reconcile, and +50% memory bump

This change diagnoses and remediates the `arc-embed/qwen3-embedded` "so many problems" report. Live diagnosis found the real cause was not a context-window problem but an Intel Meteor Lake Arc GPU compute-engine (`ccs0`) hang on the in-cluster SR-IOV-VF OVMS embedding path: wedged replicas sat `0/1`, OmniRoute load-balanced onto dead backends, and clients saw `fetch failed`. The fix abandons the in-cluster StatefulSet (scaled to 0), moves embedding serving host-native onto each gremlin's physical-function Arc device, fronts the four PF backends with an in-cluster `ovms-embeddings-proxy` (nginx, hostNetwork, least_conn + failover), corrects the model id story, reconciles the per-item ceiling to 4096 at both layers (8192 failed a measured gate and was escalated), and raises memory +50% (12Gi on both OVMS containers, `OMNIROUTE_MEMORY_MB=12288`).

Watch for: the reranker is `0/1` live, so AC6's literal "reranker stayed 1/1 throughout" is not satisfied (confirmed — pre-existing, out-of-scope `/v3/rerank` graph-load hang, restarts=0, probe unchanged); and the `ovms-embeddings-proxy.yaml` that is now the keystone of the live routing path is untracked on the branch, so the committed config does not reproduce the live serving topology (confirmed via `git status`).

**Verdict**: CHANGES_REQUESTED

## High-level view

The outage is genuinely fixed and I verified it live: 12/12 paced public `POST /v1/embeddings` calls returned HTTP 200 with 1024-dim vectors and zero `fetch failed`, model `AVAILABLE` on the healthy PF backends, and the proxy pods 4/4 Running with restarts=0. The design's StatefulSet-rolling model was superseded by a host-native PF pivot, which the user explicitly directed ("get off kube") and which addresses the root cause the design itself named.

The ceiling landed at 4096 on both layers, which the design and this task's acceptance both permit as "an escalated proven fallback." I confirmed the two layers agree live (OmniRoute guard `OMNIROUTE_EMBEDDING_SPLIT_MAX_ITEM_TOKENS=4096` and the host OVMS graph rejecting over-cap input with "longer than allowed 4096"), that an at-ceiling request serves, and that an over-ceiling external request returns a clean HTTP 400 under `overflow=auto`. The 8192 target failed a measured token sweep (a near-8192-token single item wedges the GPU >90s) and the gap was escalated to the user, who confirmed 4096 — this is the sanctioned fallback path, not a silent downgrade.

Memory is correct: both OVMS containers read 12Gi and `OMNIROUTE_MEMORY_MB=12288` live, the reranker bump was a value-only patch that preserved its working HTTP probe, and qdrant is provably untouched (gen=1, matching uid, restarts=0).

Two things keep this from APPROVED. The reranker is `0/1` from a pre-existing, explicitly out-of-scope graph-load hang; the owned part of the change (value-only patch, HTTP probe preserved) is correct, but AC6 as written asserts the reranker stayed 1/1, and it did not. And the `ovms-embeddings-proxy.yaml` — the component that makes OmniRoute reach the host backends at all — is untracked, so NFR3/AC7 reproducibility is not met for the one object that defines the new topology.

### Root cause and the host-native PF pivot (deviation from the design)

The design planned to fix the in-cluster StatefulSet in place via a partitioned rolling update, a gentler script readiness probe, and a memory bump. Implementation found that neither probe nor memory tuning cured the wedge — the SR-IOV VF compute streamer (`ccs0`) hangs under sustained inference, reproducibly across nodes. The implementer moved serving host-native onto the PF Arc device on all four gremlins and scaled the StatefulSet to 0. This is a material architecture change from the approved design, but it is the correct response to the design's own stated fatal condition ("no replica reaches READY under any probe budget → escalate to GPU-device diagnosis and the user"), and the user directed the "get off kube" path. The CPU-canary escalation the design required before widening blast radius was effectively replaced by the PF canary, which is a device-level diagnosis in the same spirit.

The residual is honest: under OmniRoute's own heavy background embedding load the PF also wedges intermittently (same `ccs0`/fence signature), rotating across nodes; nginx failover keeps 2-3/4 serving. I saw this directly — one ad-hoc call hit a 504 and one of four PF health probes timed out — while a paced 12-call run was clean (12/12, 1024-dim, sub-3s). The durable fix (i915-sriov-dkms / GuC-HuC firmware bump plus a source-side concurrency cap) is correctly scoped as follow-up D, not silently dropped.

### Ceiling reconciled to 4096 at both layers (escalated fallback, verified)

I verified both layers live: the OmniRoute guard reads `OMNIROUTE_EMBEDDING_SPLIT_MAX_ITEM_TOKENS=4096`, and a direct over-cap request to a host backend returned `longer than allowed 4096`, so the graph `max_length` is 4096 too — the two layers carry the same number, which AC5 requires. An over-ceiling external request through the public API returned a clean HTTP 400 naming the item, estimate, and cap under `overflow=auto`.

The 8192 target the user originally set failed the F2 gate with recorded evidence (near-8192-token single item >90s, wedges the GPU), 6144 was rejected because it re-enters the wedge regime under real concurrent load, and the gap was escalated via `send_message` with the user confirming 4096. This is exactly the "both layers = 8192 OR an escalated proven fallback" path this task's acceptance allows, so it is not a silent downgrade.

### Memory +50% and qdrant isolation

Both OVMS container limits read 12Gi live and `OMNIROUTE_MEMORY_MB=12288`, matching the +50%-off-8Gi/8192 base the user decided. The reranker bump was applied as a value-only patch (`resources/limits/memory` only) and its live readiness probe is still HTTP `/v2/health/ready` — the committed `/v3/rerank` exec script (which 404s live) was correctly NOT applied, preserving the reranker's probe as the task required. qdrant is provably untouched: generation=1, uid `a2c81b89-45b7-407c-bd5b-691eceb47aa8`, restarts=0, still Ready. The live-verify note that the measured OVMS footprint (~4.5-6.6Gi) makes 12Gi oversized is a fair, non-blocking observation; the +50% is the user's explicit directive.

### Reranker 0/1 — the one real gap against AC6 as written

AC6 states the reranker "stayed 1/1 throughout." Live it is `0/1`. The evidence that this change did not cause it is solid (restarts=0, empty lastState, no OOMKill, probe unchanged, 12Gi + env already live before the step), and the cause — an OVMS mediapipe `/v3/rerank` graph-load hang — is explicitly Out of scope in the design and context, with the user accepting Option A (do not pull the reranker functional fix into this task). So the owned work is correct and the gap is out-of-scope. But the acceptance criterion as literally written is not met, and closing it depends on the recorded user amendment rather than on the observed state. This is the kind of AC-vs-reality mismatch that should be explicitly reconciled rather than left implicit.

### Reproducibility: the proxy manifest and host-native config are not fully captured

FEAT-005 committed the four omniroute-memory files to diff-match live, and I confirmed no qdrant, `.changeset`, or `CHANGELOG` files were touched. But `ovms-embeddings-proxy.yaml` — the hostNetwork nginx Deployment and ConfigMap that OmniRoute's Service now points at, i.e. the single object that makes the whole host-native path reachable — is untracked (`git status` shows `??`). The committed `ovms-embeddings-statefulset.yaml` is `replicas: 0` and explicitly for rollback only, so without the proxy manifest the committed config does not describe how embeddings actually serve. The host-native OVMS service and its `max_length=4096` live in `modules/ovms-embeddings-host.nix` in a separate repo (committed there, not pushed). NFR3 asks that the fix be captured declaratively and not left as an undocumented live edit; the proxy manifest being untracked is the concrete miss.
