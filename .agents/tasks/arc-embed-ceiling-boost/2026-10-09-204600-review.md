# arc-embed outage fix, ceiling reconcile to 4096, and +50% memory bump — integration review (v2)

This change remediates the `arc-embed/qwen3-embedded` "so many problems" report. Live diagnosis found the real cause was an Intel Meteor Lake Arc GPU compute-engine (`ccs0`) hang on the in-cluster SR-IOV-VF OVMS embedding path, not a context-window problem: wedged replicas sat `0/1`, OmniRoute load-balanced onto dead backends, and clients saw `fetch failed`. The fix abandons the in-cluster StatefulSet (scaled to 0, kept for rollback), moves embedding serving host-native onto each gremlin's physical-function Arc device, fronts the four PF backends with an in-cluster `ovms-embeddings-proxy` (nginx, hostNetwork, least_conn + failover), confirms the model id story, reconciles the per-item ceiling to 4096 at both layers (8192 failed a measured gate and was escalated), and raises memory +50% (12Gi on both OVMS containers, `OMNIROUTE_MEMORY_MB=12288`). This is the second review pass; the prior pass (203532) requested three changes which have since been addressed in commit c885ebc0.

Watch for: a live GPU wedge is still observable under load — one of the four PF backends (10.1.1.15) timed out on even a 1-token ping during this review (confirmed, exit 28 at 30s), consistent with the documented residual and NOT the original fetch-failed outage; the public API still served 20/20 clean through nginx failover.

**Verdict**: APPROVED

## High-level view

The outage is fixed and verified live: 20/20 paced public `POST /v1/embeddings` calls returned HTTP 200 with 1024-dim vectors and zero `fetch failed`, and the four proxy pods are 4/4 Ready with restarts=0. The design's in-place StatefulSet-rolling model was superseded by a host-native PF pivot, which the user explicitly directed ("get off kube") and which addresses the GPU-device root cause the design itself named as its fatal-condition escalation.

The ceiling landed at 4096 on both layers. The OmniRoute guard reads `OMNIROUTE_EMBEDDING_SPLIT_MAX_ITEM_TOKENS=4096` and the host OVMS graph rejects over-cap input with "longer than allowed 4096" (verified on three of four PF nodes), so the two layers carry the same number. The 8192 target failed a measured token sweep (a near-8192-token single item wedges the GPU >90s) and the gap was escalated to the user, who confirmed 4096 — this is the "both layers = 8192 OR an escalated proven fallback" path this task's acceptance explicitly allows, not a silent downgrade.

Memory is correct and live: both OVMS containers read 12Gi and `OMNIROUTE_MEMORY_MB=12288`, the reranker bump was a value-only patch (restarts=0) that preserved its working HTTP `/v2/health/ready` probe, and qdrant is provably untouched (gen=1, uid a2c81b89, unchanged).

The three findings from the prior pass are resolved: the keystone `ovms-embeddings-proxy.yaml` is now committed, the AC6 "reranker 1/1" sub-clause is explicitly recorded as amended per the user's FEAT-004 Option-A acceptance (the reranker is 0/1 from a pre-existing out-of-scope `/v3/rerank` graph-load hang that this task's owned work provably did not cause), and the host-native/i915 reproducibility pointer was corrected in live-verify. The one remaining item is a NIT: the NixOS module defining the host-native serving path lives in a separate repo and is not present in this workspace checkout — an inherent cross-repo boundary already flagged for the user.

### Host-native PF pivot (deviation from the design, correctly sanctioned)

The design planned to fix the in-cluster StatefulSet in place via a partitioned rolling update, a gentler script readiness probe, and a memory bump. Implementation found neither probe nor memory tuning cured the wedge — the SR-IOV VF compute streamer (`ccs0`) hangs under sustained inference, reproducibly across nodes. The implementer moved serving host-native onto the PF Arc device on all four gremlins and scaled the StatefulSet to 0. This is a material architecture change from the approved design, but it is the design's own stated fatal-condition path ("no replica reaches READY under any probe budget → escalate to GPU-device diagnosis and the user"), and the user directed the "get off kube" path. The CPU-canary the design required before widening blast radius was effectively replaced by the PF canary, a device-level diagnosis in the same spirit.

The residual is honest and reproduced during this review: node 10.1.1.15 timed out on a 1-token ping (exit 28 at 30s) while the other three served over-cap rejections correctly, i.e. the PF also wedges intermittently under OmniRoute's heavy background embedding load (same `ccs0`/fence signature), rotating across nodes; nginx failover keeps the public path serving (20/20 clean this run). The durable fix (i915-sriov-dkms / GuC-HuC firmware bump plus a source-side concurrency cap) is scoped as follow-up D, not silently dropped.

### Ceiling reconciled to 4096 at both layers (escalated fallback, verified live)

Both layers were checked live: the OmniRoute guard reads `OMNIROUTE_EMBEDDING_SPLIT_MAX_ITEM_TOKENS=4096`, and a direct over-cap request to the host backends returned "Input length 5002 longer than allowed 4096" on nodes 10.1.1.12/13/14 — so the graph `max_length` is 4096 too and the two layers carry the same number (AC5). An over-ceiling external request through the public API returned a clean HTTP 400 naming the item (~6667 tokens), estimate, and 4096 cap under `overflow=auto`; a correct-id request returned 200 with a 1024-dim vector.

The 8192 target failed the F2 gate with recorded evidence (near-8192-token single item >90s, wedges the GPU), 6144 was rejected because it re-enters the wedge regime under real concurrent load, and the gap was escalated via `send_message` with the user confirming 4096. This matches the acceptance's permitted escalated-fallback path.

### Reranker 0/1 — AC6 sub-clause now explicitly amended

AC6 as written asserts the reranker "stayed 1/1 throughout"; live it is 0/1 (verified: ready=false, restarts=0). The prior pass flagged this as an implicit, unreconciled mismatch. It is now explicitly reconciled in live-verify.md: the 0/1 is a pre-existing, explicitly out-of-scope OVMS `/v3/rerank` mediapipe graph-load hang, and the task's owned work is provably not the cause — the 12Gi bump was a value-only patch (restarts=0, empty lastState, no OOMKill, verified live) and the live HTTP `/v2/health/ready` probe was preserved (the committed `/v3/rerank` exec script was correctly NOT applied). The user accepted FEAT-004 Option A, so "stayed 1/1" is recorded as not-applicable rather than left implicit. The owned memory work meets AC6; qdrant is untouched (gen=1, uid a2c81b89) and the reranker HTTP probe is intact (AC8).

### Reproducibility: proxy manifest now committed; host-native config in a separate repo

The prior pass flagged `ovms-embeddings-proxy.yaml` — the hostNetwork nginx Deployment+ConfigMap that OmniRoute's Service now points at, the single object that makes the host-native path reachable — as untracked. It is now committed (c885ebc0) and the live Service selector (`app=ovms-embeddings-proxy`, targetPort 8001) matches the manifest. The remaining gap is that the host-native OVMS service and its `max_length=4096` live in a NixOS module in the separate `nixos-k3s-configs` repo whose source is not present in this workspace checkout; live-verify.md records this and flags the push for the user. This is an inherent cross-repo boundary, not a miss resolvable from here.
