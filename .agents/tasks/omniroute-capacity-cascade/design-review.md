# Design Review: OmniRoute Capacity Cascade

## Findings

1. **HIGH — The required OmniRoute runtime/API patch is still outside the governing implementation scope.** In **Overview** and **Phase 0: Authorized Runtime/API Prerequisite**, the design correctly concludes that configuration alone cannot guarantee immediate shared-capacity failover, but then makes implementation depend on amending `requirements.md` and editing six OmniRoute application files, building an image, and deploying it. The current requirements explicitly put “Editing the OmniRoute application source checkout” out of scope. A design cannot make an out-of-scope production runtime change authorized merely by listing a future requirements amendment as its first phase; until that amendment is separately approved, there is no implementable path that satisfies both the design and requirements. This is especially material because the design’s cited current behavior converts account-semaphore queue-full into HTTP 500, so omitting the patch is not a safe fallback. **Concrete fix:** amend and approve `requirements.md` before this design is accepted, narrowly authorizing the enumerated files, tests, candidate image build, immutable-digest deployment, and digest rollback. Then update the design to reference that approved scope rather than treating requirements amendment as an implementation phase. If authorization is not granted, explicitly terminate the configuration-only approach as infeasible.

2. **HIGH — The `queueDepth: 0` immediate-failover proof omits the source step that resolves stored config and must preserve numeric zero.** In **Source-Proven Routing Semantics / Zero-depth queue and GLM strategy**, the design cites schema acceptance (`src/shared/validation/schemas/combo.ts:155-177`), semaphore behavior for `maxQueueSize: 0` (`open-sse/services/rateLimitSemaphore.ts:126-177`), and the round-robin caller passing a *resolved* queue depth (`open-sse/services/combo.ts:3245-3265`). It does not cite the resolver that turns persisted combo config into that value. Without showing that this path uses nullish/default-aware handling rather than a truthiness expression such as `queueDepth || default`, schema validity does not establish that literal zero reaches either semaphore. This missing link affects both the no-wait 4070 behavior and one-target GLM fail-up and therefore falls under the review instruction that uncited routing-semantic claims are HIGH. **Concrete fix:** add the exact `open-sse/services/comboConfig.ts` file-and-line citation proving that stored `queueDepth: 0` resolves to `0`, quote or describe the relevant nullish/default rule, and require an integration test that persists a combo through POST and PUT, reads back zero, dispatches against occupied combo-local and account gates, and asserts `queued: 0` plus immediate member/tier advancement. Keep the existing API sanitizer fix and management-route retention tests.

3. **MEDIUM — The backup/development ordering is internally contradictory.** **Backup is the first production action** says the backup must exist “before editing either source tree,” while **Candidate deployment and canaries** says to build and test the approved runtime patch before touching production and only then create/validate the production backup before deployment. Building the prerequisite necessarily edits the OmniRoute source tree, so both instructions cannot be followed. The requirements only require backup before live mutation or the writable durable-policy edit; they do not require a production-state backup before isolated application development. Ambiguous sequencing is risky here because the backup is also the runtime rollback anchor. **Concrete fix:** state one unambiguous order: (1) develop, test, and publish the approved OmniRoute candidate in an isolated clean worktree without live or durable-policy mutation; (2) make the timestamped backup the first production-host mutation and capture the old immutable digest/deployment state; (3) validate the backup; (4) deploy the candidate digest and run canaries; (5) edit/apply the durable policy and live records. Replace “before editing either source tree” with “before editing the writable durable policy source or making any live deployment/API/canary mutation.”

## Verified Assumptions

- The design supplies concrete source citations for nested execute-mode dispatch: priority is accepted by execute mode and passed to `executeRuntimeUnitCombo` (`open-sse/services/combo/dispatchPrelude.ts:691-744`); runtime combo references recurse with depth/cycle guards and priority order is preserved (`runtimeUnits.ts:93-130,165-172`); failover-eligible child responses advance the parent (`runtimeUnits.ts:220-346`).
- The cited child-capacity implementation resolves leaves, deduplicates shared connections, and regards a child as full only when all positively capped connections are full (`runtimeUnitCapacity.ts:36-89`). This supports tier1-to-tier1b pre-skip behavior when both GPU connections are occupied.
- The design cites the low-level zero-depth behaviors: zero is schema-valid (`src/shared/validation/schemas/combo.ts:155-177`), a semaphore given `maxQueueSize: 0` creates no waiter and rejects immediately (`rateLimitSemaphore.ts:126-177`), and round-robin handles combo-local queue-full/timeout by advancing (`combo.ts:3245-3265`). Finding 2 identifies the unresolved config-resolution link rather than disputing these cited behaviors.
- The one-target GLM choice is source-justified: round-robin uses the bounded member gate, and exhaustion produces failover-eligible 503 `ALL_TARGETS_SKIPPED` (`combo.ts:3836-3857`), whereas the prior one-target priority structure does not provide the required bounded member behavior.
- The `[5090, 4070, 5090]` structure is supported by citations showing distinct execution keys for unique step IDs (`comboStructure.ts:87-147`), cyclic round-robin state and success-pointer movement (`rrState.ts:38-53`; `combo.ts:3453-3464`), and connection caps overriding fallback combo concurrency (`concurrencyCaps.ts:57-75`; `comboPredicates.ts:331-345`). Together with shared account gating, this supports steady occupancy of 5090=2 and 4070=1; it does not imply a permanent request-number sequence after arbitrary prior traffic, which the design correctly disclaims.
- The account-gate race is explicitly source-cited: the key includes provider and connection/account identity (`executorHelpers.ts:16-60`), defaults permit queued waiting (`accountSemaphore.ts:42-43,182-218`), current chat dispatch does not pass zero-depth queue options (`chatCore.ts:3059-3070`), and exceptions currently propagate to the combo outer 500 handler (`chatDispatch.ts:52-64`; `chat.ts:1818-1862`; `combo.ts:3332-3339,3782-3786`). The proposed explicit queue-full classification is therefore a necessary runtime behavior, not a configuration assumption.
- Prompt-cache affinity is separately source-cited as able to reorder/reset ordinary round-robin independently of session stickiness (`combo.ts:3068-3118`; `promptCacheAffinity.ts:81-175,318-347`). The lane-scoped `disablePromptCacheAffinity` design avoids changing unrelated combos.
- The canonical managed JSON specifies both lanes consistently: provider caps 2/1/1; ordered tier1 `[5090,4070,5090]`; tier1 and tier1b `queueDepth: 0`, no retries, disabled session stickiness, and lane-scoped runtime flags; GLM concurrency 1; executable root order; local-only roots; local/root timeout 600000 ms; and cloud timeout 30000 ms. The 30000 ms cloud value matches the authoritative user request and review focus even though the current requirements text still says 60000 ms.
- The durable-source mapping covers both lane builders, provider policies, zero-depth projection/readback, tier1b generation, root wiring, cloud timeout generation, dependency ordering, legacy tester preservation, backup behavior, and exact/idempotent fixture tests. Its intended projection corresponds to the canonical live structures.
- The backup contents, owner-only modes, secret rejection, old deployment digest capture, reverse-dependency policy rollback, and runtime digest rollback are sufficient in substance once the ordering ambiguity in Finding 3 is corrected.

## Unverified/Wrong Assumptions

- **Wrong under the current requirements:** the runtime/API prerequisite is authorized. It remains explicitly out of scope until the requirements are separately amended and approved; see Finding 1.
- **Unverified in the design’s cited semantic chain:** persisted `queueDepth: 0` survives config resolution as numeric zero. The missing resolver citation/test is the gap in Finding 2.
- **Unverified:** inspected checkout commit `5458026c216f77a3da68ea49152dc33470cfe2cb` corresponds to the currently deployed old image. The design acknowledges that no revision label establishes provenance. Replacing it with a tested candidate bound to an approved commit and immutable digest must remain a deployment gate.
- **Unverified because the prerequisite does not yet exist:** the future queue-full classification, lane-scoped prompt-affinity opt-out, management API retention behavior, candidate image digest, and OCI revision binding. These must be demonstrated by the specified tests and immutable artifact before production mutation; design prose alone is not evidence of implemented behavior.
- **Unverified:** the actual durable Kubernetes deployment owner/source. The design leaves it unidentified and allows only an explicitly captured live immutable-digest operation until ownership is resolved; this must not become an indefinitely untracked deployment change.
- **Unverified:** the RTX 5090 vLLM workload still uses `--max-num-seqs 2`. The design correctly makes direct workload inspection a hard pre-load-test gate.
- **Unverified by instruction:** current live counts and values (93 combos, 44 cloud pools at 30000 ms, provider caps 2/1/1, and the missing research tier1b record) were not re-run. The validated pre-change backup/readback must establish them before mutation.
