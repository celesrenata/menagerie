## Root cause: truncate has no effect

In OVMS v2026.4.0 (`src/embeddings/embeddings_calculator_ov.cc:173`), when `truncate()` is set the calculator only adds `params["max_length"] = maxContextLength` before calling `tokenizer.encode`. Current OpenVINO GenAI `Tokenizer` has a separate `truncation` flag that defaults to false (`tokenizer_impl.cpp`, `truncation_val = false`), so encode does not truncate. The tokenize endpoint works because `tokenize_parser.cpp:92` also sets `truncation = true`. The embeddings path never does. The embeddings request parser also ignores extra JSON params, so a client cannot turn it on per request. After tokenizing, `isInputIdSizeOk` rejects anything over `max_length`.

Effect: `--max_length=8192` works as a hard reject cap, not as truncation.

- Before: items up to 32,768 tokens were embedded.
- Now: items from 8,193 to 32,768 tokens get a 400.

Zoo chunks (≤~1,150 chars) and OmniRoute memory traffic (~400 tokens) are far below the cap, so they are not affected.

## Decision: keep `--max_length=8192` as a hard per-item cap

The orchestrator chose option 1. Its reasons:

- Zoo already caps items at `MAX_ITEM_TOKENS` 8191, and memory traffic is ~400 tokens, so no known caller is affected.
- A hard per-item bound is the safer OOM guard on this iGPU.
- A clear 400 is better than an OOM cascade.

The other options were `--max_length=32768`, which keeps the old behavior but has no bound, and dropping the flags.

The manifest has a comment above the args stating that OVMS 2026.4.0 `truncate:true` does not truncate and items over 8192 tokens get a 400. The comment-only edit left the live spec unchanged (`kubectl diff` exit 0).

Commit in `~/sources/kube`: `2af4afd fix: ovms-embeddings max_length 8192 cap (truncate), memory 8Gi/2Gi`. Not pushed.

## Follow-ups

- File an upstream OVMS issue: the embeddings calculator should set `params["truncation"] = true` alongside `max_length` when `truncate()` is set, as `tokenize_parser.cpp` already does.
- Optional: have OmniRoute truncate single items over 8192 tokens before forwarding to `arc-embed`, so third-party callers get truncation instead of a 400.
