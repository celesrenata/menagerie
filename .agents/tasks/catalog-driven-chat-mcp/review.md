# Catalog-driven chat MCP servers + upstream model-sync doc

This change retires the two hardcoded GPT-5.2-era OpenAI chat MCP servers (`chat-gpt52`, `chat-codex`) and replaces them with a three-tier Nix attrset catalog (`chatModelCatalog`) that is the single source of truth for both the generated `mcpServers` entries and a new activation-time reference doc. The three servers (`chat-flagship`/GPT-6-Astra, `chat-codex`/GPT-6.1-Sol, `chat-fast`/GPT-6-Luna) are generated by mapping `mkChatServer` over the catalog rather than hand-written. A sibling `home.activation.kiroMcpModelsDoc` entry injects the catalog as JSON, cross-checks each model id against the live OpenAI `/v1/models` endpoint, and writes `$HOME/.kiro/mcp-models.md` with per-tier status/rates. All 27 unrelated servers (including the newly-added `total-pc-control`) survive unchanged, and the `kiroMcpConfig` jq-merge logic is preserved intact.

Watch for: the `RETIRING` status derives from a `shutdown_date` field on the live model object that OpenAI's `/v1/models` payload does not document, so that branch may never fire (possible). This is harmless — it degrades to `live`. No blocking issues.

**Verdict**: APPROVED

## High-level view

The catalog is a clean, DRY refactor: one attrset drives server generation (`listToAttrs (map mkChatServer ...)`) and the reference doc (`builtins.toJSON (builtins.attrValues chatModelCatalog)`), so model ids, display names, and rates cannot drift between the two consumers. Each generated server keeps the exact bash-wrapper shape of the servers it replaces, pulling the key from SOPS at launch so it never lands in the Nix store.

The new `kiroMcpModelsDoc` activation entry is fully defensive. It guards the secret read with `[[ -r ... ]]` and a stderr skip message that matches the established `zooOmniRouteImport` style, pipes curl through `|| true`, validates the response is JSON and error-free before trusting it, and otherwise falls back to a catalog-only doc with an "upstream check unavailable" note. It can only ever write a file or no-op; it never fails activation.

Slug derivation (`ascii_downcase | gsub("[^a-z0-9]+"; "-") | trim`) produces the MCP tool names (`GPT-6.1-Sol` → `chat-with-gpt-6-1-sol`), matching the verification evidence.

The one bundled concern is the `kiroMcpConfig` rewrite from all-or-nothing copy to a jq merge; spec item 4 explicitly expects this logic to be present and intact, and it is.

## Catalog as single source of truth

`chatModelCatalog` holds exactly the three required tiers, each with `serverName`, `displayName`, `model`, `description`, `inputRate`, `cachedInputRate`, and `outputRate`:

```nix
flagship = { serverName = "chat-flagship"; displayName = "GPT-6-Astra"; model = "gpt-6-astra"; ... "$10.00" / "$1.00" / "$50.00" };
codex    = { serverName = "chat-codex";    displayName = "GPT-6.1-Sol"; model = "gpt-6.1-sol"; ... "$2.00" / "$0.10" / "$10.00" };
fast     = { serverName = "chat-fast";     displayName = "GPT-6-Luna";  model = "gpt-6-luna";  ... "$0.10" / "$0.01" / "$0.50" };
```

Both downstream consumers derive from this attrset: `chatServers = builtins.listToAttrs (map mkChatServer (builtins.attrValues chatModelCatalog))` for the MCP entries, and `chatModelCatalogJson = builtins.toJSON (builtins.attrValues chatModelCatalog)` for the doc. A rate or model-id edit therefore propagates to both the server config and the reference doc without a second edit site.

## Resilient upstream model-sync doc

`kiroMcpModelsDoc` is a new `entryAfter [ "writeBoundary" ]` sibling to `kiroMcpConfig`. Its guard and skip style match `zooOmniRouteImport` in `omniroute-editors.nix`:

```bash
if [[ -r "$secret" ]]; then
  key="$(${pkgs.coreutils}/bin/tr -d '\r\n' < "$secret")"
  models_json="$(${pkgs.curl}/bin/curl -s -H "Authorization: Bearer $key" https://api.openai.com/v1/models || true)"
  ... jq -e . && jq -e 'has("error")' negation -> upstream_ok=1
  else echo "...unavailable or returned an error..." >&2
else
  echo "kiroMcpModelsDoc: $secret not readable; skipping upstream check (SOPS not yet activated)..." >&2
fi
```

The resilience chain is layered correctly: `curl ... || true` swallows network failure, `jq -e .` rejects non-JSON, `jq -e 'has("error")'` rejects an OpenAI error object, and any failure path sets `models_json='{"data":[]}'` with `upstream_ok=0`. The status column then renders `upstream check unavailable` for every tier and the header prints the degraded note. There is no path where a curl or parse failure aborts activation (confirmed; the verification smoke test with an unreadable key exited 0 and still wrote the doc at 644).

The catalog is injected via `lib.escapeShellArg chatModelCatalogJson`, which single-quotes the JSON so the embedded `$` in rate strings (`$10.00`) is not shell-expanded, then re-parsed inside the heredoc by `jq`. The doc stays in lockstep with the Nix catalog (confirmed).

## Slug and status derivation

```jq
(.displayName | ascii_downcase | gsub("[^a-z0-9]+"; "-") | gsub("^-+|-+$"; "")) as $slug
| ("chat-with-" + $slug) as $tool
```

`GPT-6-Astra` → `gpt-6-astra` → `chat-with-gpt-6-astra`; `GPT-6.1-Sol` → the `.` and `-` collapse to single dashes → `gpt-6-1-sol` → `chat-with-gpt-6-1-sol`. This matches both the spec rule and the verification output. The status branch marks `live`, `MISSING` (model id absent from `$byId`), or `RETIRING (<shutdown_date>)`.

The `RETIRING` branch keys off `($m.shutdown_date // null) != null`. OpenAI's public `/v1/models` model objects expose `id`, `object`, `created`, and `owned_by` — `shutdown_date` is not a documented field, so this branch may never fire in practice (possible — would need to be checked against the actual live payload). It is written defensively and degrades to `live` when the field is absent, so it is not a correctness defect; it is at worst inert.
