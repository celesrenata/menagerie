## What exploration found

Qdrant has its own unclipped path, `qdrant.ts embedText()`, which serves both upsert (`:321`) and search (`:389`).

No tokenizer helper exists; the repo estimates chars/3 (`embeddingBatchSplit.ts ESTIMATED_CHARS_PER_TOKEN`) or chars/4 (`retrieval/scoring.ts estimateTokens`).

A single-input request is never retried inside the handler. ## Design decisions

1. **Memory text is chunked and mean-pooled into one vector.** The data model stores one vector per memory id, both in vec_memories and in Qdrant. Per-chunk storage would need a schema change, a new dedup/score aggregation, and a reindex, and it is out of scope. A leading-chunk-only vector would make everything after 12k chars invisible to recall. Chunk vectors are mean-pooled after L2 normalization, then renormalized, and queries go through the same path so query and stored vectors share a space. Text that fits in one chunk takes the exact current code path and returns the raw vector unchanged, so existing stored vectors stay valid with no reindex.
2. **Chunk limits.** `MAX_EMBED_CHUNK_CHARS = 12_000`. At the conservative 3 chars/token that is ≤4,000 estimated tokens, under the new 4096 per-item cap, and about 3K real tokens, roughly 3–4 s on the Arc. `MAX_EMBED_CHUNKS = 3`, so at most 36,000 chars are embedded and the rest is dropped. This replaces the old 20k clip and bounds chat-path latency to 3 sequential calls. Chunks are sent **sequentially, one input per request**, not as an array, so no single OVMS inference exceeds about 4K tokens. Boundaries are chosen in this order: the last `\n\n` in the window `[maxChars/2, maxChars]`, then the last `\n`, then the last whitespace, then a hard cut. The splitter is char-based because no tokenizer helper exists; it is documented as such.
3. **Per-item guard.** It lives in the handler and reuses the split config. `EmbeddingSplitLimits` gains `maxItemTokens`, from the global env `OMNIROUTE_EMBEDDING_SPLIT_MAX_ITEM_TOKENS` (default 4096) and an optional third field on a provider entry, `id=maxItems:maxPaddedTokens:maxItemTokens`. It is therefore active exactly for the providers that get splitting (default `arc-embed,ovms-arc`) and off when splitting is off. Overflow behavior comes from `OMNIROUTE_EMBEDDING_ITEM_OVERFLOW = auto | truncate | reject` (default `auto`). Under `auto`, **internal callers truncate** (logged warning) and **external callers get HTTP 400**. The 400 matches OpenAI's over-length semantics and keeps an external client from silently getting a vector of a different text. It names the item index, the estimate, the cap, and the env var that switches to truncate. A 400 is not in `HARD_ERROR_STATUSES`, so the connection is not cooled down. Internal vs external is decided by a new explicit `internalCaller?: boolean` flag, not inferred from a missing clientRawRequest, because `/v1/providers/[provider]/embeddings` and modelTestRunner also omit it. Only `remote.ts` and `qdrant.ts` set it. Truncation: strings are cut to `maxItemTokens × 3` chars, and token arrays are cut to `maxItemTokens`. The guard runs after `applyStructuredTransport` and only when `prepared.normalizeProviderResponse === null` (plain OpenAI transport), and before `resolveSplitPlan`. As a result, every upstream request, every sub-batch, every halved re-split, and every combo target sees only capped items.
4. **No unchanged resend after a timeout or 5xx.** In the handler, decision 3 means an oversized item is never sent anywhere, and the existing policy stays: a timeout is never resent, and a 5xx sub-batch is halved once. For memory, `EmbeddingError` gains `status?: number`. `embedRemote` sets it on non-OK responses, and `embedWithRetry` returns immediately, without a second attempt, when `reason === "timeout"` or `status >= 500`. The memory is marked `needs_reindex` and the reindex sweep retries it later, so the inline retry is gone but the memory still gets embedded. `rate_limited`, network `request_failed` without a status, and `model_load_failed` are still retried once, so the #13601 tests keep passing. `embedRemote` does no retries of its own. If one chunk fails, the whole embed fails with that chunk's error.
5. **Combo fallback gate: skip, don't mutate.** When the fallback target is prefix-cache-sensitive (`isPrefixCacheSensitive(target.provider, override-from-target.connectionId)`), the proactive fallback compression is skipped entirely and a debug line is logged. Passing a hand-built `CompressionConfig` would risk changing stacked/caveman defaults, which are read off `options.config`. Also, any rewrite on a KV-prefix-sensitive target forces a full re-prefill, the opposite of the "zero-latency" goal. Skipping covers non-Lite fallback modes too (review issue 3). The target's own request still runs chatCore's gated compression.

## Gaps / assumptions

- Batch latency stays an open risk. With `maxItemTokens = 4096`, the existing 32,768 padded-token budget still allows one OVMS inference of 8 × 4096 tokens, which is likely well over the 20 s i915 watchdog. This plan doesn't change `OMNIROUTE_EMBEDDING_SPLIT_MAX_PADDED_TOKENS` because codebase-indexing throughput depends on it. Live-verify should watch for fence timeouts on large batches. If they show up, set `arc-embed=32:8192:4096` in the deployment env; that needs no code change.
- The per-item estimate is chars/3, which is conservative. The 12,288-char cap is ~3K real tokens of prose, well under an OVMS `--max_length=4096`. Very dense text (CJK) may be close to 1 char/token, so OVMS's own 4096 limit is the final backstop and returns a 400 rather than wedging.
- The memory freeze already limits re-retrieval to once per conversation, so a failing query embed is not resent every turn within a conversation.
- I did not restructure the workflow. The remaining tail includes integration-gate, deploy, ovms-maxlen, live-verify, and cleanup steps whose prompts I can't reproduce faithfully, and the four changes are small enough for the existing build loop.
