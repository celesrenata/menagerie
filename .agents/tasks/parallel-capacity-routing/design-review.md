## Verified Assumptions

Each of these the design asserts and I confirmed against source:

1. **`acquireLease(capability, signal)` signature** — `BoundedElasticScheduler.makeHandle` (`src/core/task/BoundedElasticScheduler.ts`) defines `acquireLease: async (capability: RouteCapability, signal: AbortSignal): Promise<() => void>`. The design calls it with exactly these two args; worker `priority`/`criticalPath` are read internally, not passed. Correct.
2. **Returned release fn is idempotent** — both the `makeHandle` wrapper (`let released = false; return () => { if (released) return; ... }`) and `InferenceLeasePool.makeRelease()` are idempotent. The design's "double release is a no-op" and "outer `finally` + inner `finally`" composition is safe.
3. **The lease is dead code today** — `runParallelTasks` builds the scheduler with `GENEROUS_BATCH_ROUTES` and `maxInferenceLeases: DEFAULT_SCHEDULER_BOUNDS.maxDispatched`, and the `scheduler.dispatch(spec.name, async () => {...})` run body binds no `handle` and never calls `acquireLease`. Confirmed (lines ~320–324, ~440+). Root cause A is real.
4. **The 0-capacity deadlock path is real** — `InferenceLeasePool.pump()` loops on `this.held < this.liveCapacity()` and the fast-path grant checks `this.held < this.liveCapacity()`. If `liveCapacity()` returned 0 for a capability, no acquirer could ever be admitted. `liveCapacity()` clamps each `snapshot.available` with `Math.max(0, …)`, so a negative read becomes 0. The design's floor-of-1 in `createStaticRouteCapabilityProvider` is therefore the correct and necessary guard; its placement at the single provider funnel is sound.
5. **`cancelQueued()` rejects only waiters, never held leases** — `BoundedElasticScheduler.cancelQueued()` calls `this.dispatchSemaphore.cancel()` then `pool.cancelWaiters()` for every pool; `InferenceLeasePool.cancelWaiters()` splices only the `waiters` array and never decrements `held`. PAR-021.5 claim and the abort-behavior narrative are correct.
6. **A waiting worker returns to `runnable` on abort** — `makeHandle.acquireLease`'s `catch` sets `worker.state = "runnable"` when it was `"waiting-for-inference"`, then rethrows; the dispatch body's existing `catch` records `cancelled`/`failed`. Matches the design.
7. **`openAiOmniRouteCustomRoutes` has no capability field today** — `packages/types/src/provider-settings/openai.ts` defines it as `z.array(z.object({ name: z.string(), modelId: z.string() })).optional()`. Finding #2's premise is confirmed; the proposed additive optional `capability` field is the correct non-heuristic fix.
8. **`RouteCapability` union matches the proposed schema enum** — `elasticTypes.ts`: `type RouteCapability = "reader" | "reasoner" | "long-context" | "vision" | "general"`. The design's `routeCapabilitySchema = z.enum(["reader","reasoner","long-context","vision","general"])` is an exact, lockstep match. Every capability in the capacity table is a valid member.
9. **`laneToRouteCapability` semantics** — `capabilityLanes.ts`: `coder.primary` → `"reasoner"` for `implementation`/`debugging`/`refactor`, else `"general"`; readers → `"reader"`; `reasoning.escalation` → `"long-context"`/`"reasoner"`. The design's claim that the default coder (`defaultLaneTaskType` → `"implementation"`) resolves to `"reasoner"` (finding #1's motivating case) is correct.
10. **`defaultLaneTaskType(mode)`** — `parallelWorkerRouting.ts` returns `"lookup"` for reader modes, `"implementation"` otherwise. Confirmed; this is why the spread must be on the reasoning path (finding #1 resolution is valid).
11. **`assignLanes`/`assignLane`/`laneToRouteCapability` are pure/additive** — confirmed in source and in the `capability-lanes-routing` design/tasks (Req 9.8, task 8.1). The new `resolveLaneRouteId` is a separate pure function that does not mutate these. Purity contract preserved — no spec contradiction.
12. **`route` pass-through-verbatim** — `ParallelTasksTool.rejectMastermindPhysicalPlacement` skips any spec with a non-empty `route` ("A user route override explicitly pins placement; forward it verbatim"). Decision C step 1 (explicit `route` wins) honors this exactly.
13. **Auto-reader predicate** — `runParallelTasks` gates the 90s wall-clock deadline on `spec.mode === "project-reader" && spec.name.startsWith(AUTO_READER_NAME)`, with `AUTO_READER_NAME = "m5-contract-audit"` in `ParallelTaskReader.ts`. The exemption predicate in decision B reuses this exact condition. Confirmed; it cannot accidentally exempt a code worker.
14. **`clampCeiling` lowers only, floors at 1** — `BoundedElasticScheduler.clampCeiling` is `Math.max(1, ceiling === undefined ? bound : Math.min(bound, ceiling))`. Decision D/E's "policy is the upper bound; capacity never raises a bound" is correct, and the floor-at-1 means a tight policy cannot zero out dispatch.
15. **`OMNIROUTE_ROUTE_CONTEXT_WINDOWS` precedent** — exists in `src/api/providers/omniroute.ts` as a hand-maintained `Readonly<Record<string, number>>` with a source-of-truth doc comment. Decision A's "same pattern, same discipline" analogy is accurate.
16. **`maxInferenceLeases` is not an admission gate** — the pools are per-capability (`leasePoolFor(capability)` / `InferenceLeasePool.liveCapacity()` reads the provider per capability). `maxInferenceLeases` on `SchedulerBounds` is carried through `clampCeiling`-free (`maxInferenceLeases: bounds.maxInferenceLeases`) and is not consulted by the pools. The design's "observability aggregate" characterization (finding #6) is correct.

## Unverified / Wrong Assumptions

- **OmniRoute `PROVIDER_POLICIES` slot counts (vllm ~2, ollama-local 4, llama-cpp 1).** These live in the remote `omniroute-mode.py`, which this review did not inspect (consistent with `findings.md`, which also treated it as external). The design correctly treats these numbers as *operator-provided and runtime-tunable*, fixing the mechanism rather than the literals, and places them in a single documented constant with a source-of-truth comment. This is handled exactly as the brief's "unproven capacity assumption" guard requires: it is stated as an operator-maintained assumption with a bounded fail-safe, not silently baked in. Not a finding.
- **No live OmniRoute capacity endpoint is assumed.** The design explicitly declines to invent one (decision A) and leaves the `RouteCapacityProvider` seam open for a future `LiveRouteCapacityProvider`. No fabricated endpoint shape. Not a finding.

## Findings

### 1. NIT — spread-route capability classification and lease-pool capability can diverge; make the operator coupling a checked invariant, not just prose

Decision C includes custom routes classified `"reasoner"` **or** `"general"` in `collectCodeCapableRouteIds`, and round-robins `coder.primary` workers across them. But every default `coder.primary` worker leases against the `"reasoner"` pool (its `laneToRouteCapability` is `"reasoner"`), regardless of which route id the round-robin selected — including a route the operator classified `"general"`. The design handles the capacity side correctly in prose ("the `reasoner` slot count must equal the summed code-backend slots when spread is active"), and it fails safe (OmniRoute still queues any over-commit), so this is not a deadlock or over-dispatch regression. The gap is that nothing in the mechanism *enforces* or *tests* the coupling, so an operator who adds a `"general"`-classified overflow route without bumping the `reasoner` capacity silently under-admits (only vLLM's 2 generate while two backends can serve code).

Concrete fix: add an assertion-style integration test (the design already lists "Spread + lease agreement") that fails loudly if `codeCapableRouteIds.length > 1` while `STATIC_ROUTE_CAPACITY.reasoner` equals a single backend's slots, OR add a doc-comment invariant on `STATIC_ROUTE_CAPACITY.reasoner` stating "must equal the summed real slots of every route in `collectCodeCapableRouteIds` once spread is configured" directly beside the constant (not only in the design prose). This keeps the operator coupling discoverable at the edit site.

### 2. NIT — specify behavior when `collectCodeCapableRouteIds` yields a classified route whose capability is `"reader"`/`"long-context"`/`"vision"`

The helper spec says it includes `"reasoner"` and `"general"` custom routes and excludes others, "so the spread can never accidentally send code work to a reader-only alias." That is the right intent, but the design does not state what happens to a custom route a well-meaning operator classifies `"long-context"` (a plausible code-adjacent choice given `reasoning.escalation` maps there). Under the current rule it is silently excluded from code spread, which is defensible but undocumented.

Concrete fix: in the `collectCodeCapableRouteIds` description, state explicitly that only `"reasoner"` and `"general"` are code-capable for spread, and that `"long-context"`/`"reader"`/`"vision"` classifications are intentionally excluded from the coder round-robin (they remain available via an explicit per-worker `route`). One sentence closes the ambiguity.

### 3. NIT — `SMALL_FLOOR = 4` rationale vs. the per-capability liveness invariant could be stated more tightly

Decision D seeds `maxDispatched = clampCeiling(max(capacitySum, maxPerCapability, SMALL_FLOOR), policy.maxDispatched)`. The `maxPerCapability` term is what the corrected liveness invariant (finding #5 resolution) actually requires. `SMALL_FLOOR = 4` is justified as "keeps dispatch able to feed the slots and reach lease-wait," but with `maxPerCapability` already in the `max(...)`, `SMALL_FLOOR` only binds when every per-capability capacity is < 4 — i.e. it raises dispatch permits above physical slots so more workers can sit in lease-wait inside Menagerie. That is harmless and arguably desirable, but the design's one-line justification undersells why a floor above `maxPerCapability` is wanted at all.

Concrete fix: add one clause — "`SMALL_FLOOR` lets a few extra workers queue in the lease pool (`waiting-for-inference`) rather than on the dispatch semaphore, so capacity that frees mid-batch is picked up without a dispatch-permit round-trip; it never exceeds `maxLive` and never affects deadlock-freedom." This makes the floor's purpose explicit rather than implied.

## Decision resolution check (brief's six mandatory decisions)

- **A. Capacity source** — RESOLVED with rationale: static per-capability map mirroring `OMNIROUTE_ROUTE_CONTEXT_WINDOWS` (verified to exist), no assumed live endpoint, explicit `RouteCapacityProvider` seam left open for a future live provider. Fail-safe is explicit and correct (floor-of-1, `DEFAULT_UNKNOWN_CAPABILITY_SLOTS = 2`, never 0, never 12), and the 0-capacity deadlock it guards against is a real property of `InferenceLeasePool.pump()` (verified). No unproven capacity assumption — the slot numbers are stated as operator-maintained config, not baked facts.
- **B. acquireLease wiring** — RESOLVED with rationale: per-worker lifetime lease at the top of the `dispatch` run body, idempotent release in an outer `finally`, permit-then-lease ordering, auto-reader exemption (verified predicate). The deadlock-freedom argument rests on three independent, individually-sufficient legs (acyclic permit≺lease ordering with no reverse edge; leases always eventually free via `finally` + idempotent release + one-lease-per-worker; capacity floor ≥ 1 guaranteeing `pump()` can always admit). Each leg checks out against source. No "hold a permit while awaiting a lease that can never be granted" path exists, because the floor guarantees every capability pool has ≥ 1 slot and leases drain monotonically.
- **C. Routing spread** — RESOLVED with rationale: lane-driven route-id resolution in a new *pure* `resolveLaneRouteId`, coder-only ordinal round-robin (fixes the global-index unbalancing), explicit optional schema field (verified no such field exists today) chosen over a name heuristic. `assignLanes`/`laneToRouteCapability` untouched — the `capability-lanes-routing` purity contract is preserved (verified against spec Req 9.8 / task 8.1). Opt-in, so the unconfigured common case is byte-for-byte unchanged.
- **D. Bounds seeding** — RESOLVED with rationale: `maxInferenceLeases = max(1, capacitySum)` (observability aggregate), `maxDispatched` seeded with the `maxPerCapability` term so the correct per-capability liveness invariant holds, all clamped by policy via the existing (verified) `clampCeiling`.
- **E. User control** — RESOLVED with rationale: capacity is operator config, orthogonal to the user's appetite ceiling; policy only ever lowers bounds (verified `clampCeiling` lowers-only, floors at 1). No new user-facing control; `user-controlled-parallelism` Req 3.6/4.3/8.2/8.5 are honored, not contradicted. `elastic-parallel-execution`'s lease state machine is exercised as designed. `dynamic-capability-broker` is correctly identified as orthogonal (tool-capability axis).
- **F. Backward safety** — RESOLVED with rationale: no deadlock (proven, corroborated), no throughput regression for small batches (immediate grant when `held < liveCapacity()` and no queue — verified against the pool's fast path), opt-in spread, explicit fail-safe, and all existing invariants (persistence, worktree isolation, result ownership, "never abandon siblings") preserved by the purely-additive wiring.

No blocking condition from the brief is triggered: no deadlock risk, no unproven capacity assumption (stated as assumption + fail-safe), no fail-unsafe path (unknown → bounded 2, never over-dispatch; 0 impossible by floor), no spec contradiction, and all six decisions are resolved with rationale.
