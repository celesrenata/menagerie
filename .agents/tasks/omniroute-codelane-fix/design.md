# Design: Bug 1 — SEMAPHORE_TIMEOUT process crash

Repository: `/Users/celes/sources/celesrenata/OmniRoute`, branch `feat/hybrid-reader-combo` (confirmed clean, HEAD `c9230dee8` at design time). Builds on `omniroute-tier1-priority/findings.md`'s evidence that the account-level semaphore (`open-sse/services/accountSemaphore.ts`), keyed per `provider:connectionId` and acquired via `acquireConcurrencyGates(...)` in `open-sse/handlers/chatCore.ts`, is the real per-connection concurrency gate for `pool/tier1/code` — this design does not re-derive that; it picks up exactly at the semaphore-timeout throw site the findings doc named for re-location.

## Summary of the finding

**The throw site, and every direct caller inside `chatCore.ts`, already catches `SEMAPHORE_TIMEOUT` and converts it to a normal 429 (`errorType: "account_semaphore_capacity"`).** Both the streaming leg (`if (stream) { try { ... } catch (error) { if (isSemaphoreCapacityError(error)) {...} } }`, AST-verified `tryBlock: 4148-4302`, `catchClause: 4302-4456`) and the non-streaming leg (`if (!stream) { try { ... } catch (error) { if (isSemaphoreCapacityError(error)) {...} } }`, AST-verified `tryBlock: 5025-5792`, `catchClause: 5792-5825`) wrap the full `executeProviderRequest` → `acquireConcurrencyGates` → upstream-fetch chain in a try/catch that specifically recognizes `error.code === "SEMAPHORE_TIMEOUT"` and returns a clean `{ success: false, status: 429, errorType: "account_semaphore_capacity" }` result object — never a thrown error. `src/sse/handlers/chat.ts:2322-2334` reads that `errorType` and either returns it directly (pinned combo target: `hasForcedConnection === true`) or rotates to the next account and `continue`s the `requestAttemptLoop`. This is exactly the "normal per-request outcome, feeds into existing failover" behavior the incident brief asks for — **and it is already implemented and already covers the account-semaphore path that the incident's own log lines (`Account 70b82fc9... at local concurrency cap, trying fallback account`) show firing.**

This directly contradicts the incident brief's hypothesis that the crash came from the account semaphore (`accountSemaphore.ts` / `acquireConcurrencyGates` called from `chatCore.ts`). That specific semaphore is proven safe by the code (and locked by a repo test, see below). **The crash's actual uncaught-exception stack trace must be re-examined**: either it originates from a different semaphore implementation that is NOT consistently guarded, or (per `httpClientAbortGuard.mjs`'s own documented history) from a listener-leak pattern unrelated to `accountSemaphore.ts`. Section "Open questions" below is explicit about what remains unverified.

## Evidence the account-semaphore path is already safe

1. **Throw site**: `open-sse/services/accountSemaphore.ts:303-311`, inside `acquireMany()`'s `setTimeout` callback — the exact `Error: Semaphore timeout after ${timeoutMs}ms for ${keys.join(",")}` / `code: "SEMAPHORE_TIMEOUT"` shape the incident log quotes verbatim. This confirms `accountSemaphore.ts` (not `rateLimitSemaphore.ts`, a separate, differently-worded implementation used only by round-robin/quota-share combos) is the source for this incident, since the message format (`"Semaphore timeout after Nms for key1,key2"`, comma-joined composite keys) matches `acquireMany`'s multi-key signature, not `rateLimitSemaphore.ts`'s single-model signature (`"Semaphore timeout after Nms for ${modelStr}"`, no comma-join).
2. **Call site**: `chatCore.ts:3205-3225` — `acquireConcurrencyGates` (imported as `acquireMany as acquireConcurrencyGates` at chatCore.ts:382) is called with `.catch(rethrowAdmissionError)` (`open-sse/handlers/chatCore/queueBudget.ts:12-20`). `rethrowAdmissionError` passes a coded error (`err.code !== undefined`, true for `SEMAPHORE_TIMEOUT`) straight through unchanged — it only exists to upgrade an _uncoded_ timeout into the legacy 503 code. So the rejection surfaces, still coded `SEMAPHORE_TIMEOUT`, from the `await` inside `executeProviderRequest`'s inner `execute()` closure (chatCore.ts:3159 `const execute = async () => {...}`).
3. **Containment**: `execute()`'s body is wrapped `try { ... } catch (error) { releaseRawResultAccountSemaphore(); throw error; }` (chatCore.ts:3608-3618) — this just releases a (non-existent, since acquisition itself failed) semaphore slot and re-throws; it does not swallow. The re-thrown error then propagates out of `executeProviderRequest(...)` to whichever caller invoked it.
4. **Both call sites that matter catch it**:
    - **Streaming**: `chatCore.ts:4148` `try { const pipelineOutcome = await runProviderExecutionPipeline({ ..., sendProviderAttempt: (m, d) => executeProviderRequest(m, d) }); ... } catch (error) { ...isSemaphoreCapacityError(error)... }` — AST-verified `tryBlock: 4148-4302`, `catchClause: 4302-4456` (an earlier pass of this design cited "close at chatCore.ts:4335" from a hand brace-depth trace; that was off by ~121 lines and is corrected here against the compiler's own AST). `runProviderExecutionPipeline` (`open-sse/handlers/chatCore/providerExecutionPipeline.ts`) does not itself catch/rethrow around `sendProviderAttempt` — a throw from `executeProviderRequest` propagates straight out of `runProviderExecutionPipeline`'s `await` into chatCore's `try`, which is exactly what the catch at 4302 is there to classify.
    - **Non-streaming**: `chatCore.ts:5025` `try { ...; let legResult = await runNonStreamingProviderLeg({...}); ...; const loopApply = await applyServerOwnedToolLoopIfNeeded({...}); ... } catch (error) { ...isSemaphoreCapacityError(error)... }` (close at chatCore.ts:5825). `runNonStreamingProviderLeg` (`open-sse/handlers/chatCore/nonStreamingProviderLeg.ts:467-483`) has its own inner try/catch around the executor call, and **explicitly re-throws `SEMAPHORE_TIMEOUT`/`SEMAPHORE_QUEUE_FULL` on purpose** (comment: "chatCore can map them to 429") rather than converting them to the leg's own error-result shape — this is intentional pass-through so the _outer_ chatCore catch (not the leg) does the 429 conversion, and it is locked by `tests/unit/non-streaming-provider-leg.test.ts:1163-1177` (`"semaphore capacity errors rethrow so chatCore can map them to 429"`).
5. **The classification itself** (`isSemaphoreCapacityError`, `open-sse/handlers/chatCore/streamErrorResult.ts:63-66`, AST-confirmed function span — a prior pass of this design cited `:62-65`, off by one: line 62 is a blank line before the declaration) matches exactly `code === "SEMAPHORE_TIMEOUT" || code === "SEMAPHORE_QUEUE_FULL"` and is read through `getSafeErrorMetadata` (hostile-Proxy-safe). On a match, both catch blocks build `{ status: 429 (HTTP_STATUS.RATE_LIMITED), errorType: "account_semaphore_capacity", errorCode: semaphoreCode }` and **return it as a normal result — never a re-throw.**
6. **A repo-level regression test already locks the shape of the guard**: `tests/unit/chatcore-stream-error-result.test.ts:160-180` reads `chatCore.ts` source text and asserts the non-stream leg sits inside a `try { ... runNonStreamingProviderLeg ... }` block that also contains `isSemaphoreCapacityError` — i.e., exactly the containment this design is verifying, already enforced by CI.
7. **The failover path the incident wants is already wired**: `src/sse/handlers/chat.ts:2322-2334` — on `result.errorType === "account_semaphore_capacity"`, if the combo step did **not** pin a specific connection (`!hasForcedConnection`), it logs `Account ${accountId}... at local concurrency cap, trying fallback account` (the literal line quoted in the incident) and `continue`s `requestAttemptLoop` (chat.ts:1686) to pick a different connection for the same provider via `getProviderCredentialsWithQuotaPreflight`. If the step **did** pin a connection (as `pool/tier1/code`'s `code-t1-1` GLM step does, per the tier1-priority findings — every model entry carries an explicit `connectionId`), the semaphore-429 is returned as-is up to the combo attempt loop (`comboAttemptLoop.ts`/`executeTargetAttempt.ts`), which treats it as an ordinary non-2xx response from that target and falls through to the next target in `pool/tier1/code`'s declared array order (vllm 5090 → llama-cpp GLM → ollama 4070ti) exactly like any other 429/5xx — no special-casing needed, this is the existing per-target retry/fallback machinery `executeTargetAttempt.ts` already runs for every status code.

8. **A separate category, not covered by points 1-7: three direct, un-wrapped `executor.execute()` calls inside the streaming leg bypass `executeProviderRequest` entirely and must be audited on their own terms, not folded into the "every `executeProviderRequest`/`runNonStreamingProviderLeg` call site is accounted for" claim above.** `executor.execute()` is the only call that can throw a `nvidiaConcurrencyGate.ts`-sourced `rateLimitSemaphore.ts` timeout (the account-semaphore acquisition in point 2 above is a separate, already-awaited call one level higher in the same closure, not reachable from inside `executor.execute()` itself). There are exactly three such direct call sites in `chatCore.ts`, and each resolves differently:
    - **`chatCore.ts:3255`** — inside `withRateLimit`'s callback, itself inside the try at `chatCore.ts:3232` whose catch is `chatCore.ts:3546-3549` (`catch (error) { releaseAccountSemaphore(); throw error; }`). A rejection here propagates through that catch's rethrow into `execute()`'s own outer catch (`chatCore.ts:3608-3618`: `catch (error) { releaseRawResultAccountSemaphore(); throw error; }`), then out to whichever of the two top-level guarded try/catch blocks (streaming at 4148-4456, non-streaming at 5025-5825) invoked `execute()` — both of which check `isSemaphoreCapacityError`. **Safe, by containment and failover**, same category as the `executeProviderRequest` sites above — but this chain was not previously traced explicitly for this specific call site; it is traced here rather than only asserted in the abstract ("`execute()`'s body is wrapped try/catch").
    - **`chatCore.ts:3453`** — inside `runUpstreamStream`'s own local try/catch (AST-confirmed `tryBlock: 3440-3479`, `catchClause: 3479-3481`: `try { ...; const retryRaw = await executeWithUpstreamStartTimeout({ ..., execute: (signal) => ... executor.execute({...}) }); ... } catch { return null; }` — an earlier pass of this design cited this as a single "3440-3481" range as if that were the try block's span; restated here as the try/catch split, consistent with this document's AST-style citations elsewhere), used by the stream-recovery / mid-stream-continuation re-open path. Any rejection here — `SEMAPHORE_TIMEOUT`-coded or not — is swallowed into a `null` return (interpreted by the caller as "continuation unavailable, fall back to the already-sent partial stream"), never propagated or rethrown. **Safe, but by silent absorption, not by failover-to-429** — a different outcome class than the `executeProviderRequest` sites' "converts to 429, chat.ts fails over to the next connection/target" behavior. A semaphore timeout hitting this specific retry attempt is swallowed as "could not re-open the stream," not surfaced as `account_semaphore_capacity` and not retried against a different account — a correctness/observability gap (the operator never sees this specific timeout), but not a crash risk, since it never leaves the local catch.
    - **`chatCore.ts:4572`** — inside the 401/403 credential-refresh retry's local try/catch (AST-confirmed `tryBlock: 4554-4607`, `catchClause: 4607-4620` — an earlier pass of this design cited the try-start as 4553, off by one; corrected here: `try { ...; const retryResult = normalizeExecutorResult(await runWithCapture(providerRequestCapture, () => executor.execute({...}))); ... } catch (retryErr) { ...; log?.error?.(...); }`). This catch does **not** check `isSemaphoreCapacityError`, does **not** rethrow, and does **not** return an error result — it only logs (`TOKEN | retry after refresh failed: ...`) and falls through past the `try/catch` into the surrounding `providerFailure:`-bound code, which continues using the ORIGINAL pre-refresh `providerResponse`/status (the stale 401), not a 429. **Safe from a crash standpoint** (the catch is unconditional and never rethrows), but this is a real correctness bug distinct from anything else in this audit: if `executor.execute()`'s underlying provider executor (e.g. `nvidiaConcurrencyGate.ts`'s `rateLimitSemaphore.ts`-backed gate, scoped to `provider === "nvidia"`) times out during specifically this credential-refresh retry, the client receives the stale 401 instead of a 429/`account_semaphore_capacity`, and no failover is attempted for that attempt — the request simply reports "unauthorized" when the real cause was capacity. This is flagged as a known, separate, lower-priority defect; fixing it is out of scope for this crash-focused design (see "No change to... chatCore.ts" in Proposed Fix item 3, which this finding does not override — none of these three sites justify a chatCore.ts change for the crash fix itself) but is noted here explicitly rather than silently omitted from the audit, since the audit's completeness claim depends on this category being enumerated.

    None of these three sites can produce an uncaught/crash-level rejection — all three terminate in a local catch before reaching the module boundary — so this finding does not change the design's bottom-line recommendation (crash-guard fix + diagnostic listener, no `chatCore.ts` change). What it does change is the completeness claim: the audit above is exhaustive for `executeProviderRequest`/`runNonStreamingProviderLeg` call sites specifically, and separately exhaustive (as of this revision) for direct `executor.execute()` call sites, but these are two different call-site categories and neither one's exhaustiveness implies the other's.

**Conclusion**: for the account-semaphore acquisition path quoted in the incident, chatCore already produces a clean 429 that already fails over past the GLM target to the 4070ti target through the combo's normal priority order. No code change is needed on this specific path to achieve the behavior the incident brief wants.

## Why the incident still crashed the process — re-scoping the investigation

Given the above, the uncaught `SEMAPHORE_TIMEOUT` that killed the pod in the incident log did **not** come from the single account-semaphore acquisition this investigation initially assumed. The stack trace quoted in the incident (`file:///app/httpClientAbortGuard.mjs:289`, `Timeout.<anonymous>`, `listOnTimeout`) is the **process-level `uncaughtException` re-throw**, not the original throw site — `httpClientAbortGuard.mjs:282-290`'s `process.on("uncaughtException", (err, origin) => { if (shouldSwallowUncaught(err, origin)) {...; return;} throw err; })` deliberately re-throws anything `shouldSwallowUncaught` does not recognize, on a _fresh_ stack, which is why the visible frames are the guard's own `throw err` line and Node's timer internals rather than `accountSemaphore.ts`'s `acquireMany`. This is **consistent with** an unhandled rejection from a promise that was never attached to any awaited chain — matching the general shape of the brief's own hypothesis about a `setTimeout` reject firing into a promise chain nobody is holding — but this is a hypothesis supported by circumstantial evidence (the stack-frame shape matches a known `setTimeout`-orphan pattern seen elsewhere in this codebase, see the `hedge-cancelled` precedent below), not a demonstrated fact: the exact leak site is not identified by this design (see Open Question 1), and no reproduction of the crash was attempted (see Open Question 4). What IS directly confirmed is narrower: the account-semaphore `setTimeout` reject (accountSemaphore.ts:306-312) rejects the SAME promise `acquireMany()` returned to its caller (`new Promise((resolve, reject) => { request.timer = setTimeout(() => {...; reject(...); ...}, timeoutMs); ... })`), and that promise IS awaited (chatCore.ts:3205 `await acquireConcurrencyGates(...)`) — so there is no separate orphaned promise in this one, specific acquisition call, as coded on this branch. That narrower, source-verified fact is what rules out "the main `chatCore.ts:3205` acquisition call is itself the leak" — it does not by itself prove where the real leak is, or even that an orphaned-`setTimeout`-promise is the correct general theory rather than, say, a detached `.then()`/listener registered elsewhere on an otherwise-safe promise (a distinct failure mode, discussed in Risk bullet 2 and Open Question 1 below). This leaves three concrete possibilities, listed in priority order of likelihood given the evidence gathered — none of them independently confirmed, each evaluated below for whether it is ruled out, narrowed, or still open:

1. **A different semaphore/timeout implementation threw the SAME error shape.** `open-sse/services/rateLimitSemaphore.ts:169-176` throws an error with an _almost_ identical message (`` `Semaphore timeout after ${timeoutMs}ms for ${modelStr}` ``, code `SEMAPHORE_TIMEOUT`) from its own `setTimeout` callback (line 162-176), used by `roundRobinCombo.ts:599` (combo round-robin dispatch) and `quotaShareConcurrency.ts:58` (quota-share dispatch) — **neither of which is `pool/tier1/code`'s strategy** (confirmed `priority` strategy per the tier1-priority findings), so this is unlikely to be the direct culprit for _this_ combo, but the incident log's phrase "single connection, no fallback account" and "maxConcurrent:1" matches the account-semaphore's per-connection cap wording more than round-robin's per-model cap wording — this reinforces (rather than contradicts) that `accountSemaphore.ts` is the right file, but the specific _call site_ that leaked may not be the main `chatCore.ts:3205` one profiled above. `nvidiaConcurrencyGate.ts:38` (`semaphore.acquire` from `rateLimitSemaphore.ts`, called from `default.ts:1155`'s `execute()`, itself awaited inside the SAME `try { ... } finally { releaseNvidiaSlot?.(); }` at `default.ts:1158-1162` — a rejection here propagates out of `executor.execute()` and into whichever of `chatCore.ts`'s already-guarded call sites invoked it, not around them) is a second, unrelated consumer scoped to `provider === "nvidia"` only — not relevant to a llama-cpp target, ruled out. A third consumer, `src/sse/services/codexWsLease.ts:16`'s `acquireCodexWsLease` (calling `accountSemaphore.ts`'s `acquire`/`acquireMany` directly, for the Codex WS-bridge lease, entirely outside `chatCore.ts`), is also ruled out: it passes `failFast: true` (never arms the `setTimeout`, so `SEMAPHORE_TIMEOUT` cannot fire from this call at all — only a synchronous `SEMAPHORE_QUEUE_FULL`-shaped rejection from `findQueueRejection` is possible) and wraps the call in an unconditional `catch { return null; }`. A repo-wide grep for every live caller of `accountSemaphore.ts`'s `acquire`/`acquireMany` (excluding tests) confirms exactly two call sites exist — `chatCore.ts:3205` and `codexWsLease.ts:16` — so this is now an exhaustive, not partial, enumeration of that function's callers.
2. **A `SEMAPHORE_TIMEOUT` rejection reached one of the few `executeProviderRequest`/`runNonStreamingProviderLeg` call sites that is NOT inside the two guarded top-level try/catch blocks.** `executeProviderRequest` is called from 7 sites in `chatCore.ts` (lines 4244, 4705, 4823, 4916, 5123, 5138, 5312). **Of the three sites inside `providerFailure:`'s fallback blocks, only two (4823, 4916) are locally guarded; the third (4705) is not, and this was a factual error in an earlier pass of this design, corrected here after direct re-verification against the branch's AST.**
    - **4823 and 4916 ARE each individually wrapped** in their own local `try { ... } catch { ... return createErrorResult(...); }` — AST-confirmed `tryBlock: 4822-4860` / `catchClause: 4860-4879` and `tryBlock: 4915-4952` / `catchClause: 4952-4971` respectively. Both catches unconditionally swallow and convert to the ORIGINAL error's status/message without re-checking `isSemaphoreCapacityError`, but they also do not re-throw, so a `SEMAPHORE_TIMEOUT` hitting either of these two fallback-retry sites is silently absorbed into a plain `createErrorResult(statusCode, errMsg, ...)` using the _stale_ status/message from the FIRST failure — a correctness bug (wrong status code surfaced), not a crash.
    - **4705 is NOT locally guarded — this is a real, confirmed, non-hypothetical leak candidate, not a safe path.** AST verification shows the only `try` statement whose range contains line 4705 is the single outer `try { ... } finally { ... }` wrapping the entire `handleChatCoreInner` body (lines 789-6431); that statement has **no `catch` clause at all**. The call sits inside `recoverAnthropicThinkingSignature`'s `execute` callback (chatCore.ts:4696-4707, the Anthropic thinking-signature-recovery retry triggered by `isAnthropicThinkingSignatureError`), and neither `recoverAnthropicThinkingSignature` (`thinkingSignatureRecovery.ts`) nor `executeWithAnthropicThinkingSignatureRecovery` (`passthroughHelpers.ts`) contains any `try`/`catch` of its own (grepped both files for `try {`, zero matches). A `SEMAPHORE_TIMEOUT`-coded rejection from `executeProviderRequest(currentModel, false)` at this site therefore propagates, confirmed by direct read at every hop: out of the unguarded `recoverAnthropicThinkingSignature` call; out of the 789-6431 `try`/`finally` (the `finally` runs but does not catch); out of `handleChatCoreInner`/`handleChatCore`; out of `chatHelpers.ts`'s `executeChatWithBreaker`, whose catch (`chatHelpers.ts:658-685`) only recognizes `CircuitBreakerOpenError` and `PROXY_UNREACHABLE`/`proxy unreachable`-message errors and ends in an unconditional `throw cbErr;` (confirmed, line 685) for anything else; out of `chatDispatch.ts`'s `dispatchChatWithAffinityEviction`, whose catch (`chatDispatch.ts:61-63`) unconditionally evicts and `throw dispatchErr;`s; out of `chat.ts`'s own wrapping try, whose catch (`chat.ts:2045-2049`) unconditionally releases the OAuth session/lease and `throw error;`s; and finally out of `chatAdmission.ts`'s exported `withChatAdmission` catch (`chatAdmission.ts:334-344`), which releases the admission lease via `releaseHandlerFailure` and unconditionally `throw err;`s. At no point in this chain does any catch recognize `SEMAPHORE_TIMEOUT`/`SEMAPHORE_QUEUE_FULL` the way the two guarded chatCore.ts blocks (4148-4456, 5025-5825) do, so this rejection reaches the module boundary uncaught — a request-scoped `unhandledRejection`/thrown error from the route handler, reachable without any combo or tool-loop involvement: any single-model Claude/anthropic-compatible-\* request that returns the specific "invalid signature in thinking block" 400 and then re-fails with `SEMAPHORE_TIMEOUT` on the recovery retry hits this exact path. (Whether this specific uncaught rejection, once it reaches the Next.js route-handler layer, always becomes a process-level `uncaughtException`/`unhandledRejection` versus being caught first by Next's own request-handling machinery was not traced to that final layer in this pass — see Open Question 1a — but regardless of that outcome, the design's prior claim that this site was "individually wrapped" like 4823/4916 was simply wrong, and is corrected here.)
    - The line-5312 site is inside `followUpLegInput`'s `runNonStreamingProviderLeg` call for the server-owned-tool-loop follow-up leg (`phase: "follow-up"`) — this goes through the SAME `runNonStreamingProviderLeg` guarded re-throw (nonStreamingProviderLeg.ts:475-483) and is awaited inside `continueServerOwnedToolLoop`'s `resumeUpstream` (serverOwnedToolLoopWire.ts:57-73), which is awaited inside `runServerOwnedToolLoop`'s main loop (`src/lib/skills/serverOwnedToolLoop.ts:412` `const nextLeg = await options.resumeUpstream(...)` — re-verified against the branch's current source; an earlier pass of this design cited line 333, which was stale), which is awaited inside `applyServerOwnedToolLoopIfNeeded` (serverOwnedToolLoopWire.ts:153 `const loop = await continueServerOwnedToolLoop({...})`), which IS inside the chatCore.ts:5024 outer try (confirmed: `applyServerOwnedToolLoopIfNeeded` is called from chatCore.ts:5255, strictly between the try at 5025 and its catch at 5792) — so this path is also covered, assuming no listener leak inside the tool-loop chain (unverified, see below).

**A fourth call site, outside `chatCore.ts` entirely, was found on this verification pass and was NOT enumerated by the original design: `src/sse/services/codexWsLease.ts:16`'s `acquireCodexWsLease` calls `acquireAccountSemaphore` (the `acquire` export, which internally delegates to the same `acquireMany` throw site) directly, for the Codex WebSocket-bridge lease path — a code path with no relation to `chatCore.ts`'s HTTP request/response flow at all.** This call site IS safe, but for a different reason than the chatCore sites: it passes `failFast: true`, so it never reaches the `setTimeout`/`SEMAPHORE_TIMEOUT` branch in the first place (it rejects synchronously via `findQueueRejection` inside `acquireMany`, before any timer is armed, whenever the slot isn't free), and the call is wrapped in a bare `try { ... } catch { return null; }` that swallows any rejection shape unconditionally, timeout-coded or not. This closes a gap in the original design, which only audited `executeProviderRequest`/`runNonStreamingProviderLeg` callers inside `chatCore.ts` and did not search for _other importers_ of `accountSemaphore.ts`'s `acquire`/`acquireMany` exports elsewhere in the codebase. A full-repo grep (`acquireAccountSemaphore\|acquireConcurrencyGates\|accountSemaphore\.acquire\b`, excluding tests) found exactly these two live call sites — `chatCore.ts:3205` and `codexWsLease.ts:16` — and no others; both are now confirmed safe. 3. **A listener-leak pattern of the exact class `httpClientAbortGuard.mjs`'s own docstring already documents fixing twice** (`#fix-dev-server-aborted`, `#12861`, `#13636`): a secondary `.catch()`/`.then()`/event-listener attached to the SAME semaphore-timeout rejection, registered somewhere in the combo/tool-loop plumbing, that is never cleaned up when the primary awaiter already handled it, and whose independent rejection path has no handler. The guard's docstring explicitly describes this exact failure mode for `hedge-cancelled` (`upstreamTimeouts.ts::executeWithUpstreamStartTimeout`, fixed in commit `706dc75c1`) and for undici fetch failures — i.e., this general bug CLASS has recurred twice already in this codebase for _other_ error reasons, and `SEMAPHORE_TIMEOUT` is not yet in `httpClientAbortGuard.mjs`'s recognized swallow-list (`isClientAbortError`, `isRecoverableUpstreamTimeoutError`, `isIntentionalComboAbort`, `isUpstreamNetworkError` — none match `code === "SEMAPHORE_TIMEOUT"`), so if a `SEMAPHORE_TIMEOUT` rejection ever does leak to `uncaughtException`/`unhandledRejection` through ANY path, it will NOT be swallowed and WILL crash the process exactly as the incident shows.

**This third possibility is the one the proposed fix must close, because it is the only one that explains an actually-uncaught `SEMAPHORE_TIMEOUT` given everything traced above, and it is a change category (recognizing an existing coded error class in the crash guard's swallow-list) with low risk and a precedent (two prior commits did exactly this for other error reasons).**

## Proposed fix

**Do not add a new catch anywhere in `chatCore.ts`** — the account-semaphore acquisition path already has correct containment (sections above), and adding a redundant catch risks masking the real leak instead of fixing it. Instead:

1. **Primary fix — close the crash-guard gap**: add `SEMAPHORE_TIMEOUT` and `SEMAPHORE_QUEUE_FULL` to `src/shared/utils/httpClientAbortGuard.mjs`'s recognized-swallow set, as a new `isSemaphoreCapacityTimeoutError(err)` predicate (mirroring the existing `isClientAbortError`/`isIntentionalComboAbort` shape: a plain function matching `err.code === "SEMAPHORE_TIMEOUT" || err.code === "SEMAPHORE_QUEUE_FULL"`, checked only via the `.code` property on the error object — unlike the combo-abort reasons, there is no bare-string-reason case to additionally match, since `createSemaphoreError` in `accountSemaphore.ts` always produces `new Error(message)` with `.code` set, so a `.code`-only check is sufficient; an earlier pass of this design claimed "both message and bare-code-on-object checked," which overstated what the sketched implementation actually does — corrected here to match the code), wired into `shouldSwallowUncaught`'s `if (!isClientAbortError(err) && !isRecoverableUpstreamTimeoutError(err) && !isIntentionalComboAbort(err) && !isUpstreamNetworkError(err))` condition. This is a **last-resort safety net**, not the primary fix for correctness — see item 2 — but it directly stops the exact crash the incident describes regardless of which exact code path leaked the rejection, consistent with every prior fix to this same guard file. Rationale for doing this even though it does not fix the underlying leak: `httpClientAbortGuard.mjs`'s own documented purpose is precisely "recoverable runtime/environmental conditions the request layer already handles; neither is process-fatal" — `SEMAPHORE_TIMEOUT`/`SEMAPHORE_QUEUE_FULL` are _by definition_ already-handled-elsewhere conditions (proven in the Evidence section above for every path chatCore.ts controls), so if one still reaches process level, it is logically the same "already handled it in principle, but a stray duplicate rejection escaped" class this guard exists for.
2. **Diagnostic fix — find and fix the actual leak, by instrumentation, not guesswork**: add a ring-buffer diagnostic listener for `SEMAPHORE_TIMEOUT`/`SEMAPHORE_QUEUE_FULL` unhandled rejections, mirroring the EXACT existing pattern in `open-sse/services/combo/targetTimeoutRunner.ts:60-91` (`ensureDiagnosticListener`/`recordTimeoutContext`/`drainLastTimeoutContexts`) — that pattern already solves "the next production incident is diagnosable" for `combo-per-model-timeout`, and should be duplicated (not generalized/shared — the two timeout classes have different context shapes) for the semaphore case: a module-scoped `process.on("unhandledRejection", ...)` in `accountSemaphore.ts` (or a new small sibling file, to avoid growing that file's lint-suppression surface — see AGENTS.md note on `eslint-suppressions.json`) that recognizes `reason.code === "SEMAPHORE_TIMEOUT"`, logs the full stack plus the key(s) involved (available from the error message's `for ${keys.join(",")}` suffix) via `console.error`, and keeps a small ring buffer so the stack trace of the true orphaned-promise call site is captured in the next incident's logs instead of only the generic `Timeout.<anonymous>` frame the guard's re-throw currently produces. This buys the next production occurrence (which the crash-guard fix in item 1 will have converted from "crash" to "swallowed and logged") a real, attributable stack trace, so the actual orphaned-promise call site (one of the three candidates named above, or a fourth not yet identified) can be fixed with certainty instead of inferred.
3. **No change to `accountSemaphore.ts`, `rateLimitSemaphore.ts`, `chatCore.ts`, or the combo attempt loop** is proposed. Every call site that owns a semaphore-timeout rejection today already awaits it inside a guarded try, confirmed above; the fix belongs entirely in the crash-safety-net layer (`httpClientAbortGuard.mjs`) plus the diagnostic layer, not in request-handling logic. This also respects the setup.md exclusion list — none of the four reserved files (`reasoningEffort.ts`, `targetRequestSanitizer.ts`/`BaseExecutor.execute()`, `modelCapabilityOverrides.ts`, `check-provider-consistency.ts`) are touched by either change.

### Exact fix shape

In `src/shared/utils/httpClientAbortGuard.mjs`, add alongside the existing exported predicates:

```js
/**
 * A local admission-semaphore rejection (#<incident-id>): accountSemaphore.ts's
 * acquireMany() times a queued waiter out via setTimeout and rejects with a
 * coded Error (never a bare string). Every *known-guarded* chatCore.ts call
 * site converts it to a normal 429 — see isSemaphoreCapacityError in
 * handlers/chatCore/streamErrorResult.ts — but at least one call site (the
 * Anthropic thinking-signature-recovery retry, chatCore.ts:4705) does NOT,
 * and propagates it uncaught through the request-dispatch chain up to the
 * route handler. This predicate exists specifically because that gap, and
 * possibly others not yet found, means a stray SEMAPHORE_TIMEOUT/
 * SEMAPHORE_QUEUE_FULL can still reach process level. Swallow it rather than
 * crash, matching the already-handled-elsewhere contract this guard exists
 * for (see module docstring).
 */
export function isSemaphoreCapacityTimeoutError(err) {
	if (!err || typeof err !== "object") return false
	const e = /** @type {NodeJS.ErrnoException} */ (err)
	return e.code === "SEMAPHORE_TIMEOUT" || e.code === "SEMAPHORE_QUEUE_FULL"
}
```

...and in `shouldSwallowUncaught`:

```js
if (
	!isClientAbortError(err) &&
	!isRecoverableUpstreamTimeoutError(err) &&
	!isIntentionalComboAbort(err) &&
	!isUpstreamNetworkError(err) &&
	!isSemaphoreCapacityTimeoutError(err)
) {
	return false
}
```

In `open-sse/services/accountSemaphore.ts`, mirroring `targetTimeoutRunner.ts`'s pattern, add a module-scoped diagnostic (sketch; exact ring size/format to match the existing pattern's 4-entry ring):

```ts
let semaphoreDiagnosticInstalled = false
function ensureSemaphoreDiagnosticListener(): void {
	if (semaphoreDiagnosticInstalled) return
	semaphoreDiagnosticInstalled = true
	process.on("unhandledRejection", (reason: unknown) => {
		const isSemaphoreTimeout =
			reason instanceof Error && (reason as Error & { code?: string }).code === "SEMAPHORE_TIMEOUT"
		if (!isSemaphoreTimeout) return
		console.error(
			"[SEMAPHORE-TIMEOUT-DIAGNOSTIC] unhandledRejection from accountSemaphore.ts.\n" +
				`  message: ${reason.message}\n` +
				`  stack: ${reason.stack}`,
		)
	})
}
```

Call site, decided (not left open): `targetTimeoutRunner.ts`'s precedent calls `ensureDiagnosticListener()` once from inside `buildTargetTimeoutRunner` (confirmed at `targetTimeoutRunner.ts:105`), a factory invoked once per combo-runner construction — `accountSemaphore.ts` has no equivalent factory (`acquireMany` is a plain top-level exported function, called directly on every request, not built once per combo), so mirroring "call it from the nearest one-time construction point" means calling `ensureSemaphoreDiagnosticListener()` as a bare top-level statement in `accountSemaphore.ts`'s module body (next to the existing `const gates = new Map(...)` / `const queuedRequests = new Set(...)` module-scope initializers), not from inside `acquireMany` itself. Module evaluation happens exactly once per process under Node's ESM/CJS module cache, so a bare top-level call never re-enters this function in normal operation — the `if (semaphoreDiagnosticInstalled) return;` guard inside it is therefore NOT a per-call hot-path optimization (there is no hot-path call to optimize away, since nothing calls this function more than once in the module-eval case). Its actual purpose, consistent with `targetTimeoutRunner.ts`'s own identically-shaped guard, is defense against double module instantiation — e.g. a CJS/ESM dual-load of the same file under two different module identities (a scenario this codebase explicitly guards against elsewhere, per `httpClientAbortGuard.mjs`'s own "build-free" docstring constraint) — which would otherwise register the `process.on("unhandledRejection", ...)` listener twice and double-log every diagnostic line. Keep the guard; the earlier "avoids a per-call hot-path check" framing is removed because it mischaracterized a module-eval-time call as if it were per-request.

## Before/after trace

**Before** (what the incident shows): `acquireMany`'s `setTimeout` rejects a promise with code `SEMAPHORE_TIMEOUT` → the rejection reaches `uncaughtException`/`unhandledRejection` from a call site not yet pinpointed (candidates in "Why the incident still crashed" above) → `httpClientAbortGuard.mjs`'s `shouldSwallowUncaught` does not recognize the error (no matching predicate) → `process.on("uncaughtException", (err, origin) => { ...; throw err; })` re-throws on a fresh stack → Node terminates the process (exit code 7, confirmed by `kubectl describe pod`) → every in-flight request across every lane fails during the crash+restart window.

**After**: the SAME orphaned rejection (whichever call site produces it — not yet fixed at the source by this design, see Open Questions) now matches `isSemaphoreCapacityTimeoutError` → `shouldSwallowUncaught` returns `true` → the guard logs `"[server] swallowed benign uncaughtException:"` plus the full error (preserving the stack) via `logger("warn", ...)` and returns WITHOUT re-throwing → the process stays alive → the diagnostic listener in `accountSemaphore.ts` (installed independently, fires on the same `unhandledRejection` event) logs the attributable stack trace with the full key list → the NEXT iteration of this investigation (not blocked on reproducing a crash) can read that stack and fix the true leak at its source, after which the diagnostic log — and eventually the crash-guard entry, once the leak is proven gone and verified absent for a full release cycle — can be removed.

**For the specific, VERIFIED-SAFE account-semaphore path this investigation traced in full** (chatCore.ts:3205's acquisition, both streaming and non-streaming legs): the before/after is unchanged by this fix, because that path never reaches the crash guard today — it already resolves as a normal 429 → `account_semaphore_capacity` → chat.ts's `requestAttemptLoop` continue (unpinned) or combo fallthrough (pinned, like `pool/tier1/code`'s GLM step) → next target in priority order (4070ti) attempted, exactly the "5090 → m5max → 4070ti" chain the incident brief asks the fix to preserve. This chain is NOT touched by either proposed change.

## Risks

- **Risk: masking a real bug instead of fixing it.** Adding `SEMAPHORE_TIMEOUT` to the crash-guard swallow-list converts a crash into a silent (well, `console.warn`-logged) no-op for the specific request that leaked. If the underlying leak is frequent (not a rare race, but a systematic missing-await), this could mask request-level data loss (a client that was waiting on that promise now gets... nothing, since the guard operates at the process level, not the request level) instead of surfacing it as a crash that forces investigation. Mitigation: item 2 (the diagnostic listener) is not optional — ship both together, and treat the diagnostic's first production log line as a P1 follow-up to find and fix the true leak, not as "done."
- **Risk: the leak candidates are only partially resolved, and one of them is no longer merely hypothetical — it is a confirmed, reachable gap.** This revision re-read `rateLimitSemaphore.ts`'s two consumers in full: `roundRobinCombo.ts:596-612` locally catches and `continue`s past `SEMAPHORE_TIMEOUT`/`SEMAPHORE_QUEUE_FULL`, and `quotaShareConcurrency.ts:60-70` locally catches and fails open — both are confirmed safe containment, not unverified, downgrading that candidate. The server-owned-tool-loop follow-up leg's full call depth was traced end to end this pass (`chatCore.ts:5312` → `nonStreamingProviderLeg.ts`'s rethrow → `serverOwnedToolLoopWire.ts:60-73`'s `resumeUpstream` → `src/lib/skills/serverOwnedToolLoop.ts:412`'s `await options.resumeUpstream(...)` → `serverOwnedToolLoopWire.ts:153` → `chatCore.ts:5255`, strictly inside the 5025-5792 guarded try) and found no gap — every `await` in that chain is a direct, unbroken await of its immediate caller's promise, so there is no point where a `.then()`/listener could detach from the awaiting chain. **However, this revision also corrected a prior factual error: the chatCore.ts:4705 Anthropic thinking-signature-recovery retry site is NOT locally guarded** (see "Why the incident still crashed" possibility #2, revised above) — it propagates an uncaught rejection through `chatHelpers.ts`/`chatDispatch.ts`/`chat.ts`/`chatAdmission.ts`'s unconditional-rethrow chain, reachable by any Claude/anthropic-compatible-* request that re-fails with `SEMAPHORE_TIMEOUT` on this specific retry — a concrete, reproducible path, not a residual theoretical gap like the detached-listener class. This is a materially different risk than "a leak inside a verified-intact chain cannot be ruled out by static reading alone": the 4705 site's lack of containment IS visible to static reading, and was simply mis-described in an earlier pass of this document. The crash-guard fix (item 1) still closes it, because `isSemaphoreCapacityTimeoutError` matches on `.code` regardless of which call site produced the rejection — but the diagnostic listener (item 2) is now expected to fire on a *known\*, not merely suspected, trigger (a reproducible thinking-signature-recovery-retry timeout), in addition to any still-unidentified detached-listener leak. The residual, genuinely-unconfirmed-by-static-reading gap is now narrower than before this revision but is not reduced to zero: a leak inside the verified-intact tool-loop await chain, or inside the now-corrected 4705 path's own downstream handling, still cannot be ruled out purely by eye (an await chain traced by eye can still miss a detached `.catch()` registered elsewhere, e.g. telemetry/logging code reading the same promise) — closed by the diagnostic listener, not by further static tracing. If a FUTURE combo adds a new `rateLimitSemaphore.ts` consumer without copying its two siblings' catch/convert pattern, that new call site would need the same two-part fix; `isSemaphoreCapacityTimeoutError`'s `.code`-only match (sketched above) already covers it without changes, since `rateLimitSemaphore.ts` and `accountSemaphore.ts` set `.code` identically despite their slightly different message formats.
- **Risk: no automated regression test can prove "no more crashes" directly.** The existing `httpClientAbortGuard.test.mjs` and `httpClientAbortGuard-default-logger.test.mjs` suites test `shouldSwallowUncaught`/`isClientAbortError` etc. as pure functions — adding `isSemaphoreCapacityTimeoutError` tests there (unit-level: `assert.equal(isSemaphoreCapacityTimeoutError({code: "SEMAPHORE_TIMEOUT"}), true)` and the `shouldSwallowUncaught` integration case) is straightforward and should be added, but it only proves the guard _recognizes_ the error shape — it cannot prove the orphaned-promise leak stops recurring, since that requires reproducing the actual leak (not yet pinpointed). This is an accepted limitation per the Test Placement Guidance in AGENTS.md: add the regression test at the lowest layer that would have caught the bug (the guard's classification function), and rely on the diagnostic listener's production log for the layer this design cannot reach in a unit test.
