# Design: local-model-proxy coexistence rework (GLM-5.3 + Uzu resident concurrently)

Primary file: `/Users/celes/sources/m5max-darwin-flake/.worktrees/proxy-coexistence/packages/local-model-proxy/model_proxy.py` (async aiohttp OpenAI-compatible proxy, 21317 bytes at design time).
Config file: `.../packages/local-model-proxy/models.json` (key `backends`; `$UID` in `service` expanded by `load_config()`).
Scope note: `index.js` in the same package is a *separate, older* Node implementation using config key `chat`; it is **not** the deploy target and is out of scope. All design decisions below concern the Python proxy only.

## Reconciliation with the task brief's "CURRENT behavior" (read the real file first)

The task brief's "CURRENT behavior" section describes an `acquire_backend()`/`QUEUE_TIMEOUT`/`_gen_event`-drain/`reconcile_launchctl_backends`/`launchctl_is_running` machine. **That machinery does not exist in the file on disk.** A full read of `model_proxy.py` plus a grep for `acquire_backend|reconcile_launchctl|launchctl_is_running|_gen_event|QUEUE_TIMEOUT` returns **zero matches** for all of those except the bare `_gen_event` *attribute*, which is created and `.set()` once in `ProxyState.__init__` and then **never awaited, cleared, or read anywhere** — it is dead code. The real current behavior is simpler and is what this design must transform:

- `ProxyState` (model_proxy.py ~L58-91) holds: `active_backend: str | None`, `switching: bool`, `generating: int` (a single global in-flight counter, not per-alias), `last_used: dict[str,float]`, `_lock: asyncio.Lock`, `_gen_event: asyncio.Event` (dead), and `backend_for_model()` (direct-key match, then `model_names` scan, else `None`).
- Each handler (`handle_chat_completions` ~L300, `handle_responses` ~L360, `handle_messages` ~L420, `handle_completions` ~L480; plus `handle_v1_catchall`) resolves the alias, falls back to `active_backend`, then does `async with state._lock: await activate_backend(alias)`, releases the lock, increments `state.generating`, forwards the request, and in `finally` decrements `generating` and stamps `last_used`.
- `activate_backend(alias)` (~L170): if `active_backend == alias` returns; else, if `active_backend` set, `await deactivate_backend(active_backend)` **immediately with no drain** (this is a real pre-existing bug the task's "drain-before-stop safety" claim assumes is already present — it is not; this design *adds* it), sets `switching=True`, then `launchctl_start` + `health_wait` (launchctl) or `ollama_load_model` + `health_wait` (ollama); on success sets `active_backend=alias`; on any exception sets `active_backend=None` and re-raises; `finally` clears `switching`.
- `deactivate_backend(alias)` (~L205): `launchctl_stop` + `sleep(1.0)` for launchctl, or `ollama_unload_model` + `sleep(0.5)` for ollama; wraps the stop in a broad `try/except` that only **logs** a warning (it does **not** re-raise on failed stop — another divergence from the brief; this design changes it to re-raise for launchctl stops so eviction cannot silently proceed over a live process). Clears `active_backend` if it matched; pops `last_used`.
- Error mapping today: `aiohttp.ClientError` → `502`; a `health_wait`/`launchctl` `RuntimeError` propagates out of the `async with state._lock` block, is **not** caught by the handler (whose `try` starts *after* the lock block), and surfaces as aiohttp's default unstructured `500`. `asyncio.TimeoutError` is **not** caught anywhere (no queue/drain timeout exists yet).

The brief told us the file "may have evolved"; it has *regressed from the brief's mental model*. This design is written against the on-disk reality and explicitly rebuilds the drain machinery the brief assumed, rather than editing a drain path that isn't there.

Also: **`qwen38-uzu` is not in `models.json`.** The config has `qwen38-mlx` (:8070), `glm53` (:8082), `deepseek-v41-uncensored` (:8084), and `qwen35-reader-262k` (ollama). Adding the Uzu backend entry (alias `qwen38-uzu`, service `gui/$UID/com.celes.uzu-server`, :8073) is part of this change.

## Summary and chosen approach

Replace the single-`active_backend`/single-`generating`-counter model with a **resident-set model keyed by launchctl alias**, where each resident alias carries its own in-flight generation counter and its own drain event. Two aliases — `glm53` and `qwen38-uzu` — are tagged **coexistence** and are allowed to be resident simultaneously; every other launchctl alias is **exclusive** and, when requested, evicts the entire resident set (both coexistence backends and any other exclusive backend) before starting solo. Ollama/non-launchctl backends are untracked and unaffected.

The core concurrency decision — and the hardest part — is the **lock discipline**: the single `_lock` must serialize *decisions about the resident set and its transitions*, but must **not** be held across the long `health_wait` of a cold start, or across request forwarding, because doing so would serialize an independent coexistence backend behind the other's cold start. The design achieves this with a short critical section that mutates intent (per-alias "state": `STARTING`/`RESIDENT`/`DRAINING`/`STOPPING`) plus **per-alias `asyncio.Event`s** that let a waiter sleep on *exactly* the transition it needs (a specific alias becoming `RESIDENT`, or a specific alias finishing drain) without holding `_lock`. The lock is reacquired only to re-check and commit the next step. This is the standard "lock guards the state machine; await happens outside the lock; events signal completion" pattern, applied per alias so independent aliases never share a wait.

Technology stack is **locked**: Python 3.11+ asyncio + aiohttp (unchanged — same imports already in the file), `launchctl kickstart -k` / `launchctl kill SIGTERM` via `asyncio.create_subprocess_exec` (unchanged), `models.json` as config. No new third-party dependencies. Backend classification is **data-driven via a new `"coexist": true` field in each `models.json` backend entry**, parsed in `load_config()` into a derived set on `ProxyState` — chosen over a hardcoded module constant because the config is already the single source of truth for backend topology, the field is additive and backward-compatible (absent ⇒ `false` ⇒ exclusive, preserving today's behavior for `qwen38-mlx`/`deepseek-v41-uncensored`), and it keeps the two primary aliases (`glm53`, `qwen38-uzu`) from being special-cased in code where they could drift from config. A module-level fallback constant `DEFAULT_COEXIST_ALIASES = frozenset({"glm53", "qwen38-uzu"})` is retained as a defensive default, with a **per-entry, not all-or-nothing** trigger rule (finding 8) to avoid a silent half-migration regression:

- `coexist` is read **per entry**: a backend that carries `"coexist": true` is coexistence; a backend that omits the field is exclusive (absent ⇒ `false`). The config wins per entry.
- The `DEFAULT_COEXIST_ALIASES` fallback is applied **only when zero entries in the entire loaded config declare `"coexist"` at all** (a fully un-migrated config on an older deploy) — in that case the two named aliases are forced into the coexistence set, with a startup `log.warning`.
- Crucially, the fallback is **not** disabled merely because *one* entry declared the field. A config where only `glm53` carries `coexist: true` and `qwen38-uzu` was deployed without it is a **partial migration**: `coexist` is still read per entry (so Uzu would resolve to exclusive), but to make that dangerous state loud rather than silent, after parsing, **if `glm53` or `qwen38-uzu` resolves to exclusive, emit a `log.warning` naming the alias** ("coexistence backend <alias> is not tagged coexist; the GLM/Uzu pair will not co-reside — check models.json"). This keeps config-as-source-of-truth while turning the exact regression the constant guards against (the pair silently never coexisting) into a visible warning instead of a swallowed misconfiguration.

This avoids both a silent regression to swap-everything behavior if the config is deployed a step behind the code *and* a silent half-migration where only one of the pair is tagged.

## Data model: the new `ProxyState`

Replace the three fields `active_backend`/`switching`/`generating` with a per-alias residency map. Keep `config`, `backends`, `backend_for_model`, `last_used`, and `_lock`. Drop the dead `_gen_event`.

Per-alias record (one dataclass instance per **launchctl** alias that is or is becoming resident; ollama aliases never get a record):

- `alias: str`
- `state: Literal["STARTING", "RESIDENT", "DRAINING", "STOPPING"]` — the authoritative lifecycle state. There is **no `ABSENT` literal** (finding 11 resolved): absence of the alias from `resident` is the sole representation of "not resident." A record exists in exactly one of the four live states for as long as it is a value in `resident`; the single teardown point is `del resident[alias]` under `_lock` (performed by whichever evictor/failed-start path owns the record — see below), and that same critical section sets `record.gone`.
- `generating: int` — in-flight forwarded requests *for this alias only*. Replaces the global counter.
- `ready: asyncio.Event` — set when `state == RESIDENT`; cleared while `STARTING`/`DRAINING`/`STOPPING`. Waiters that need this alias up `await record.ready.wait()`.
- `drained: asyncio.Event` — set when `generating == 0`; cleared when a request increments the counter. Evictors `await record.drained.wait()` (with timeout) before stopping.
- `gone: asyncio.Event` — **set exactly once**, under `_lock`, by the code path that removes this record from `resident` (successful stop, or failed-start cleanup). Waiters that observed this record in `DRAINING`/`STOPPING` and must wait for the eviction to fully complete park on `gone` (finding 1). It is the unambiguous "this specific record instance is now torn down; the map key is free" signal, distinct from `drained` (which fires mid-drain, before the stop) and `ready` (which is never set again on a record headed for teardown).
- `start_error: BaseException | None` — the exception from the most recent failed start, read by waiters that were parked on `ready` so a cold-start failure propagates to *all* waiters as a structured error rather than hanging.

A record's identity is the dataclass **instance**, not its alias key. Re-requesting an alias that is being evicted creates a *new* instance under the same key once the old one's `gone` fires and it has been removed; the two instances are never confused because every commit re-validates instance identity (see the record-identity invariant in "Lock-hold boundaries").

`ProxyState` gains:

- `resident: dict[str, BackendRecord]` — alias → record, for every launchctl alias currently `STARTING`/`RESIDENT`/`DRAINING`/`STOPPING`. The set of keys with `state == RESIDENT` is "what is up right now."
- `coexist_aliases: frozenset[str]` — derived at load time from the `"coexist"` field (see above).
- `_lock: asyncio.Lock` — unchanged identity; **new, tighter discipline** (below).

Helper predicates on `ProxyState`: `is_coexist(alias) -> bool`, `is_launchctl(alias) -> bool` (type == `"launchctl"`), `exclusive_launchctl_aliases() -> set[str]` (all launchctl aliases not in `coexist_aliases`). `backend_for_model` is unchanged.

Rationale for per-alias `generating` + `drained`/`ready` events instead of one global counter: the whole point of the task is that a GLM request and a Uzu request are **independent**. A single global `generating` counter cannot express "GLM has 2 in flight, Uzu has 0, so Uzu may be evicted but GLM may not" — which is exactly what exclusive-eviction and the drain-before-stop rule require. Per-alias counters make the drain target precise and let the two coexistence backends' in-flight work be fully decoupled.

## Constants and timeouts (concrete values — finding 5)

All of the following are **module-level constants** in `model_proxy.py`, each overridable by an environment variable (consistent with the existing `PORT`/`HOST`/`CONFIG_PATH` pattern that already reads env vars with a default). Concrete defaults are chosen, not left to the implementer:

- `QUEUE_TIMEOUT = float(os.environ.get("LOCAL_MODEL_PROXY_QUEUE_TIMEOUT", "30.0"))` — seconds an evictor will wait for a victim's in-flight generations to drain (`drain_and_stop`) and the bound a re-requester waits on a record's `gone` event. On expiry the switch aborts with a fast structured `503 model_switch_queue_timeout` and the victim is **left running** (never force-killed mid-generation). 30s is long enough to let a short completion finish but short enough that a wedged generation does not hang a switch indefinitely.
- `DEFAULT_STARTUP_TIMEOUT = float(os.environ.get("LOCAL_MODEL_PROXY_STARTUP_TIMEOUT", "300.0"))` — default cold-start/health bound when a backend entry omits `startup_timeout`. Raised from `health_wait`'s historical 60s to **300s** because the heaviest coexistence backend (GLM ~67.6 GiB) can take well over 60s to answer health from cold; a 60s bound would 503 every normal GLM cold start (this is exactly the regression finding 4 flags). Per-backend `startup_timeout` in `models.json` overrides this (see below).
- `EXIT_CONFIRM_TIMEOUT = float(os.environ.get("LOCAL_MODEL_PROXY_EXIT_CONFIRM_TIMEOUT", "60.0"))` — bound on confirming a stopped launchctl process has actually exited (used by `deactivate_backend`'s confirmed-exit poll).
- `LAUNCHCTL_START_TIMEOUT = float(os.environ.get("LOCAL_MODEL_PROXY_LAUNCHCTL_START_TIMEOUT", "15.0"))` — the subprocess bound on the `launchctl kickstart -k` call in `launchctl_start` (finding iteration-4/2). This is the first half of a cold start's wall time; the second half is `health_wait(..., timeout=startup_timeout)`. The constant is **reused** as the kickstart subprocess timeout *and* added to a coalesced waiter's `ready.wait()` bound (`waiter_timeout = LAUNCHCTL_START_TIMEOUT + startup_timeout`) so a parked waiter can never time out before the starter's whole budget (`LAUNCHCTL_START_TIMEOUT + startup_timeout`) is exhausted. Defined once, here.
- `EXIT_POLL_INTERVAL = 0.5` — seconds between `launchctl print` polls during exit confirmation.
- `HEALTH_POLL_INTERVAL = 0.3` — unchanged from the current `health_wait` loop.
- `RETRY_AFTER_QUEUE_TIMEOUT = "2"` and `RETRY_AFTER_BACKEND_UNAVAILABLE = "5"` — concrete `Retry-After` header values (seconds, as strings) for the two 503 responses. A queue timeout clears as soon as the in-flight generation finishes, so a short 2s retry is appropriate; a `backend_unavailable` means a cold start/health failed and a retry forces another full cold start, so a longer 5s cadence avoids hammering a struggling backend.

### `startup_timeout` wiring (finding 4 — net-new behavior, called out explicitly)

The current `activate_backend` calls `health_wait(entry["health_url"])` with **no** timeout, so `health_wait`'s hardcoded 60s default is used and the `startup_timeout: 300` already present on `qwen38-mlx` is **silently ignored**. The new cold-start path **changes this**: it computes `timeout = entry.get("startup_timeout", DEFAULT_STARTUP_TIMEOUT)` and passes it to `health_wait(entry["health_url"], timeout=timeout)` and uses the same value as the `ready`-wait bound for coalesced waiters. Documented behavior changes this introduces:
- `qwen38-mlx`: effective cold-start bound goes 60s → 300s (its configured value is finally honored).
- `glm53` and the new `qwen38-uzu`: get an explicit `startup_timeout` added to their `models.json` entries (see "Files to modify") sized for their cold-load times, rather than inheriting a too-short bound.

## The acquire/evict state machine

A single new coroutine `acquire(alias) -> BackendRecord` replaces the handlers' `async with state._lock: await activate_backend(alias)` call. It returns once the requested backend is `RESIDENT` with this request's slot already counted (`generating` incremented and `drained` cleared), or raises a typed error. **Slot bookkeeping is bound to acquire *success*, not to the handler's `finally` (finding iteration-4/1).** `acquire` returns the record (or the Class-1 sentinel) only after it has counted the slot; on any failure it raises *without* having incremented. The `try/finally` that owns `release` therefore begins **after** `acquire` returns, so a raising `acquire` never reaches the `finally`:

```python
record = await state.acquire(alias)   # raises on failure -> no slot counted, no release owed
try:
    ... forward ...
finally:
    state.release(record)             # no-op for the Class-1 sentinel; decrements only a counted slot
```

The contract, stated unambiguously: **a `finally: release` must not run when `acquire` raised.** Because `release` is reached only on the success path, it can never decrement a counter that was never incremented (which would drive `generating` negative, corrupt the `drained` predicate, and — during an eviction — spuriously decrement a live *other* backend's counter).

Three classes, dispatched on `alias`:

### Class 1 — ollama / non-launchctl (`qwen35-reader-262k` and any future ollama)

No residency management at all. `acquire` detects `type != "launchctl"` and returns immediately with a sentinel (no `BackendRecord`, no counter). The handler forwards the request to the ollama `base_url` as today; Class 1 performs **no** `ollama_load_model`/`ollama_unload_model` and **no** `health_wait` — ollama residency is entirely untracked (the `ollama_url`/`ollama_model`/`keep_alive` lifecycle is dropped for this path; those fields were the load/unload targets, not `base_url`, which is only the forwarding target). These aliases are never in `resident`, never evicted, never counted — satisfying task requirement 4. `release` is a no-op for them.

### Class 2 — coexistence (`glm53`, `qwen38-uzu`)

Goal: ensure *this* alias is resident **without evicting the other coexistence alias**, but **do** evict any exclusive backend that is resident (the symmetric case: an exclusive ds4 was running and now GLM is requested).

`acquire(alias)` loop (each iteration takes `_lock` only for the bracketed decision, releases it to await):

1. **[under `_lock`]** Read `resident`.
   - If an **exclusive** alias is resident (`any(a in resident for a in exclusive_launchctl_aliases())`): we must evict it first. Pick the eviction target set = all exclusive residents. Mark each target `DRAINING` (clear its `ready`), snapshot their records, **release `_lock`**, go to step 2 (drain+stop), then `continue` the loop (re-evaluate from the top — state may have changed while we awaited).
   - Else if `alias` already has a record:
     - `state == RESIDENT`: increment `record.generating`, clear `record.drained`, **release `_lock`**, `return record`. (Fast path — the common steady-state case: both coexistence backends up, request slots counted with a single lock acquisition.)
     - `state == STARTING`: another task is already cold-starting this exact alias. Snapshot `rec = record`, **release `_lock`**, then compute the wait bound from the **same config entry the starter reads** — `startup_timeout = entry.get("startup_timeout", DEFAULT_STARTUP_TIMEOUT)` for *this requested alias* (finding 7) — but **give the waiter headroom over the starter's *whole* budget (finding iteration-4/2)**. The starter's worst-case wall time is `launchctl_start` (bounded by `LAUNCHCTL_START_TIMEOUT`, the kickstart bound) **plus** `health_wait(..., timeout=startup_timeout)` — i.e. up to `LAUNCHCTL_START_TIMEOUT + startup_timeout` before it fires `ready.set()`. A waiter parked with only `startup_timeout` can therefore elapse ~`LAUNCHCTL_START_TIMEOUT` seconds *before* a legitimately slow-but-successful cold start finishes, spuriously 503-ing a request whose backend is seconds from `RESIDENT`. The waiter therefore parks with `waiter_timeout = LAUNCHCTL_START_TIMEOUT + startup_timeout`, which is strictly larger than the starter's whole budget, so the timeout never races a live cold start. **Correctness does not rest on this bound racing the starter: the authoritative give-up signals are the starter's own `start_error`/`gone` events** (set on failure/teardown), which wake the waiter immediately; the generous `waiter_timeout` is only a last-resort ceiling for a starter that neither succeeds nor signals. Then `await asyncio.wait_for(rec.ready.wait(), timeout=waiter_timeout)` (on `asyncio.TimeoutError` raise `BackendUnavailable`). After waking, **re-acquire `_lock`** and run the **coalesced-waiter commit sequence** (finding 3), which is the *only* correct way a parked waiter may claim its slot:
       1. if `rec.start_error is not None`: release and raise it (mapped to `BackendUnavailable`);
       2. elif `resident.get(alias) is rec and rec.state == RESIDENT`: increment `rec.generating`, clear `rec.drained`, release, `return rec`;
       3. else (the record was evicted/replaced between the `ready.set()` and this waiter waking — e.g. a fast exclusive request drained it): release and `continue` the acquire loop from the top. **The waiter must not increment a record that is no longer the resident instance** — doing so is the counter-leak wedge (hazard 7). This step enforces the record-identity invariant for the coalesced path.

       This coalesces concurrent cold-starts of the same alias into exactly one `launchctl_start`.
     - `state in (DRAINING, STOPPING)`: this alias is mid-eviction (e.g. an exclusive request started evicting it and ours raced in). Snapshot `rec = record`, **release `_lock`**, then `await asyncio.wait_for(rec.gone.wait(), timeout=QUEUE_TIMEOUT)` (finding 1 — the one specified mechanism). `rec.gone` is set only when the record is removed from `resident` *after the stop fully completes*, so the waiter cannot wake before the backend is confirmed down and the map key is free. On wake, `continue` the acquire loop: the alias is now absent from `resident`, so the next iteration takes the "create a fresh `STARTING` record" branch and starts the backend clean (task requirement 2, "starts fresh"). On `asyncio.TimeoutError` raise `ModelSwitchQueueTimeout` (503). **Do not** park on `rec.drained` (set mid-drain, races the stop) or on `rec.ready` (never set again on a record headed for teardown) — only `gone` is correct here.
   - Else (`alias` not in `resident` and no exclusive resident, or exclusives already handled): create a record in state `STARTING` (`ready` cleared, `drained` set, `generating=0`), insert into `resident`, **release `_lock`**, go to step 3 (cold start).

2. **Evict exclusives (outside `_lock`)**: for each exclusive target, `await drain_and_stop(record, deadline=QUEUE_TIMEOUT)` (defined below). `drain_and_stop` owns the removal and `gone` signalling for a successful stop; the caller does **not** separately mutate `resident` for that target (removal is the single chokepoint's job, so there is no double-delete race). On drain timeout, `drain_and_stop` raises `ModelSwitchQueueTimeout` (503) and the acquire aborts. Then `continue` the acquire loop.

3. **Cold start (outside `_lock`)**: let `startup_timeout = entry.get("startup_timeout", DEFAULT_STARTUP_TIMEOUT)` (finding 4). `await launchctl_start(entry["service"])` then `await health_wait(entry["health_url"], timeout=startup_timeout)`. The record this step owns is the `STARTING` instance it created in step 1; call it `my_record`.
   - On success: **[under `_lock`]** first assert the record-identity invariant — if `resident.get(alias) is not my_record`, this start has been superseded (its `STARTING` record was removed by an evictor that then re-created the key, or the record was torn down); abandon the result without mutating anyone, release, and `continue` the loop. Otherwise set `my_record.state = RESIDENT`, `my_record.ready.set()`, increment `my_record.generating`, clear `my_record.drained`, release, `return my_record`.
   - On failure (`RuntimeError`/`asyncio.TimeoutError`/subprocess error): **[under `_lock`]** if `resident.get(alias) is my_record`, set `my_record.start_error`, remove the record from `resident` (so the next request retries a clean start), set `my_record.gone` (frees any `gone`-waiter), and set `my_record.ready` **anyway** to wake coalesced `ready`-waiters (their commit sequence re-checks `start_error` and raises). If the record was already superseded, do none of that. Release and raise `BackendUnavailable` (503). **Crucially, never touch any *other* resident record** — a GLM start failure must leave a resident Uzu fully intact (task's "do not tear down a healthy resident backend when a different backend's start fails").

The coexistence path **never** drains or stops the *other* coexistence alias. A GLM cold start (step 3) runs entirely outside `_lock`, so an already-`RESIDENT` Uzu request takes the step-1 fast path, increments its own counter, and forwards — **it never blocks on GLM's `health_wait`**. This is the central anti-serialization guarantee.

### Class 3 — exclusive (`qwen38-mlx`, `deepseek-v41-uncensored`, future ds4)

Goal: only the requested exclusive backend may be resident. Evict **everything else launchctl** — both coexistence backends and any other exclusive backend — then start solo.

`acquire(alias)` loop (same record-identity discipline as Class 2):

1. **[under `_lock`]** Read `resident`.
   - If `alias` is already present:
     - `state == RESIDENT` and no other key is in `resident`: fast path — increment `record.generating`, clear `record.drained`, release, `return record`.
     - `state == RESIDENT` but other keys exist: mark **every other** resident record `DRAINING` (clear each `ready`), snapshot that target set, release, go to step 2.
     - `state == STARTING`: run the identical coalesced-waiter path as Class 2 (park on `rec.ready` bounded by `startup_timeout`; on wake, under `_lock`, raise `start_error`, or commit iff `resident.get(alias) is rec and rec.state == RESIDENT` **and no other key is resident** — if another launchctl backend slipped in, `continue` to evict it; else `continue`).
     - `state in (DRAINING, STOPPING)`: park on `rec.gone` bounded by `QUEUE_TIMEOUT`, then `continue` (identical to Class 2).
   - Else (`alias` absent): mark every current resident key `DRAINING` (clear each `ready`), snapshot the target set, create the `my_record` for `alias` in state `STARTING`, insert it, release, go to step 2.
2. **Drain + stop every target (outside `_lock`)**, each via `drain_and_stop(record, deadline=QUEUE_TIMEOUT)` (which is itself idempotent and identity-guarded — finding 6). As each completes, `drain_and_stop` removes it from `resident` and sets its `gone`. If any target's drain exceeds the deadline, `drain_and_stop` raises `ModelSwitchQueueTimeout`; the acquire aborts with that 503 — **do not** force-kill a mid-generation backend. The partially-evicted-then-abort cleanup contract is in hazard 6 below. Then `continue` the loop (re-evaluate: targets should now be gone).
3. **ds4 single-process-lock safety**: before `launchctl_start` of an exclusive ds4-family backend, every target must be **confirmed exited** (not merely SIGTERM-sent). `drain_and_stop` → `deactivate_backend` performs the confirmed-exit poll (below) *before* it removes the record and sets `gone`, so by the time step 2 completes for all targets they are provably down. The exclusive start in step 4 proceeds only after `resident` is empty of all other launchctl keys. This preserves "never start a ds4 while another ds4 may hold its lock."
4. **Cold start (outside `_lock`)** identical to coexistence step 3, operating on `my_record`: compute `startup_timeout = entry.get("startup_timeout", DEFAULT_STARTUP_TIMEOUT)`; `launchctl_start` + `health_wait`; on success, under `_lock`, assert `resident.get(alias) is my_record` (else `continue`) then commit `RESIDENT` + increment; on failure, under `_lock` and only if still the resident instance, set `start_error`, remove record, set `gone`, set `ready`, raise `BackendUnavailable`.

### `drain_and_stop(record, deadline)` — the drain-before-evict primitive

Takes the record **instance** it was told to evict. Its long awaits run **outside `_lock`**; it reacquires the lock only for the guard and the final removal.

0. **Idempotency + identity guard (first action, under `_lock`) — finding 6.** Re-read `cur = resident.get(record.alias)`. If `cur is not record` (the record was already removed and perhaps replaced) **or** `record.state == STOPPING` (another evictor already owns the stop), **return immediately without doing anything** — this is a no-op. This makes "two evictors, same victim" safe: whichever thread wins the guard owns the stop; the loser returns at once and never issues a second `launchctl kill`. Only one evictor ever advances past step 0 for a given record instance. Release `_lock`.
1. **[under `_lock`]** Set `record.state = DRAINING`, `record.ready.clear()` (new acquires for this alias will not take the fast path; they park on `gone` and later restart it). Release.
2. `try: await asyncio.wait_for(record.drained.wait(), timeout=deadline)` — block (lock-free) until this alias's in-flight count hits 0. `record.drained` is set by `release()` when `generating` reaches 0. On `asyncio.TimeoutError` the drain is aborting *before* anything was stopped, so the victim is still alive and healthy and must be **restored to a serving state, not left bricked** (finding 1). Perform the **aborted-drain recovery** under `_lock`, then re-raise as `ModelSwitchQueueTimeout`:
   - **[under `_lock`]** re-read `cur = resident.get(record.alias)`. **Only if `cur is record`** (the record is still the resident instance — identity guard) **and `record.state == DRAINING`** (we never advanced to `STOPPING`, so `deactivate_backend`/`launchctl kill` was never issued and the backend is provably still up): revert `record.state = DRAINING → RESIDENT` and `record.ready.set()`. This restores the still-alive victim so every subsequent `acquire` for this alias takes the fast path again instead of parking on a `gone` that will never fire. If `cur is not record` or the state already moved to `STOPPING` (another evictor won the stop in the meantime), do **not** revert — that evictor owns the teardown and will set `gone` itself. Release `_lock`.
   - Then raise `ModelSwitchQueueTimeout` to the task that wanted the *other* backend. The switch requester still gets a fast structured 503 to retry; the victim keeps serving its in-flight and future requests.

   This is the mandatory recovery transition `DRAINING → RESIDENT` for an aborted drain that stopped nothing. The invariant it enforces: **a drain abort that issued no stop must leave the victim `RESIDENT`, never `DRAINING`.** The only way a record stays `DRAINING` after `drain_and_stop` returns/raises is if an evictor is still actively driving it toward `STOPPING` on another task; a `DRAINING` record with no owning evictor cannot exist. Because the revert is identity- and state-guarded, it cannot race a concurrent evictor that *did* advance to `STOPPING`: that evictor's own step-0 guard already claimed the stop, our `state == DRAINING` check fails, and we leave the record alone for it to tear down.
3. **[under `_lock`]** Set `record.state = STOPPING`, release. Then (lock-free) `await deactivate_backend(record.alias)` which for launchctl does `launchctl_stop(service)` **and waits for confirmed process exit** (mechanism below).
4. **[under `_lock`]** `del resident[record.alias]` **iff** `resident.get(record.alias) is record` (identity), then `record.gone.set()`. Releasing the key and signalling `gone` happen in the *same* critical section, so any `gone`-waiter that wakes is guaranteed to find the key absent (or re-created by a later task — its own identity check handles that). Release.

### `deactivate_backend` modification and the confirmed-exit mechanism (finding 7)

For **launchctl** backends, `deactivate_backend`:
1. `await launchctl_stop(service)` (SIGTERM via `launchctl kill`).
2. **Confirm process exit** — not health-URL-down. Health-URL non-200 only proves the HTTP listener stopped answering; the OS *process* may still be alive holding memory and, critically, the ds4 single-process lock. The confirmation polls `launchctl print <service>` every `EXIT_POLL_INTERVAL` up to `EXIT_CONFIRM_TIMEOUT`. **The stored `service` string is already the complete `launchctl` domain-target** — `models.json` carries it as `gui/$UID/com.celes.<name>` and `load_config()` has already expanded `$UID` in place (e.g. `gui/501/com.celes.uzu-server`), so the command is `launchctl print gui/501/com.celes.uzu-server`. Do **not** prefix another `gui/$UID/`: `launchctl print gui/$UID/<service>` would expand to `launchctl print gui/501/gui/501/com.celes.uzu-server`, a malformed target that `launchctl print` rejects with an argument-format error — which, if mis-classified as "gone," would silently declare every process confirmed-exited immediately and defeat the entire ds4 single-process-lock safety this mechanism exists to provide. Parse the result by exit code and output:
   - **exit code 0** with a live `pid = <n>` line in the output → the process is **still running**; keep polling.
   - **non-zero exit** whose stderr is the "Could not find service" / "service not found" result → the on-demand agent (`KeepAlive=false`) has disappeared from the domain once dead → **confirmed gone**.
   - an **argument-format / usage error** (e.g. a malformed target) is **not** "gone" — it is a bug or misconfiguration; treat it as *unconfirmed* (keep polling until `EXIT_CONFIRM_TIMEOUT`, then raise per step 3) rather than silently declaring the process exited. This guards against the exact mis-detection the double-prefix bug would cause.
3. If exit is **not** confirmed within `EXIT_CONFIRM_TIMEOUT`, **raise** `RuntimeError` (task's "re-raise-on-failed-stop"): the evictor's `drain_and_stop` does not reach step 4, so the record stays in `resident` as `STOPPING` and `gone` is never set — no phantom "stopped but still live" state, and no exclusive ds4 start can proceed because step 3 of Class 3 only advances when every target is confirmed gone.
4. **Reconciling re-raise with idempotency (finding 6):** a `launchctl kill` that returns non-zero because the service is already **not running** is classified as **success** (confirmed-not-running), never an error — only a failure to *confirm exit* in step 2/3 raises. This prevents the re-raise change from spuriously aborting a switch when a redundant kill lands on an already-dead service. `launchctl_stop` keeps its existing "non-zero may mean already stopped" tolerance; the authority on liveness is step 2's `launchctl print`, not the kill's return code.

Ollama `deactivate` keeps best-effort/log-only semantics (ollama is never part of eviction anyway).

### `release(alias)`

For launchctl aliases with a record: under `_lock`, decrement `record.generating`; if it reaches 0, `record.drained.set()` (unblocking any evictor parked in `drain_and_stop`). No-op for ollama/sentinel. This replaces the handlers' `finally: state.generating -= 1`.

## Lock-hold boundaries (the deadlock/serialization contract)

The invariant: **`_lock` is held only for synchronous reads/writes of `resident` and record fields; it is never held across `await launchctl_start`, `await health_wait`, `await drain_and_stop`, `await deactivate_backend`, or request forwarding.** Every long await happens after `_lock` is released, and progress is signalled through per-alias events, not by holding the lock.

Concretely, within one `acquire`:
- Lock acquisition #1: classify + decide (fast path return, or mark targets `DRAINING`, or create `STARTING` record). Released before any await.
- (awaits: drain targets, stop targets, cold start — all lock-free)
- Lock acquisition #2…n: commit each completed sub-step (remove a drained target; set `RESIDENT` + increment on start success; set `start_error` + remove on failure).

### Record-identity invariant (finding 2 — the correctness condition for every lock-free await)

**Snapshots taken before releasing `_lock` are read-only hints. The only authority is `resident[alias]` re-read under `_lock` on each commit, compared by instance identity (`is`), not by key presence.** Every commit step that mutates based on work done during a lock-free await MUST, under `_lock`, check `resident.get(alias) is my_record` before mutating; if the check fails, the record it was working on has been superseded (removed and possibly re-created under the same key by a re-request during eviction — explicitly allowed by hazard 4), so it discards its local record and `continue`s the acquire loop (or, for a cold-start success that was superseded, abandons the started backend to be reconciled by the next request rather than committing a stale `RESIDENT`). This single rule is what makes all the lock-free awaits safe: because keys can be reused across a `DRAINING → gone → fresh STARTING` cycle, key presence alone is never sufficient — identity is. It applies in exactly these places:
- coexistence/exclusive cold-start success commit (set `RESIDENT` + increment);
- cold-start failure cleanup (set `start_error`, remove, set `gone`/`ready`);
- the coalesced-waiter post-wake commit (increment only iff `resident.get(alias) is rec and rec.state == RESIDENT`);
- `drain_and_stop`'s step 0 guard and step 4 removal (`del` only iff `resident.get(alias) is record`).

Lost-wakeup freedom follows: a waiter parked on `rec.ready` or `rec.gone` is woken only by a commit on *that same instance*; after waking it re-validates identity, so a wake that no longer reflects reality (the instance was superseded) safely degrades to a `continue` rather than a corrupt mutation.

Because the lock is only ever held for non-awaiting critical sections, it cannot be held across a point where the event loop could schedule another `acquire` that then blocks on the same lock behind a long operation — which is the only way this single lock could serialize independent work. A `glm53` cold start holds the lock for microseconds (to flip the record to `STARTING`), releases it, then spends up to `startup_timeout` in `health_wait` **with the lock free**, so a concurrent `qwen38-uzu` request acquires the lock, sees Uzu `RESIDENT`, increments, and forwards without ever contending on GLM's progress.

Deadlock freedom: there is exactly one lock and it is never held across an await, so there is no lock-ordering cycle and no await-while-holding hazard. Cross-alias waits use `asyncio.Event`s, never nested lock acquisition. An evictor waiting on `record.drained` is woken only by `release()` setting that event; `release()` takes the lock briefly and never waits on anything, so it cannot be starved. The `startup_timeout`/`QUEUE_TIMEOUT` bounds guarantee every wait terminates.

## Concurrency hazards and how the design avoids each

1. **Serializing independent coexistence backends.** Avoided by never holding `_lock` across `health_wait`/forwarding and by per-alias counters/events (above). Verified by the "GLM cold start vs resident Uzu" trace.
2. **Cold-start-while-other-serving deadlock.** The cold-starting task parks (outside the lock) on *its own* `record.ready`; the serving task touches only *its own* record. No shared wait object, no shared lock hold. No deadlock possible.
3. **Thundering-herd cold start (N concurrent requests for the same not-yet-resident alias).** The first creates the `STARTING` record and runs the single `launchctl_start`; the rest see `STARTING`, park on `rec.ready`, and on wake each runs the **coalesced-waiter commit sequence** under `_lock` (finding 3): raise `start_error` if set; else increment + clear `drained` *only if* `resident.get(alias) is rec and rec.state == RESIDENT`; else `continue`. Exactly one `launchctl_start` fires. A waiter that wakes after a fast exclusive request has already evicted the backend falls into the `continue` branch and re-drives the acquire from the top instead of incrementing a dead record — this is what prevents the counter-leak wedge (hazard 7). Coalescing is per alias, so a herd for GLM does not touch a herd for Uzu.
4. **Evict-while-draining race / request arriving mid-eviction.** When an alias is `DRAINING`/`STOPPING`, its `ready` is cleared, so a new `acquire` for it does not take the fast path; it snapshots the record and parks on `rec.gone` (bounded by `QUEUE_TIMEOUT`), then `continue`s. `gone` fires only in the same `_lock` critical section that `del`s the key (step 4 of `drain_and_stop`), so the waiter cannot resume until the stop is fully complete and the key is free; its next iteration creates a fresh `STARTING` record (task requirement 2, "starts fresh"). The restart cannot overlap the stop because (a) the old record stays in `resident` until confirmed exit + removal, and (b) the new record is a *different instance*; the record-identity invariant guarantees no commit crosses the two.
5. **Two evictors targeting the same victim** (two exclusive requests arrive, or an exclusive and a coexistence-evicting-an-exclusive). Both may mark the victim `DRAINING`, but `drain_and_stop`'s **step-0 guard** (under `_lock`: bail if `resident.get(alias) is not record` or `state == STOPPING`) ensures exactly one evictor advances to the actual stop; the other returns a no-op immediately. Only one `launchctl kill` is issued per record instance, so the re-raise-on-failed-stop change (finding 6) never fires on a redundant second kill. A `launchctl kill` that reports "service not running" is classified as confirmed-not-running (success), never an abort.
6. **Partial eviction then start failure.** Scenario: exclusive ds4 requested; GLM and Uzu both evicted successfully (each removed + `gone` set); ds4 `launchctl_start`/`health_wait` fails. Contract: under `_lock`, if the ds4 record is still the resident instance, set its `start_error`, remove it, set `gone`+`ready`, and return `BackendUnavailable` (503). The two coexistence backends are **not** auto-restarted here (they were legitimately evicted to honor the memory budget — restarting them would blow it); they start fresh on their next request, per requirement 2. `resident` is left empty of launchctl backends — a valid state. Deliberate trade: a failed exclusive start costs a cold start on the next GLM/Uzu request but never risks co-resident OOM. If instead a *target drain* times out mid-eviction (not all targets stopped), `drain_and_stop` raises `ModelSwitchQueueTimeout`; already-stopped targets stay removed, the still-draining target stays `DRAINING` in `resident`, and the ds4 `STARTING` record created in step 1 is removed under `_lock` as part of the abort (identity-checked) so a retry re-evaluates cleanly.
7. **Drain never completes (a wedged generation holds `generating > 0`), or a leaked counter wedges future evictions.** The drain itself is bounded by `QUEUE_TIMEOUT` in `drain_and_stop`; on timeout the switch is aborted with a fast structured 503 (`model_switch_queue_timeout`) and the victim is **left running** (not force-killed), so an in-flight long generation is never truncated. **Critically, the aborted drain also runs the recovery transition (`drain_and_stop` step 2, finding 1): under `_lock`, if the record is still the resident instance and never advanced past `DRAINING`, it is reverted `DRAINING → RESIDENT` with `ready` re-set.** This closes the permanent-liveness-wedge: without it, a record left `DRAINING` after a timed-out drain would clear `ready` and every future `acquire` would park on a `gone` event that no evictor will ever fire (because the drain was aborted and nobody owns the teardown), 503-ing forever against a healthy backend — including the entirely normal case of a 45-second completion colliding with a switch, not just a wedged generation. The revert restores the fast path immediately once the in-flight work drains. The adjacent failure mode — a `generating` counter that is incremented but never decremented, permanently blocking that alias's drain — is prevented structurally: (a) every acquire path that increments does so under `_lock` in the same critical section that confirms `RESIDENT` identity, so no increment lands on a `STOPPING`/removed record (findings 2, 3); and (b) the single shared `proxy_request` helper guarantees a matching `release(record)` in `finally` on **every exit path *after a successful `acquire`*** (forward success, a 502 or 400 raised during forwarding, cancellation of the forward), so a counter cannot leak from a missed decrement in one of four divergent handler copies. **The `finally` is deliberately scoped to the post-`acquire` region: a 503 (or any other failure) raised *by `acquire` itself* never reaches the `release`, because `acquire` increments only on success and the `try/finally` begins after it returns (finding iteration-4/1). This prevents the mirror-image underflow bug — an unconditional `finally: release` would decrement a slot a failed `acquire` never counted, driving `generating` negative and, during an eviction timeout, spuriously decrementing a live *other* backend's counter.**
8. **`release` racing the evictor's `drained.wait()`.** `release` decrements and sets `drained` under `_lock`; the evictor's `asyncio.wait_for(record.drained.wait(), …)` wakes on that set. If `release` sets `drained` an instant before the evictor awaits, `Event.wait()` returns immediately (the event is already set) — no lost wakeup. The evictor clears `drained` implicitly by transitioning to `STOPPING`; no new request can re-arm it because `ready` is cleared (new acquires park, they do not increment this record).
9. **Memory budget across the launchctl set.** Enforced *structurally* by the eviction rule, not by a RAM guard (task says do not add one unless trivial/safe). GLM (~67.6 GiB) + Uzu (~15 GiB) ≈ 83 GiB fits in 128 GB; a full-residency ds4 (~90 GiB) is exclusive, so requesting it evicts the pair first — the two can never be co-resident with ds4 because ds4's acquire drains everything else before starting. Within the launchctl set, the classification *is* the budget and no explicit accounting is needed. **The one footprint this structural rule does *not* bound is a resident ollama model** — see the dedicated "Ollama co-residency and the memory budget" subsection below, which is a deliberate behavior change from today and the single place the budget argument is not purely structural.

## Ollama co-residency and the memory budget (finding 4 — deliberate behavior change)

The rework makes ollama/non-launchctl backends (`qwen35-reader-262k` and any future ollama) **completely untracked**: they are never in `resident`, never counted, never drained, and never evicted (Class 1). This is required by task requirement 4 ("do not stop/evict them and do not count them in coexistence/residency logic"), and it is correct — but it is a **real behavior change from today that must be called out, not left silent**:

- **Today** (verified against `activate_backend`): an ollama request first runs `if state.active_backend: await deactivate_backend(state.active_backend)` — i.e. selecting the ollama backend **evicts** whatever launchctl backend was active before loading the ollama model. The current proxy is swap-one-at-a-time across *all* types, so ollama and launchctl are mutually exclusive in memory.
- **After the rework**: an ollama request does no eviction at all, and a launchctl `acquire` drains only launchctl residents and never unloads a resident ollama model. Consequently a request for `qwen35-reader-262k` while GLM (~67.6 GiB) + Uzu (~15 GiB) are both resident leaves **GLM + Uzu + the ollama model all co-resident simultaneously**, and symmetrically a launchctl `acquire` will *not* reclaim memory held by a resident ollama model.

Because this co-residency is now possible, hazard 9's "the classification *is* the budget" is true **only within the launchctl set** and does not by itself bound total memory once a never-evicted ollama model sits on top of the 83 GiB pair.

**Decision (chosen, not left to the implementer):** cross-type (ollama ↔ launchctl) eviction is **explicitly out of scope** for this change, and the **operator owns the ollama/launchctl memory budget**. Rationale: (a) requirement 4 forbids the proxy from evicting or even tracking ollama, so the proxy *cannot* enforce a cross-type budget without violating the task; (b) the production reader model in config (`qwen3.5-reader:9b-262k`, a ~9B model) is small — on the order of a few GiB at 4-bit even with a large context — so in the intended deployment it fits alongside the 83 GiB pair within 128 GB with headroom, and the common case is safe; (c) a correct cross-type guard would require a RAM accounting layer the task explicitly says not to add unless trivial, and reconciling it with "never evict ollama" is not trivial. The design therefore records the budget as an **operator responsibility** for the ollama footprint specifically, documents the ~9B reader as the sized expectation, and does not add a guard. If a future large ollama model is introduced, that is the point at which an explicit cross-type budget decision must be revisited — flagged here so it is not a silent surprise.

## Validation of external inputs

- **`model` field** (request body JSON): optional string. Resolved by `backend_for_model`. The old `alias = state.active_backend` fallback is **removed** (ambiguous with a set). One unresolved-model rule applies to **every** forwarding path — the four POST handlers and `handle_v1_catchall` (finding 9): **zero** launchctl residents → `503 backend_unavailable`; **exactly one** launchctl resident → use it (back-compat for bare requests during single-residency); **more than one** resident → `400 model_not_resolved` listing available model names. No path "picks an arbitrary alias." This is a deliberate, documented behavior change forced by the resident-set model; the only cross-path asymmetry is the catchall's counter-exemption and tolerate-disappearance behavior documented above, which does not change the resolution rule.
- **Request body**: must be valid JSON (existing `json.JSONDecodeError → 400 "Invalid JSON"`, unchanged).
- **`"coexist"` config field**: optional boolean per backend entry; absent ⇒ `False` (read per entry — see the Summary's fallback rule). `load_config()` validates it is a bool if present and raises a startup `SystemExit` with a clear message on a malformed value (consistent with the existing "config not found → exit(1)" strictness). The `DEFAULT_COEXIST_ALIASES` fallback is applied only when **zero** entries declare the field; a partial migration (field present on some entries, absent on others) is honored per entry, and if `glm53` or `qwen38-uzu` ends up exclusive after parsing, `load_config()` emits a `log.warning` naming the alias so the half-migrated pair is visible. Only meaningful on `type == "launchctl"` entries; a `"coexist": true` on an ollama entry is logged as a warning and ignored (ollama is never residency-managed).
- **`startup_timeout`** per backend (already in config for `qwen38-mlx`): optional, a positive number of seconds. When omitted it defaults to `DEFAULT_STARTUP_TIMEOUT` (300s — see "Constants and timeouts"; there is **one** default, defined in that one place, deliberately *not* `health_wait`'s historical 60s, which would 503 every normal heavy cold start — the finding-4 regression). Used as the cold-start/`ready`-wait bound.

## Error mapping (handler layer)

Introduce typed exceptions raised by `acquire`: `ModelSwitchQueueTimeout` (drain exceeded `QUEUE_TIMEOUT`) and `BackendUnavailable` (start/health failed). The handlers wrap `await state.acquire(alias)` and the forward in one `try`:

- `ModelSwitchQueueTimeout` → **503** `{"error": {"type": "model_switch_queue_timeout", "message": …}}` with `Retry-After: <small>` header. (Preserves the task's 503 semantics; today `asyncio.TimeoutError` isn't caught at all, so this is net-new structured behavior.)
- `BackendUnavailable` (wraps the start/health `RuntimeError`/`asyncio.TimeoutError`) → **503** `{"error": {"type": "backend_unavailable", "message": …}}` with `Retry-After`. This replaces today's unstructured 500 escape, so OmniRoute can fail up cleanly and fast.
- `aiohttp.ClientError` during forwarding → **502** (unchanged).
- `json.JSONDecodeError` → **400** (unchanged).
- Unresolved model with ambiguous residency → **400** `model_not_resolved`.

All four POST handlers share this mapping. To avoid four divergent copies (today they are near-duplicates), factor the acquire+forward+map into a single helper `proxy_request(request, upstream_suffix)` that each handler calls with its path suffix (`/chat/completions`, `/responses`, `/messages`, `/completions`). This is a refactor the coexistence change makes worthwhile because the `finally: release(alias)` and the new error mapping must be identical across all four; duplicating them four times is the most likely place for a drain-counter leak (a missed `release` leaves `generating` permanently > 0 and wedges future evictions — hazard 7). One helper, one `finally`, one mapping.

### Admin and catchall paths (findings 8, 9)

The resident-set model forces every path that forwards to or stops a launchctl backend through the same chokepoints; no handler may call `deactivate_backend` directly or forward to a backend an evictor may be stopping.

- **`/admin/status` (`handle_status`)**: reports the full `resident` map — a list of `{alias, state, generating}` — plus the derived `coexist_aliases`, instead of a single `active`/`switching`/`generating`. Read-only; no locking beyond a snapshot under `_lock`.
- **`/v1/models` (`handle_models`)**: the per-alias `active` flag becomes "`alias in resident and resident[alias].state == RESIDENT`" (a backend can now be resident while others are too). **Client-visible contract change (finding iteration-4/nit):** today exactly one alias (and its `model_names`) reports `active: true`; after this change **two can report `active: true` simultaneously** (GLM + Uzu co-resident). Any downstream consumer that assumes a single active model must be confirmed not to rely on single-active — verify at the integration layer (e.g. OmniRoute route selection, any UI that picks "the" active model); the design records no consumer that depends on single-active, and this must be re-confirmed during integration.
- **`/admin/select`** — **warm-up-only, no pin (finding iteration-4/3)**: ensures the named alias is started/resident by running the full `acquire(alias)` state machine (including evicting exclusives/coexistence per the alias's class), then immediately releasing the slot it took, and returns the resulting resident set. It must **not** call `activate_backend` directly. The semantics are defined explicitly: `/admin/select` is a *warm-up*, not a *pin*. It leaves the backend `RESIDENT` with `generating == 0`, so **normal eviction rules apply immediately** — a subsequent request for a different exclusive backend may evict the just-selected alias, and that is intended. There is **no special pin flag** and no durable "stay resident until replaced" guarantee; durable residency comes only from the coexistence classification (`glm53`/`qwen38-uzu` are allowed to co-reside and are re-started on their next request after any eviction). This resolves the previously-undefined pin semantics: a `RESIDENT`-with-zero-slots record is a deliberate, documented outcome, not a race.
- **`/admin/stop` (`handle_stop`)**: takes an **optional** `alias` in the body. If `alias` is given, resolve it with `rec = resident.get(alias)` under `_lock` (snapshot) — **never** an unguarded `resident[alias]` index, which would `KeyError → 500` on a non-resident or typo alias (finding 6). Branch:
  - `alias` is not a key in `state.backends` (not a configured backend) → `400 {"error": "Invalid alias", "valid": [...]}`, matching the existing `/admin/select` validation shape.
  - `alias` is a valid config backend but `rec is None` (not currently resident) → `200 {"stopped": [], "note": "not resident"}` — an idempotent no-op (stopping an already-stopped backend succeeds trivially).
  - `rec` exists → stop exactly that one via `drain_and_stop(rec, deadline=QUEUE_TIMEOUT)` (draining in-flight work first — it must **not** call `deactivate_backend` directly), then return `200 {"stopped": [alias]}`.
  If `alias` is omitted, it drains-and-stops **every** current resident launchctl backend via `drain_and_stop`, each independently, and returns the list actually stopped. On drain timeout for any target, returns `503 model_switch_queue_timeout` for that target and leaves it running. This closes the pre-existing drain-bypass where `/admin/stop` killed `active_backend` mid-generation.
- **`handle_v1_catchall`**: must participate in the same residency discipline rather than "pick any." It resolves a target alias using the **same rule as the POST handlers** (finding 9): if the path/query names a resolvable model, use its alias; otherwise — zero residents → `503 backend_unavailable`; exactly one launchctl resident → use it; more than one → `400 model_not_resolved` (require an explicit model/alias). Because the catchall carries no body model field for most GET paths, the "exactly one resident" fallback is the common case and the many-resident case correctly refuses rather than guessing. The catchall is a **non-generating, counter-exempt** path (it forwards short metadata GETs, not long completions), but it is documented as counter-exempt and therefore **must tolerate the backend disappearing mid-request**: a concurrent evictor may stop the chosen backend, so a forwarding `aiohttp.ClientError`/connection-refused maps to `503 backend_unavailable` (not a 502), signalling a transient residency change the caller can retry. This is the one deliberate asymmetry from the POST handlers (which hold a counter slot and so cannot be evicted mid-request), and it is justified by the catchall's read-only, short-lived nature; counting it would add a slot to every metadata poll for no safety benefit since it never truncates a generation.

## Invariant ownership

- **"At most the coexistence pair, or exactly one exclusive, is resident"** — owned by `acquire` (Class 3 drains all-but-self; Class 2 drains exclusives-but-not-the-other-coexistence). The data model cannot by itself enforce it; the acquire state machine does.
- **"A backend is stopped only with `generating == 0`"** — owned by `drain_and_stop` (waits on `drained`), the single chokepoint for every stop. No other code path calls `deactivate_backend` on a launchctl backend.
- **"Exactly one `launchctl_start` per cold start"** — owned by the `STARTING`-record coalescing in `acquire`.
- **"ds4 never started while another ds4 process may hold its lock"** — owned by `deactivate_backend`'s confirmed-exit wait feeding Class 3 step 3.

## Testability

- **Unit (package-local, pytest-asyncio against a mocked `launchctl`/`health_wait`)** — the bulk of coverage, since the whole change is a pure asyncio state machine behind two injectable boundaries (`launchctl_start`/`stop` subprocess calls and `health_wait` HTTP polling). Inject fakes for both and drive `acquire`/`release` directly:

A design that needed the real launchd to test its *logic* would be a smell; this one isolates launchd behind two seams, so the logic is fully unit-testable and only the OS integration is manual.

## Iteration 4 / final fixes

This iteration applies three pre-approved fixes from the final review (`design-review.md` / `design-review.json`: 1 HIGH, 2 MEDIUM) plus three NITs. No design-review gate is re-run; these are confirmed resolutions, not a redesign.

- **Fix 1 (HIGH — `release` in `finally` underflows the per-alias counter when `acquire` raises).** Resolved. Slot bookkeeping is now bound to `acquire` **success**, not to the handler `finally`. "The acquire/evict state machine" intro states that `acquire` increments only on success and returns the record/sentinel, and that the `try/finally` owning `release` begins **after** `acquire` returns — so a raising `acquire` (e.g. a 503) never reaches the `release`. Hazard 7's "every exit path" clause is re-scoped to "**every exit path *after a successful `acquire`***" (forward success, forwarding 502/400, cancellation) and explicitly excludes a 503 raised by `acquire` itself. The contract is stated unambiguously: a `finally: release` must not run when `acquire` raised. This closes the mirror-image underflow (negative `generating`, corrupted `drained` predicate, spurious decrement of a live *other* backend during eviction).
- **Fix 2 (MEDIUM — coalesced-waiter `ready.wait()` timeout shorter than the starter's worst-case cold start).** Resolved. A new module constant `LAUNCHCTL_START_TIMEOUT = 15.0` (env-overridable, defined once in "Constants and timeouts") bounds the `launchctl kickstart` subprocess **and** is added to the coalesced waiter's bound: `waiter_timeout = LAUNCHCTL_START_TIMEOUT + startup_timeout`. This gives the waiter headroom over the starter's whole worst-case budget (`LAUNCHCTL_START_TIMEOUT + health_wait(startup_timeout)`), so it can no longer 503 a request ~15s before a legitimately slow cold start completes. The design now states that the authoritative give-up signals are the starter's `start_error`/`gone` events (not the raw timeout), with the generous bound as a last-resort ceiling. Class 3's STARTING branch inherits this via "identical coalesced-waiter path as Class 2."
- **Fix 3 (MEDIUM — `/admin/select` acquire-then-immediate-release leaves undefined pin semantics).** Resolved. `/admin/select` is defined explicitly as **warm-up-only**: ensure the backend is started, return the resident set, and let normal eviction rules apply. It leaves the alias `RESIDENT` with `generating == 0` (immediately eligible for eviction by a later exclusive request) **by design** — there is **no special pin** and no durable "stay resident until replaced" guarantee; durable residency comes only from the coexistence classification. The previously-undefined pin semantics are now a documented outcome.
- **Nit (Class 1 ollama prose).** Resolved. Class 1 prose now states it performs **no** `ollama_load_model`/`ollama_unload_model` and **no** `health_wait` (ollama residency untracked), forwarding only to `base_url`; the `ollama_url`/`ollama_model`/`keep_alive` fields are named as the dropped lifecycle targets, distinct from the `base_url` forwarding target.
- **Nit (`models.json.new`).** Resolved. "Files to modify" now notes `models.json.new` is a stale scratch file (different aliases: `ds4` :8080, `evocua`) that must be left **untouched**; this change edits only `models.json`.
- **Nit (`/v1/models` multiple `active:true`).** Resolved. `/v1/models` prose now notes it may report **multiple** `active: true` entries (GLM + Uzu) after this change and calls for integration-layer confirmation that no consumer relies on single-active.
