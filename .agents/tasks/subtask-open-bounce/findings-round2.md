# Subtask-open bounce — Round 2 investigation (read-only)

## Summary answer (most likely root cause)

**The merged round-1 fix (commit `b2a6c9459`) is NOT running.** The webview and
extension bundles that the user is actually executing were built *before* the fix
was committed, so the old "recompute `showWelcome` on every state push" code is
still live. This is why the symptom persists unchanged after the merge.

Hard evidence:

- Fix commit `b2a6c9459` ("make webview welcome gate sticky…") is **HEAD**, dated
  **2026-10-09 08:08**.
- Built webview bundle `src/webview-ui/build/assets/index.js` is dated
  **2026-10-02 20:25** (7 days older than the fix).
- Built extension bundle `src/dist/extension.js` is dated **2026-10-07 14:58**
  (2 days older than the fix).
- Both build outputs are **gitignored** (`git check-ignore` confirms), i.e. they
  are local build artifacts, not regenerated by `git` state alone — they only
  change when you actually rebuild.
- The fix symbol `hasLoweredWelcomeGateRef` appears **4×** in source
  (`webview-ui/src/context/ExtensionStateContext.tsx`) but **0×** in the built
  bundle `src/webview-ui/build/assets/index.js`, and `hasLoweredWelcomeGate`
  appears **0×** in `src/dist/extension.js`.

**How to tell whether the running bundle includes the fix:** grep the built
webview bundle for the sticky-gate marker. It is intentionally retained in the
minified output as a `useRef` identifier is mangled, but the *string*
`hasLoweredWelcomeGate` is not a React-mangled name — searching the built chunk
for it is a reliable yes/no:

```
LC_ALL=C grep -c "hasLoweredWelcomeGate" src/webview-ui/build/assets/index.js
```

Today this prints `0` → the fix is not in the running webview. After a correct
`pnpm` build/package of `webview-ui` it should print a non-zero count. The user
must **rebuild the webview (and extension) and reload the VS Code window** before
any conclusion about whether round 1's fix works can be drawn.

### Was round 1 wrong, or correct-but-insufficient?

Round 1's *diagnosis mechanism* (webview recomputes `showWelcome` on every state
push; task-scoped pushes carry an under-configured, task-scoped `apiConfiguration`
plus a cold `zooCodeIsAuthenticated`, flipping `showWelcome` → `true`, so
`App.isSetupGatedTab` renders `WelcomeView`) is a **real and correctly-identified
bounce path** that exists in the source. The code at
`webview-ui/src/context/ExtensionStateContext.tsx:362-379` and the gate at
`App.tsx` (`isSetupGatedTab = showWelcome && tab !== "settings" && tab !==
"marketplace"`) confirm it.

However it is **impossible to say whether that fix is sufficient**, because it was
never actually exercised — the running bundle predates it. The persisting symptom
is therefore most parsimoniously explained by "not rebuilt / not reloaded," not by
"wrong root cause."

There is also a **secondary ambiguity round 1 may have gotten wrong** (see next
section): the user's "main page" is very likely **not** `WelcomeView` at all, but
the **ChatView empty/home surface**. If so, the sticky-welcome-gate fix would be
*insufficient* even once it is running, because it does nothing about an empty
`clineMessages` landing. This needs a rebuild to disambiguate.

## Which "home" view does the user actually land on?

There are two distinct "landing" surfaces, and they are easy to conflate:

1. **`WelcomeView`** — the setup/sign-in gate. Rendered by `App.tsx` only when
   `isSetupGatedTab` is true:
   `const isSetupGatedTab = showWelcome && tab !== "settings" && tab !== "marketplace"`
   (`webview-ui/src/App.tsx`). Driven by `showWelcome`, which is set in
   `ExtensionStateContext`.

2. **ChatView empty/home surface** — rendered inside `ChatView` when there is **no
   current task**. In `ChatView.tsx`:
   - `const task = useMemo(() => messages.at(0), [messages])`
     (`clineMessages[0]`), line ~140.
   - When `!task`, the render falls into the else branch
     (`ChatView.tsx` ~1781-1795) that shows `RooHero` + `RooTips` +
     `{taskHistory.length > 0 && <HistoryPreview />}`.
   This is the "start page with your recent tasks listed" surface.

**Most likely the user lands on surface #2 (ChatView home), not WelcomeView.**
Reasoning: round 1 already made `WelcomeView` sticky, yet the user reports *no
change*. The ChatView home surface appears whenever `clineMessages` is empty,
which is exactly the transient (or stuck) state right after
`showTaskWithId → chatButtonClicked` switches to the chat tab but before the
opened task's messages arrive. If they never arrive (or get overwritten by a
later empty push), the user is parked on RooHero/HistoryPreview — which reads
exactly as "dumped back to the start page."

The active view is selected by:
- `tab` state in `App.tsx` (`"settings" | "history" | "chat" | "marketplace"`),
  switched via `tabsByMessageAction` on incoming `{ type: "action", action }`
  messages. `chatButtonClicked → "chat"`.
- Within the chat tab, ChatView's own `!task` check picks home vs. the task
  transcript.

So "task board only lets you click, not view" + "dumps me back to start page" are
consistent with: the click posts `showTaskWithId`, the extension switches to the
chat tab, but the chat tab shows its empty home surface because the opened task's
`clineMessages` are not present in the webview state.

## Corrected full message-flow trace for a SUBTASK click

1. **Webview — `SubtaskRow.tsx` `handleClick`**
   `vscode.postMessage({ type: "showTaskWithId", text: item.id })`.
   Confirmed identical to `TaskItem.tsx` `handleClick` (same message, same
   `item.id`). **The id passed for a subtask is the same shape and the same field
   (`item.id`) a top-level `TaskItem` passes.** `useGroupedTasks.buildSubtree`
   carries the real `HistoryItem` through unchanged (`item: task as
   DisplayHistoryItem`), and subtasks are stored as **top-level `HistoryItem`s with
   a `parentTaskId`** (grouping is derived in the webview via
   `childrenMap`/`taskMap`, not a composite id). → **Round 1's assumption that the
   id resolves fine is correct; there is no subtask-specific id mismatch.**

2. **Extension — `webviewMessageHandler.ts` `"showTaskWithId"` case** (~line 970)
   `await provider.showTaskWithId(message.text!)`.

3. **`ClineProvider.showTaskWithId(id)`** (`ClineProvider.ts:2477`)
   - If `id !== current task id`: `const { historyItem } = await
     this.getTaskWithId(id)` then `await this.createTaskWithHistoryItem(historyItem)`.
   - `getTaskHistoryItem(id)` reads from `taskHistoryStore` (falls back to legacy
     global state). A subtask IS found here (it's a top-level `HistoryItem`), so
     **`getTaskWithId` resolves a subtask id correctly** — no "Task not found"
     throw in the normal case. (Throw only happens if the id is truly absent; then
     `showTaskWithId` rejects and the webview receives nothing — no tab switch — so
     that is NOT this symptom.)
   - `createTaskWithHistoryItem` → `createTaskWithHistoryItemUnlocked`
     (`ClineProvider.ts:1384`): calls `evictCurrentTask()` (unless rehydrating the
     same id), constructs a `Task` with **`startTask: false`**, then
     `scheduleTask(this.taskScheduler, task, "createTaskWithHistoryItem")`.
     **It does not await the task's `run()`.**
   - Back in `showTaskWithId`, immediately:
     `await this.postMessageToWebview({ type: "action", action: "chatButtonClicked" })`.

4. **Webview — `App.onMessage`** receives `chatButtonClicked`, maps via
   `tabsByMessageAction` to `"chat"`, calls `switchTab("chat")`. The chat tab is
   now active. At this instant `clineMessages` is whatever it was — for a fresh
   open it is **empty**, so ChatView renders the **home surface**.

5. **Asynchronously — `TaskScheduler.schedule`** acquires the single permit
   (`maxConcurrency = 1`, `TaskScheduler.ts`), then calls `task.run()` →
   `resumeTaskFromHistory()` (`Task.ts:2618`) → `getSavedClineMessages()` →
   `hydrateClineMessages(...)` → `this.ask("resume_task" | "resume_completed_task")`
   which calls `postStateToWebview()`. That state push carries the subtask's
   `clineMessages` + `currentTaskId` + `currentTaskItem` with a fresh
   `clineMessagesSeq`.

6. **Webview — state handler** (`ExtensionStateContext.tsx:358`) merges via
   `mergeExtensionState`. If this push's `clineMessagesSeq` is greater than the
   last applied one, `clineMessages` updates, `task` becomes truthy, ChatView
   switches from home to the transcript. **If the fix were running**, the
   task-scoped under-configured `apiConfiguration` would NOT re-raise `showWelcome`.
   **In the running (pre-fix) bundle**, step 6's own push (task-scoped,
   under-configured) flips `showWelcome` → `true` and `App` renders `WelcomeView`
   over everything — the round-1 path.

**Why it looks like "home" either way:** in the pre-fix bundle you may actually be
seeing `WelcomeView` (round-1 path) OR the ChatView home surface (empty
`clineMessages`), depending on config/auth timing. Both present as "dumped back to
the start page." The only way to separate them is to run the fixed bundle and see
which one remains.

### Difference between subtask-open and top-level-open paths

They are **the same code path** (`showTaskWithId` → `getTaskWithId` →
`createTaskWithHistoryItem` → `chatButtonClicked`). There is **no subtask-specific
branch** in `showTaskWithId`/`createTaskWithHistoryItem`, and the webview posts an
identical message from both `TaskItem` and `SubtaskRow`. The one behavioral
divergence that can make subtasks *feel* worse:

- A subtask's `historyItem` usually has `parentTaskId` set and often
  `status: "completed"` or `"interrupted"`/`"delegated"`. On resume this yields a
  `resume_completed_task` / `resume_task` ask whose primary button is
  **"Start New Task"** (ChatView ~479-492, 554-564). The transcript still renders;
  this is not itself a bounce. But if the opened subtask's `clineMessages` never
  reach the webview (step 6 dropped/not sent), the home surface stays — and for a
  completed subtask there is no streaming activity to force a later state push, so
  it can look permanently stuck on home. Top-level tasks the user "can open" may
  simply be ones whose state push won the seq race.

## Second reset-to-home paths considered (besides the welcome gate)

- **ChatView `!task` home surface** — the primary candidate (see above). Driven
  purely by `clineMessages` emptiness. No fix for this exists in `b2a6c9459`.
- **`clineMessagesSeq` stale-push guard** (`mergeExtensionState`,
  `ExtensionStateContext.tsx:181-190`): keeps older `clineMessages` when an
  incoming push has `seq <= prev`. This protects against an *empty* late push
  wiping a *ready* earlier push (the `cd09db10e` "Child task view returns to Home"
  fix assigns the seq synchronously at the start of `postStateToWebview`). This
  guard is present and correct in source; it does not clear messages to empty on
  its own.
- **`App.tsx` effects**: no effect resets `tab` to chat/home when `clineMessages`
  becomes empty. The only `showWelcome`-driven effect
  (`App.tsx` ~176-186) handles settings-import and does not bounce on task open.
- **No navigation is triggered by `didHydrateState`** on task open; it only gates
  the initial `return null`.

No *additional* code-level bounce path beyond (a) the welcome-gate recompute and
(b) the ChatView empty-home surface was found.
