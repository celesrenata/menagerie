# Design: Decouple the Task Board / task lifetime from the editor tab

> Revision 3. Revision 2 was reviewed (`design-review.md`, verdict CHANGES_REQUESTED: 1 HIGH, 2 MEDIUM, 2 NIT). The ownership model (Option i-b: keep the owning popout provider headless) was accepted; the blocking gaps were mechanical. This revision fixes them: (Finding 1 HIGH) the headless self-reap now fires on the provider's own `TaskCompleted`/`TaskAborted` listeners, because completion does *not* drain the registry; (Finding 2 MEDIUM) re-attach uses a dedicated `rebindView(panel)` that routes the view-close listener through `webviewDisposables` so re-open accumulates no duplicate listeners; (Finding 3 MEDIUM) `detachTabView()` nulls `this.view` *before* disposing the panel so the re-entrant `onDidDispose` short-circuits; (Findings 4, 5 NITs) the checker's `/8` summary literal becomes `/9`, and exhaustiveness of the editor-provider kinds is a recorded pre-implementation grep with an unknown-role → `dispose()` default. Responses to every finding are at the end.

## Overview

A Menagerie task opened in an editor tab is owned by a dedicated editor-render-context `ClineProvider`. Closing that tab fires `webviewView.onDidDispose`, which in the tab branch calls `await this.dispose()`, and `dispose()` drains the owning provider's task registry through `evictCurrentTask()` → `removeClineFromStack()` → `task.abortTask(true)`. The sidebar branch instead calls `clearWebviewResources()`, which tears down only webview-scoped disposables and leaves the task registry — and the running task — intact. So in the editor case the *view's* lifetime owns the *task's* lifetime; in the sidebar case it does not. The user-reported symptoms are (1) the Task Board shows entries but detail/interaction still routes through an editor surface, and (2) closing a task's editor tab kills the running task so it disappears from the board.

The root cause is confirmed in `src/core/webview/ClineProvider.ts` `resolveWebviewView` at the `onDidDispose` handler (the tab branch, selected by `inTabMode`, calls `await this.dispose()`). The board enumerates tasks via `collectTaskBoard()` → `ClineProvider.getAllInstances()` → `provider.getCurrentTask()` (`src/activate/taskBoard.ts`), reading exactly one task per provider; once the owning editor provider is disposed and removed from `activeInstances`, the task vanishes from the board.

**Two known kinds of editor-context provider exist today, and this revision keeps them distinct.** Both were confirmed by reading source (below); the claim that these are the *only* two is treated as a pre-implementation verification step, not an asserted fact — see Assumption 1, which records the `grep 'new ClineProvider(' | grep '"editor"'` result and defaults any third, unknown editor-role creator to the safe `dispose()` path.

- **Interactive popout.** `openClineInNewTab` (`src/activate/registerCommands.ts` ~line 222) constructs `new ClineProvider(context, outputChannel, "editor", …)` and resolves a `WebviewPanel`. The command itself does *not* call `createTask`; the task is created later when the webview posts a `newTask` message, handled in `webviewMessageHandler` (`case "newTask"`, ~line 718) by `provider.createTask(...)` on that same editor provider. So the popout editor provider **does** own its task today — this is exactly the provider whose tab-close aborts the running task. **This is the bug.**
- **Parallel worker.** `createParallelTaskRuntime` (`src/core/webview/ClineProvider.ts` ~line 3395) constructs `new ClineProvider(this.context, this.outputChannel, "editor", …)`, opens a `WebviewPanel`, and calls `provider.createTask(..., { startTask: false, parallelWorker: true, … })` on it. Each worker is an editor-context provider that owns exactly one worker task and surfaces on the board as a row with `parallelWorker: true`. For a worker, closing its panel aborting the worker is the **intended** lifecycle, not a bug.

Because both are `renderContext === "editor"`, the first revision's guard `renderContext === "editor" && taskRegistry.length === 0` was wrong: it would have driven every parallel-worker tab-close down a "programming error → dispose/abort" fallback while *framing worker abort-on-close as a defect*, and it rested on a false global invariant ("editor-context providers never own a task") that `createParallelTaskRuntime` directly contradicts. This revision discriminates **by an explicit per-provider role**, not by `renderContext` or registry emptiness.

This design makes closing an **interactive popout** tab a **view detach**, not a task kill, while leaving **parallel-worker** tab-close semantics (abort-on-close) exactly as they are. The mechanism (chosen in Decision A) is to detach the popout's *view* without disposing the *provider*: the popout provider keeps owning its task and survives headless in `activeInstances`, so `collectTaskBoard()` keeps enumerating it as one row — no cross-provider task mirroring and no consolidation onto the sidebar provider are required (this resolves review Findings 2 and 3). The primary durable inspection surface remains the sidebar Task Observatory (`.kiro/specs/task-observatory/design.md`), which already enumerates tasks read-only via `getAllInstances()`.

The change touches real lifecycle ownership and provider/task disposal ordering, so it is a HEAVY lifecycle change: it adds one new modeled transition (`view-detach`) to the cleanup protocol model and keeps `pnpm lifecycle:model-check` green without weakening the known-unsafe witnesses (#1469/#1021).

The technology stack is locked to the existing one: TypeScript, the VS Code extension host API (`WebviewView`/`WebviewPanel`), the existing `ClineProvider` + `TaskRegistry` + `TaskScheduler` structures, the shared reducers in `src/core/task-persistence/taskLifecycle.ts`, the `TaskHistoryStore`, the React webview under `webview-ui/src`, and the explicit-state model checkers under `scripts/`. No new framework, process model, or persistence layer is introduced.

## Decisions

### A. Ownership model — chosen: Option (i) specialized as "detach the view, keep the owning provider headless"

The brief's two options:

- **(i) Editor tab is a pure VIEW over a task owned by a surviving provider.** Closing the tab detaches the view without aborting the task; the task continues to be owned and enumerated by a long-lived provider.
- **(ii) Keep per-provider ownership but HAND OFF the running task to a surviving owner on tab close** before releasing the tab provider.

Within Option (i) there are two sub-mechanisms for *which* provider survives as the owner:

- **(i-a) Consolidate onto the sidebar provider.** The popout provider is a non-owning presenter; the task is created on and owned by the sidebar provider. *Rejected.* `collectTaskBoard()` reads exactly one `provider.getCurrentTask()` per provider, and `TaskRegistry.current` (`TaskRegistry.ts` line 42) returns a single top-of-stack task. Routing N popout tasks onto one sidebar provider puts N tasks in one registry, so the board would surface only the top-of-stack one — silently dropping concurrent popout tasks and colliding with the parallel-worker model (N workers = N providers = N rows). It also requires a cross-provider state-mirroring and message-forwarding channel that does not exist today: `setWebviewMessageListener` binds `webview.onDidReceiveMessage` to `webviewMessageHandler(this, …)` and `postStateToWebview`/`get messages()` read `this.getCurrentTask()`, all hard-wired 1:1 to the resolving provider. (This is exactly review Findings 2 and 3.)
- **(i-b) Keep the popout provider as the owner, but make tab-close detach the *view* without disposing the *provider*.** The popout provider stays in `activeInstances` with its one owned task still in its registry, now headless (no live webview). `collectTaskBoard()` keeps enumerating it as exactly one row. No consolidation, no cross-provider mirroring, no top-of-stack loss. **Chosen.**

Option (ii) is rejected for the same reason as before: moving a live, mid-run `Task` (its listeners, scheduler permit, pending edits, message queue, registry slot) between providers while it streams is a second ownership-transfer race class (the same family as the delegation/abort ordering where a late `saveClineMessages` can overwrite status), and it still leaves the editor provider owning the task up to the handoff instant.

**We choose Option (i-b).** Concretely, we introduce an explicit per-provider **view-ownership role** rather than overloading `renderContext`:

1. Add a constructor-time field `editorViewRole: "popout" | "worker" | undefined` on `ClineProvider` (`undefined` for the sidebar provider; set to `"popout"` by `openClineInNewTab`, `"worker"` by `createParallelTaskRuntime`). `renderContext` stays `"sidebar" | "editor"` and is unchanged; the new field refines the `"editor"` case. A helper `isDetachableView()` returns `editorViewRole === "popout"`.
2. In `resolveWebviewView`, the `onDidDispose` handler is still selected by the existing `inTabMode` discriminator (the panel vs. view shape, `"onDidChangeViewState" in webviewView`), **not** by `renderContext` (review Finding 6). *Inside* the `inTabMode` branch we then check the role: if `isDetachableView()` is true, call the new `detachTabView()`; otherwise (worker, or any editor tab that is not a popout) keep the existing `await this.dispose()`. The sidebar branch is unchanged (`clearWebviewResources()`).

   **Listener registration moves from `this.disposables` to `webviewDisposables` (review Finding 2).** Today the `onDidDispose` handler is pushed onto `this.disposables` (process-lifetime), while `setWebviewMessageListener` already pushes its binding onto `webviewDisposables` (view-lifetime, drained by `clearWebviewResources()`). Because re-attach (Decision C) calls `resolveWebviewView`-equivalent setup a second time on the *same surviving provider*, a view-close/message listener that is not drained on detach would accumulate: each re-open would add another `onDidDispose` and another message listener, so a later single tab-close would fire `detachTabView()`/`dispose()` multiple times. We fix this by registering the view-close `onDidDispose` disposable onto **`webviewDisposables`** (not `this.disposables`), so `clearWebviewResources()` — called by both `detachTabView()` and `dispose()` — drains it on every view teardown. After detach there is then **zero** live view-close listener and **zero** live message listener; a subsequent rebind (step via Decision C's `rebindView`) installs exactly one of each. This is asserted by the "detach→re-open→detach leaves exactly one `onDidDispose` and one message listener" unit test (Testability). The sidebar's own `onDidChangeVisibility` disposable already lives on `webviewDisposables`, so this makes the tab path consistent with it.
3. New private `detachTabView()` releases **view resources only** and leaves the provider and its task registry intact. **The step ordering is load-bearing** because the tab's `onDidDispose` handler (registered in `resolveWebviewView`) is what calls `detachTabView()`, and `detachTabView()` itself disposes the owned `WebviewPanel`, which re-fires that same `onDidDispose` handler (review Finding 3). To make the double-detach guard effective against this re-entrancy, the panel must be captured into a local and `this.view` nulled **before** the panel is disposed. The exact ordering:
   - **Guard first:** if `_disposed` is set or `this.view === undefined`, return immediately (double-detach / detach-after-dispose no-op).
   - **Capture + null:** `const panel = this.view; this.view = undefined`. Now any re-entrant `onDidDispose` fired by the upcoming `panel.dispose()` sees `this.view === undefined` and short-circuits at the guard above.
   - `clearWebviewResources()` (drains `webviewDisposables` — which, per the Finding 2 fix below, now also holds the tab's view-close listener and the message-listener binding).
   - **Dispose the captured local:** if `panel` has a `dispose` method, `panel.dispose()` inside a try/catch (mirrors the panel dispose that `dispose()` would have done — review Finding 7). Because `this.view` is already `undefined`, the re-entrant handler is a no-op; because we dispose the captured `panel` local rather than `this.view`, there is no "dispose undefined" error.
   - **Terminal-check reap:** if the sole owned task is already terminal (completed/aborted) at detach time — i.e., the tab was closed *after* the task finished — run the same reap as the `TaskCompleted` listener: `void this.dispose()`. Otherwise leave the provider live and headless.
   - **Never** call `removeClineFromStack`/`evictCurrentTask`/`abortTask`/task `dispose` for a *still-running* task, and (when not reaping) **does not** remove the provider from `activeInstances` and **does not** set `_disposed`.
   The popout provider therefore remains in `activeInstances` owning its one still-running task, now with `this.view === undefined`; or, if the task was already terminal, is reaped out of `activeInstances`.
4. Genuine disposal (extension deactivate, explicit "close task"/complete, and **parallel-worker tab-close**) still goes through `dispose()`, which still drains the registry with the existing eviction/interrupt semantics. We change `dispose()` not at all; we only stop invoking it from the *view-close* path of a **popout** tab.

**How the task stays enumerable after the view closes.** `collectTaskBoard()` maps `getAllInstances()` → `getCurrentTask()`, one row per provider. After a popout detach, the popout provider is still in `activeInstances` and its registry still holds the one owned task, so `getCurrentTask()` returns it and the board row persists with live status. Because each popout keeps its own provider, **two concurrent popout tasks are two providers = two rows**, and **N parallel workers remain N providers = N rows** — the enumeration model is unchanged for every case. This is the direct answer to review Finding 2: the task stays enumerable because *its owning provider is never disposed by a popout tab-close*, not because it was moved anywhere.

**Headless-provider lifecycle (new state to reason about).** A detached popout provider is a live, webview-less owner. It must still be reaped at the right times. This is the point review Finding 1 (HIGH) corrected: **completion does not drain the registry**, so a reap keyed on "registry becomes empty at task terminal" never fires for a standalone top-level popout task. Confirmed in source: the provider's `onTaskCompleted` listener (`ClineProvider.ts` ~435) writes `status: "completed"` to the history store and emits `RooCodeEventName.TaskCompleted`, but it does **not** call `removeClineFromStack()`/`evictCurrentTask()`. The completed task stays in `taskRegistry` as the current task — that is precisely why `collectTaskBoard()` can report a `"completed"` row for it (`taskBoard.ts` reads `getCurrentTask()` and derives status from history/last message). The registry drains only on explicit close (`removeClineFromStack` call sites), delegated-child completion, `clearTask`, or `dispose()`.

The reap trigger is therefore defined on the provider's own task-event listeners, not on a registry-drain point:

- **Reap seam = the `TaskCompleted` / `TaskAborted` listeners (`ClineProvider.ts` ~435, inside `taskCreationCallback`).** We augment `onTaskCompleted` and `onTaskAborted`: after their existing work (status write + `emit`), if the provider is a detached popout and the terminated task is the sole registry entry — `editorViewRole === "popout" && view === undefined && taskRegistry.getCurrentTaskId() === terminatedTaskId` — the provider calls `void this.dispose()` (idempotent via `_disposed`). `dispose()` then runs `evictCurrentTask()`/`removeClineFromStack()`/view-dispose/`activeInstances.delete(this)` exactly as today, so the empty headless instance leaves `activeInstances` and the board row disappears at task terminal. The disposed-task's `"completed"`/`"aborted"` status is already persisted to the history store before the reap, so history/board history views are unaffected; only the live in-memory row is removed, which is the intended "task ended" behavior.
- **Why key on the event, not on registry length:** at the instant `onTaskCompleted` fires the task is still in the registry (length 1), so a "length === 0" guard would be false. The listener already identifies the exact `taskId` that terminated, so the reap condition is "this provider's current task is the one that just terminated and there is no live view," which is decidable at the listener without waiting for a drain that never comes for top-level tasks.
- **Visible-tab completion is untouched.** The guard requires `view === undefined`. If the task completes while the popout tab is still open (`view` defined), the reap does **not** fire; the existing in-tab completion UX (the webview shows the completed task; the user closes the tab, which then detaches/reaps) is preserved. Closing that tab afterward hits `detachTabView()`, which, finding the registry already holding only a terminal task, is itself the point where the reap would then be re-evaluated — but to avoid relying on that, `detachTabView()` also performs the same terminal-check-and-reap after nulling the view (see Decision A step 3), so a tab closed *after* completion still disposes the empty provider rather than leaving it headless.
- **Extension deactivate.** Unchanged: `dispose()` on every instance drains and removes it.

This headless window is bounded (it ends at task terminal via the listener reap, at post-completion tab-close via `detachTabView()`'s terminal check, or at deactivate) and introduces no orphan: the task always has exactly one owning provider for its whole life, and the provider is reaped the moment its sole task is terminal and no view is attached.

**Tradeoff accepted.** A popout provider now outlives its visible tab until its task ends. That is a small, bounded memory cost (one webview-less provider per detached-but-running popout task) and is the intended behavior: a running task is a durable board citizen whose editor tab is just a window. The alternative mechanisms (consolidate onto sidebar; headless *holder* provider distinct from the owner) either break board enumeration (i-a) or add a third owner type and more enumeration surface for no board benefit; both are rejected above.

### B. Single-open-task invariant and the stack

The single-open-task invariant and `removeClineFromStack` are properties of a *single provider's* `taskRegistry` (LIFO stack of task IDs with `tasks.size === stack.length`, per `TaskRegistry`). In the chosen model the popout provider's registry is **not mutated** by a view detach: the task keeps the exact slot it already held in that provider's registry. So:

- A detached-but-running popout task occupies exactly one slot — the slot it already held in its own popout provider's registry. There is **no** orphan "task with no provider": the task's owning provider never changes and is not disposed by the tab-close.
- Closing the popout tab removes **nothing** from any stack (detach does not pop), so it cannot violate `tasks.size === stack.length`, cannot violate single-current-task-per-provider, and cannot disturb delegation-stack semantics (parent below, delegated child current) — the detach never pushes or pops.
- Parallel-worker providers are unaffected: their tab-close still goes through `dispose()`, which drains their one-slot registry exactly as today.

For `pnpm lifecycle:model-check`: the production-backed delegation checker (`scripts/check-task-lifecycle.ts`) operates on `HistoryItem` records and the four reducers; a view detach performs **no** reducer call and **no** `HistoryItem` status mutation, so that checker's state space and invariants are untouched. The relevant model is the cleanup protocol model (Decision D).

### C. Re-attach

After closing a popout tab, the still-running task is inspectable and re-openable:

- **Primary (in scope, no new runtime):** the sidebar **Task Observatory** inspects the task read-only via `getAllInstances()`; it observes the owning popout provider directly (that provider is still in `activeInstances`), so the task appears unchanged the instant the tab closes. No re-attach work is needed because the Observatory never attached to a webview — it reads live task state across instances.
- **Secondary (in scope):** "re-open the task in a new editor tab." We add `openTaskInNewTab(taskId)`. Because the chosen model keeps the task on its original popout provider, re-attach does **not** need cross-provider mirroring; it **re-binds a fresh `WebviewPanel` to the existing owning provider**. Mechanism: locate the owning provider via `ClineProvider.getAllInstances()` and find the one whose `getCurrentTask()?.taskId === taskId`; create a new `WebviewPanel`; call a new, dedicated `owningProvider.rebindView(panel)`.
  - **Why a dedicated `rebindView(panel)` and not a second `resolveWebviewView(panel)` (review Finding 2).** `resolveWebviewView` is written for first-time initialization: it re-runs full HTML build, `getState()` terminal-config seeding, and the `removeClineFromStack()`-on-stale-task block near its end, and (pre-fix) registered `onDidDispose` on `this.disposables`. Re-running all of that on a live, task-owning provider is both wasteful and risky (the stale-task block could evict the very task we are re-opening). `rebindView(panel)` does only what a re-attach needs, and only on an already-initialized provider:
    1. Assert `this.view === undefined` (the provider is currently headless/detached) and `_disposed === false`; otherwise log and decline.
    2. `this.view = panel`; set `panel.webview.options`; set `panel.webview.html` (reuse the same HMR/prod `getHtmlContent` branch as `resolveWebviewView`).
    3. Register exactly one message listener via `setWebviewMessageListener(panel.webview)` (pushes to `webviewDisposables`) and exactly one view-close `onDidDispose` onto `webviewDisposables` (same handler body as the tab branch: role check → `detachTabView()`), plus the `onDidChangeViewState` repost disposable onto `webviewDisposables`. Because the prior detach drained `webviewDisposables`, there is now exactly one of each — no accumulation.
    4. `void this.postStateToWebview()` so the re-bound panel renders the live task immediately.
    To avoid duplicating the HTML/listener setup between `resolveWebviewView` and `rebindView`, factor the shared "bind this panel's webview" body (options + html + message listener + view-close `onDidDispose` + view-state listener, all onto `webviewDisposables`) into a private `bindWebview(view)` helper that both call; `resolveWebviewView` keeps its first-time-only extras (terminal seeding, stale-task clear) around that call. This guarantees the two paths register listeners identically and on the same (`webviewDisposables`) lifetime.
  - Since `postStateToWebview`/`get messages()` read `this.getCurrentTask()` on that same owning provider, the reopened panel renders and drives the live task through the existing 1:1 channel with **no** new forwarding path. The provider's `view` is repopulated and `editorViewRole` stays `"popout"`, so a later close detaches again.
  - Validation: if no instance owns `taskId` (completed/closed between board render and click), do **not** create a task — show an information message ("That task is no longer running") and decline. Never fall back to `createTask`.
- **Explicitly scoped out:** re-attaching a popout task as the *sidebar's* current chat (so the sidebar webview drives it) requires `setCurrent`/focus routing into the sidebar registry and reopens the active-chat-selection surface the Observatory deliberately avoids. It is tracked as a follow-up. The primary fix (close ≠ kill) and both re-inspection and editor re-open do not depend on it.

### D. Lifecycle model impact — new modeled transition `view-detach` in the cleanup protocol model, with named state

A view detach is **not** `abandon` and **not** `interrupt`: it changes no `HistoryItem`, clears no lineage, and sets no status. It is a provider/view-resource transition, which is the scope of the **task cleanup protocol model** (`scripts/check-task-cleanup-protocol.ts`, documented in `docs/architecture/task-cleanup-protocol-model.md`, run under `pnpm lifecycle:model-check`), not the persisted delegation graph.

The current checker's `TaskState` models `abort`, `disposal`, `reversion`, `cleanup`, `finalization` and a shutdown cursor; it has **no** representation of view attachment or ownership. Simply naming a `view-detach` action would be unprovable because there is no modeled link from a view to abort (review Finding 4). We therefore add explicit state and a predicate:

1. **New per-task field** `view: "owning-visible" | "owning-detached" | "none"`. Initial value for the two modeled tasks is `"owning-visible"` (a task begins owned by a provider with a live view). `"none"` denotes a task with no view binding (e.g., a sidebar-owned task is out of scope for this field; the two modeled tasks represent popout-owned tasks for this submodel's purposes). The field is independent of `abort`/`disposal`.
2. **New action** `view-detach(task)`, enabled only when `view === "owning-visible"` and the task's `disposal === "idle"` (you cannot detach a view mid-dispose). Its transition sets `view = "owning-detached"` and asserts, in the transition itself, that it leaves `abort`, `disposal`, `reversion`, `cleanup`, `finalization`, the registry-slot abstraction, and the shutdown cursor **unchanged**. It does not enable, start, or precede any `abort`, `dispose`, `complete-abort`, `skip-final-save`, or shutdown action — the enabledness of those actions is defined solely by their existing guards, which `view-detach` does not touch.
3. **New invariant predicate** (added to `invariantViolations`): *"a `view-detach` must not change a task's abort/disposal/finalization state"* — concretely, there is **no reachable state** in which `view === "owning-detached"` co-occurs with an `abort`/`disposal` value that could only have been produced by the detach itself. Operationally: because `view-detach` is the only writer of `view` and writes nothing else, and because no other action reads `view` as a guard, the detach is provably orthogonal to the abort/dispose subspace. The invariant also asserts: a task may reach `abort`/`disposal` from `"owning-detached"` **only** via the ordinary `dispose()`/shutdown actions (deactivate / explicit close), identical to the `"owning-visible"` case — detach neither blocks nor accelerates eventual disposal.
4. **New named landmark** `view-detach-preserves-owned-task`: there is a reachable state where a task is `view === "owning-detached"` while `abort === "idle"` and `disposal === "idle"` (the task is still fully live after its view detached), **and** a reachable state where that same task later completes normal `dispose()`/shutdown (detach does not strand it). This is the model-level proof of "close ≠ kill, and the task is still reapable."

We keep the model's existing bounds (`MAX_DEPTH = 20`, `MAX_STATES = 100_000`, two tasks). Adding one orthogonal ternary field multiplies the state space by at most 3× per task; if the budget is approached we raise `MAX_STATES` explicitly per the model's extension rules rather than sampling. We add `view-detach` to `expectedActions` and the new landmark to `expectedLandmarks`.

**Checker summary literal (review Finding 4).** `scripts/check-task-cleanup-protocol.ts` prints its reached-landmark count against a hardcoded total — today `… ${result.landmarks}/8 landmarks reached …`. Adding `view-detach-preserves-owned-task` makes the total 9, so the literal `8` must be bumped to `9` (and any analogous count assertion that compares against the landmark total) in the same edit that extends `expectedLandmarks`; otherwise the summary line misreports and a count assertion could fail spuriously. This is a mechanical edit to be made alongside the `expectedLandmarks` change.

We do **not** add any transition to `taskLifecycle.ts` reducers (no `HistoryItem` transition occurs; adding one would misrepresent a view event as a persisted lifecycle event). We do **not** touch `VALID_TASK_STATUS_TRANSITIONS`. We do **not** weaken or delete the #1469 / #1021 known-unsafe witnesses: those live in `scripts/check-task-store-concurrency.ts` (a different submodel), `view-detach` writes no state those witnesses read, and this change adds only reachable-but-safe states to the cleanup submodel. The checker must still fail on any pre-existing violation.

### E. "Board still uses the editor" facet — scope-tight

The primary fix is "closing a view must not kill the task." We address "move off the editor" only as far as needed to make the board the durable surface:

- The **durable inspection surface is the sidebar Observatory**, which already exists and already enumerates tasks read-only. We do not build a new detail surface.
- The editor tab **stays available but, for popouts, becomes non-killing** (Decision A). We do not remove the editor tab or forbid opening tasks in a tab; we sever only the *popout* tab→task lifetime coupling. Parallel-worker tabs keep their existing abort-on-close.
- The legacy `TreeView` in `taskBoard.ts` is already trimmed (no focus-on-selection, no `ViewColumn.Beside` detail panel per its own doc comment); we leave it as the compat/debug snapshot writer and change nothing there except confirming it still enumerates correctly after the ownership change (the regression test in Testability).

Blast radius: the popout tab-close path, the new per-provider role field, one re-open entry point, the headless-popout self-reap, and one cleanup-model transition.

  - `resolveWebviewView` `onDidDispose`: keep the `inTabMode` discriminator; inside the tab branch, if `isDetachableView()` call `await this.detachTabView()`, else `await this.dispose()` (unchanged for workers and non-popout editor tabs). ## Error handling

- **`detachTabView()` view-resource release.** `clearWebviewResources()` and panel disposal can throw if a disposable is already disposed. `clearWebviewResources()` already pops-and-disposes defensively. Failure here is **recoverable**: wrap the panel `dispose()` in try/catch, log at `this.log` level, continue. The task and registry are never touched, so a view-cleanup failure cannot affect task execution. It is an event handler, so no value is returned; the failure is logged, not surfaced, matching the existing fire-and-forget disposal convention.
- **Role mismatch at detach.** Invariant: only `editorViewRole === "popout"` providers reach `detachTabView()`. If `detachTabView()` is somehow entered for a non-popout provider (programming error), it logs a warning and falls back to `dispose()` (the safe, task-draining path). This fires only for a true role violation. **It does not fire for parallel workers**, because workers are routed to `dispose()` by the role check *before* `detachTabView()` is ever considered — worker abort-on-close is the intended path, not a logged regression (this is review Finding 5; the first revision mislabeled worker close as a programming error).
- **Headless popout that unexpectedly still has a view at reap time.** The self-reap guard in `onTaskCompleted`/`onTaskAborted` requires `view === undefined`; if the task completes while the tab is still open (`view` defined), the reap does not fire — the normal in-tab completion UX runs, and the eventual tab-close hits `detachTabView()`, whose terminal-check then disposes the now-empty provider. **Recoverable**; no user-facing error.
- **Re-entrant `onDidDispose` during `detachTabView()`.** `detachTabView()` disposes the owned panel, which synchronously re-fires the view-close `onDidDispose`. Because `this.view` is nulled *before* the panel is disposed (Decision A step 3) and the handler guard returns on `this.view === undefined`, the re-entrant call is a no-op. **Recoverable by construction**; covered by the re-entrancy idempotency unit test. If the ordering were ever regressed, the guard would still catch the second entry on `_disposed` after the first `detachTabView()` completes — but the primary defense is the pre-dispose null.
- **`rebindView` on a provider that is not headless.** If `rebindView(panel)` is called while `this.view` is defined or `_disposed` is set (e.g., a race where the task was reaped between board click and rebind), it logs and declines (disposes the just-created `panel` to avoid an orphan window) rather than clobbering a live view or binding to a dead provider. **Recoverable**; the user sees no task appear and can retry/observe via the Observatory.
- **Re-open binds to a missing task.** `openTaskInNewTab(taskId)` where no instance owns `taskId`: validation looks up the owner via `getAllInstances()`; if none, show the info message and decline. **Recoverable**; the user is informed; never `createTask`.
- **Double detach / detach after dispose.** `detachTabView()` is guarded: if `_disposed` is already set or `this.view` is already `undefined`, it returns immediately. Combined with the null-before-dispose ordering, this prevents double panel-dispose, double resource release, and the re-entrant self-call described above.

## Input validation

- **`taskId` for re-open (external input from webview/board click).** Required, non-empty string, type-checked at the message boundary. On missing/empty/unknown owner: no task creation, user-facing info message, no throw across the extension host. Single taskId; no batch re-open in this change.
- **`editorViewRole` (internal, set at construction by the two editor call sites).** Union `"popout" | "worker" | undefined`; read only by `isDetachableView()` and the detach/reap guards. No external input.
- **`renderContext` (internal, constructor-provided).** Already `"sidebar" | "editor"`; unchanged; not used as the detach discriminator (role is).

## Invariant ownership

- **"A running task always has exactly one owning provider in `activeInstances` for its full life" (new).** Owned by `ClineProvider`: popout detach never removes the owner; the owner is reaped only when the task reaches terminal state or on deactivate. This layer owns it because provider construction, task creation, detach, and reap all live inside `ClineProvider`.
- **"Only a `popout`-role editor provider detaches its view on tab-close; workers abort" (new).** Owned by the `onDidDispose` role branch plus `isDetachableView()`. Enforced in code at the single branch point; set correctly at the two construction call sites.
- **"View detach ≠ task abort for a popout" (new, modeled).** Owned by the cleanup protocol model (Decision D) plus the detach guards. The model owns the proof that detach cannot enable abort (orthogonality invariant + landmark); the code owns runtime enforcement.
- **Single current task per provider / stack `size === length` (existing).** Still owned by `TaskRegistry`; untouched because detach mutates no registry.
- **Persisted `HistoryItem` transition legality (existing).** Still owned by `taskLifecycle.ts` reducers; untouched because detach performs no reducer call.

## Assumptions (and how each is verified during implementation)

1. **The two *known* editor-context provider kinds are the popout (`openClineInNewTab` → later `createTask` via `newTask` message) and the parallel worker (`createParallelTaskRuntime` → `createTask`).** The two cited call sites are verified by reading source (`registerCommands.ts` ~222 and `ClineProvider.ts` ~3395; popout ownership via the `webviewMessageHandler` `newTask` path ~718). **Exhaustiveness is not yet proven and is a required pre-implementation step (review Finding 5):** run `grep -rn 'new ClineProvider(' src | grep '"editor"'`, record the full result set in the implementation PR, and assign each hit an explicit `editorViewRole`. The stated contract is that any editor-context provider whose role is unknown/unset defaults to the existing `dispose()` path on tab-close — so a missed third creator fails safe (task-draining as today), never into a silent detach. Only `"popout"` opts into detach.
2. **Keeping the popout provider headless (webview-less, still owning its task) does not break any code that assumes `view` is defined while a task runs.** Verified by grepping `this.view` reads on paths reachable from a running task and confirming they are guarded (`postMessageToWebview`/`postStateToWebview` already no-op or guard when `view` is undefined, as the sidebar-hidden case already produces a webview-less-but-task-owning provider today). Add a unit test that a headless popout provider's `postStateToWebview()` is a safe no-op.
3. **A detached popout provider is reaped at task terminal (via the `TaskCompleted`/`TaskAborted` listener), at post-completion tab-close (via `detachTabView()`'s terminal check), or at deactivate — with no earlier and no missed reap.** This explicitly accounts for the fact that completion does **not** drain the registry (review Finding 1): the reap is keyed on the terminal *event* for this provider's current task plus `view === undefined`, not on registry-emptiness. Verified by the self-reap unit tests (event-triggered reap with the task still in the registry; no reap while visible; terminal-check reap on later tab-close) and by asserting the board row persists until task end and disappears at task end.
4. **`clearWebviewResources()` plus panel disposal fully releases popout view resources with no listener leak when `dispose()` is skipped.** Verified by asserting `webviewDisposables` is drained and the panel is disposed in the detach unit test.
5. **The cleanup protocol model represents `view-detach` plus the ternary `view` field within budget.** Verified by running `pnpm lifecycle:model-check` and confirming completion within `MAX_STATES`; if approached, raise the bound explicitly per the model's extension rules rather than sampling.
6. **The sidebar `ClineProvider` is a process-lifetime singleton not disposed by any tab close.** Verified (first review confirmed: created once in `extension.ts` as `"sidebar"`, disposed only on deactivate); unchanged by this design, which no longer routes popout tasks onto it.

If assumption 1 or 2 fails (a popout provider genuinely cannot run headless, or a third editor creator owns tasks), the role branch defaults that provider to the existing `dispose()` path, preventing a leaked ownerless running task, and the finding is surfaced for a follow-up rather than silently changing abort semantics.
